# 决策记录（ADR）：组团流水线的执行通道

- 状态：**待用户拍定**（本文只把事实与两条路摆清，不替产品做决定）
- 相关：spec §4 决策 **D10**、用户故事 **I1–I5**、工单 `tickets/021`、`tickets/020`（交接父子链）
- 日期：2026-10-06

## 为什么要记这一条

D10 写的是："组团协作 = `group_task_templates` + 一次运行实例；步骤间执行**复用 `message_bot` 交接链路**（grant/深度上限/审计原样生效），不新造通道。"

本轮把这条路摸到底，结论是**按字面做不到**：交接台的入口签名要求一次"真实在跑的 run"签发的断言。

- `server/src/agents/handoff.ts:64-77`：`HandoffDesk.send()` 的第一个参数是 `from: RunAssertion`，注释写明"答案回到哪儿也由它决定——让 Bot 自己报线程，就等于让它可以把一轮丢进它从没参加过的对话"。
- 编排器（流水线）不是一次 run，拿不到这个断言。**伪造一个**＝同时绕过 grant、深度上限与审计三道闸，而选这条链路的**全部理由**就是这三道闸原样生效。

也就是说：D10 不是"实现有点难"，是**它描述的那条通道从外部不可进入**。要么改变编排器的位置（A），要么改变谁掌握步序（B）。

## A. 编排器自己发起每一层的无人值守 run（建议）

流水线按步序逐层调用**已存在的无人值守通道**（`routines/run-turn.ts` 的 `createTurnRunner`：本地 `PostgresAgentRunner` + 平台线程锁 + 同一条 transcript），每步 `board.opened({source:"handoff", parentTaskId})` 落一张子卡，上一步产出注入下一步指令。

- D10 的实质（"不新造执行通道"）保住了：复用的是本仓库**已经为无人值守工作打通**的那条路，而不是再造一条 RPC。
- I2/I3/I4（子任务、挂起恢复、**中止/跳步**）都由编排器**确定性地**掌握——这正是 I4 的要求。
- 代价：① 措辞要改，从"复用 `message_bot`"变成"复用无人值守 run 通道 + 沿用同一套 grant/审计口径"；② 员工之间"能不能对话"的**授权语义**要重新定义：现在那是 handoff grant（`mayAddress`），A 方案里编排器是替人派活，权限应落在"这个人能不能用这个员工 + 这个组是谁"，**不是**"员工 A 被授权员工 B"。这一条如果不写清楚，就会悄悄绕过 D11 的"每员工独立授权"。
- 还依赖一件未完成的事：`postgres-runner` 目前**丢弃** `board.opened()` 返回的卡 id，交接父子链因此还没接上（`tickets/020` 末节已把接缝四步写清）。

## B. 由第一步的 run 自己去逐跳交接

第一步照常是一次真人/编排器发起的 run，之后每步由上一层员工调 `message_bot` 交给下一位。治理最纯——一行都不用新写。

- 代价致命：**"N 步计划"变成模型的自由发挥**。中止、跳步、步序状态、"第 2 步批准后从第 2 步继续"都要靠提示词祈使，I4 与验收标准里的确定性断言无法成立；测试决策 #6 也测不了。
- 适用面：如果产品后来只想要"把同事叫进来一起干"而不想要可管理的流水线，B 更省。但那不是 I1–I5 写的东西。

## 建议与后果

选 **A**。同时需要三处联动改动（都要显式做，不要偷偷改）：

1. 在 spec §4 把 D10 的"复用 `message_bot` 交接链路"改成"复用无人值守 run 通道，交接的 grant/审计口径另行适用于编排器"，并在此文件留一条指向。
2. 定义编排态的授权：谁能对该组派活、组内每位员工是否要求该人可用（建议：都要求，且不因入组而扩权）。
3. 先接 020 的父子链（A 方案需要父卡 id），再开 021 的两张表——`steps` 里存什么、`runs` 里是否要存 run 断言，都取决于本决定，所以现在**不预先建表**是对的。

拍定之前，021 保持未开工；这比先建两张表再发现要改强。

## 决策（2026-10-07 拍定＝A；用户在该项目上给了全权授权，时代为决策不再等确认）

选 **A**（编排器逐层调用**已存在的无人值守 run 通道**）。判据是**可验收性**：B 把"N 步计划"交给模型自由发挥，I4（中止/跳步/从第 2 步续跑）与 spec 测试决策 #6 都要求**确定性**，而确定性只能握在编排器手里。A 的实质代价不在代码量，在**授权语义要重定义**——"员工 A 被授权找员工 B"（handoff grant）在 A 方案里不是那道闸，真正的闸必须是"**这个人能不能用这个员工**、以及这个组是谁"；这句话不写清楚，就会悄悄绕过 D11 的每员工独立授权。

三处联动改动按原计划执行，顺序不变：
1. spec §4 的 D10 措辞改为"复用无人值守 run 通道，交接的 grant/审计口径另行适用于编排器"（本文件即留痕处）。
2. 编排态授权定义：组内每位员工都要求**发起人可用**，不因入组而扩权。
3. **先接 020 的父子链**（`postgres-runner` 目前丢弃 `board.opened()` 返回的卡 id），再开 021 的两张表；`021` 在父子链接通前不建表。

## 三处联动改动的执行状态（2026-10-07）

1. ✅ **spec 措辞已改，而且改了三处而不是 D10 一处**：`D10`、用户故事 `I5`、测试决策 `#6` 三句说的是同一件事，只改 D10 会留下互相矛盾的需求（前一次会话就是按"改一条"理解的）。现在三句统一读作"复用既有无人值守 run 通道，暂停闸／白名单／线程锁／审计原样生效"。
2. ✅ **编排态授权已成文为 I6**：谁能对 Group 派活＝对该 Group 有权限的人；**逐步校验"这个人能不能用这一步的员工"**，不因入组扩权；不过 ⇒ 该步拒绝开跑并给可行动的失败，**不许换成别人代跑、也不许用平台身份替人跑**。测试决策 #6 把这条列进了断言，因为它正是"悄悄绕过 D11"会留下的形状。
3. ✅ **020 的父卡 id 已接通**（`board.opened({parentRunRef})` 在投影器内反查父卡，落地记录在 `tickets/020`），所以两张表现在可以设计。一条设计约束顺手定在这里：**`steps` 不存 run 断言** —— 断言是每次无人值守 run 现场签发的一次性凭证，存进模板就是把一次治理冻在表里，而模板要被复用无数次。

## 补充（2026-11-04）：WakerFlow 动作节点直调工具的例外

- 状态：**已拍定**（2026-11-04，用户采纳 `docs/specs/2026-11-04-wf7-flow-graph-nodes.md` 决策 D6 = A-1）。
- 相关：故事 WF7（D10）；规格 §3.5 和阶段 WF7-4。

### 例外是什么

本 ADR 选 A 的含义是：流水线的每一步都是一次员工轮次，经由已有的无人值守 run 通道（`pipeline/turn-channel.ts` 的 `createPipelineStepRunner`，背后是 `routines/run-turn.ts` 的 `createTurnRunner`）执行。WF7 新增的**动作节点**（`kind: "action"`）是唯一的例外：它不开员工轮次、不调用模型，而由编排器以该步骤员工的身份，用编辑器里写好的参数，直接调用**一个** MCP 工具（`server/src/plugins/store.ts` 的 `callTool`）。

例外的理由：动作节点要的是确定的调用，即"这个工具、这些参数"。放进一次轮次里，模型可能改写参数，还要花模型额度。

例外的范围只到这里。worker、decision、嵌套 Flow 节点仍然遵守本 ADR 的 A：worker 步骤照旧走无人值守 run 通道，decision 由编排器求值、不碰任何员工能力，嵌套 Flow 通过 WakerFlow 自己的启动路径开出子运行。

### 必须通过的闸门

动作节点每执行一次，按下面的顺序检查，任何一道不放行，工具都**一次也不调用**：

1. **`guardBotTurn`**（`server/src/agents/lifecycle.ts`）：员工处于暂停状态，或者其他生命周期状态不允许开始轮次时，拒绝执行。与轮次使用同一个函数，不另写一份判断。
2. **`headlessTurnRefusal`**（`server/src/admin/controls.ts`）：Use Bots 关闭、企业管控不允许等，与无人值守轮次同样拒绝。
3. **I6**：运行发起人必须仍然能使用该员工，用的是逐步执行时的同一个判定，不因员工"在流程里"而扩权。
4. **审批闸门**：`callTool` 内部的审批闸门照常生效，判定的发起人是运行发起人（`actorId`）。需要审批时，这一步停在 `awaiting_action` 并带 `approvalId`；批准后经审批续跑路径恰好执行一次；被拒绝时这一步失败，没有副作用。SEC1 的"禁用"规则同样在这里生效。
5. **只限 MCP 工具**：动作节点只能引用已授权给该员工的 MCP 工具（`<serverId>/<toolName>`）。电脑动作（shell、文件、浏览器）、`host/*` 和交接都不能作为动作节点；保存时校验一次，执行时再校验一次。
6. **审计**：每次调用都写审计行，发起者记为这次 WakerFlow 运行（与轮次的审计口径一致），被任何一道闸拒绝时同样写一行，并记下是哪一道闸。

### 锁定

WF7-4 必须带测试逐条锁定上面的闸门：员工暂停时、`headlessTurnRefusal` 拒绝时、发起人不能使用该员工时、引用了非 MCP 工具或未授权的工具时，`callTool` 的调用次数都为 0；需要审批时，批准前调用次数为 0，批准后为 1。另有一条测试断言 worker 步骤仍然只经过 `createPipelineStepRunner`。以后放宽其中任何一条，都要先修改本节。
