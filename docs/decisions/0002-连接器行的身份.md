# 决策记录（ADR）：连接器行的身份——一个目录键在多个租户下必须各有一行

- 状态：**已拍定＝方案 B**（2026-10-07，用户授予全权后代为决策；理由见文末"决策"）
- 相关：spec **J4 / D11 / E3**、决策 **D12**、工单 `tickets/028`、`tickets/027`、`tickets/025`（§5 三租户并行演示）
- 日期：2026-10-07（拍定于同日）

## 决策（为什么是 B，以及已经落到哪一步）

选 **B**（行身份带租户前缀，目录键另存一列），理由不是"看起来简单"，而是**可验证性**：A 要把 `mcp_servers` 主键换成 `(tenant_id, id)` 并重建 5 条子表外键，它的失败方式只在**有跨租户残留的真实部署**上出现，本机两种库都测不出来；B 每一步都能留在绿上，且漏改一处的表现（"列表里有、调用说没有"）是可测的。

**已落地的两步（扩展 + 收缩）**：迁移 `0073_mcp_catalogue_key.sql` 给 `mcp_servers` 加 `catalogue_key` 列 + `UNIQUE (tenant_id, catalogue_key)`，并把每行的 `id` 回填进 `catalogue_key`（拆分之前 `id` 就是目录键，回填是如实重述而不是猜测）。收缩于 2026-10-08 落地：写入按 `id = <租户>:<目录键>`、读点按语义分流（"哪一行"用 `row.id`，"哪个 app"用 `catalogue_key ?? id`），验收靶心是 `openbot/server/tests/plugin-tenant-catalogue-row.test.ts`（两租户各一行、重复添加不落第二行、列表/`serverExists`/`serverAddress` 认这一行、**授权在各自行上解得开**）。

**测量**：连接器这一族（`plugin-*.test.ts` + `connector-*.test.ts`，20 个文件）从 HEAD 的 **431 pass / 28 fail** 降到 **460 pass / 1 fail**；直接下游 12 个文件 **219 pass / 0 fail**。剩的 1 条在 HEAD 基线里就有，形状是对不可达 URL 的拨号没有截止时间导致的 5s 超时，**不是行身份的症状**（同一族里它会在两条之间漂移）。逐条读点归宿、两处与工单清单不同的最终做法（`or` 只用于读侧、`grant`/`ref` 不改而改建 ref 的地方）、以及夹具里两类"因为读不到而变绿"的假绿，记在 `tickets/028-连接器行身份.md` 末节"收缩落地并验过了"。

## 事实（实测，不是推断）

`mcp_servers.id` 是**全库主键**，而"把目录里的连接器加进来"这条路径写的 id **就是目录键本身**：

- `src/plugins/store.ts:2598` — `insert(mcpServers).values({ id: resolved.entry.key, ... })`；
- `src/plugins/store.ts:2582-2592` — 先 `select ... where id = <目录键>` 判"有没有"，而这一步在 RLS 下**只看得见本租户 / `system` / `platform` 的行**；
- `src/plugins/store.ts:2605` — 写入是 `onConflictDoUpdate(target: mcpServers.id)`。

于是：**整个部署只能存在一行 `google-drive`**。第一个加上它的租户拥有那一行；之后任何租户加同一个连接器，预检回答"没有"，写入撞上别人的行 ⇒ 策略拒绝。以受 RLS 约束的 `openbot_app` 角色复现：

```
begin;
set local app.tenant_id = 'w-tenant-a';
insert into mcp_servers (id,title,vendor,url,provenance)
  values ('google-drive','Google Drive','Google','https://a','first-party')
  on conflict (id) do update set url = excluded.url;
-- ERROR: new row violates row-level security policy (USING expression) for table "mcp_servers"
rollback;
```

上层没有把这个错误映射成产品语言，所以用户看到的是一条 500。**这不是迁移 0072 造成的**：0072 之前，该行的 UPDATE 侧 `USING`/`WITH CHECK` 同样不允许别的租户改写，这条错误一直在。

## 与 spec 的冲突在哪

spec 的口径是明确的：

- **J4**「模型凭据、连接器 token **按租户**入加密 vault；底座"管理员上架目录"升级为**平台级目录**，租户在目录内**自助开通到自己的账户**」；
- **D11**「平台控制目录，租户控制装配」；**E3**「员工所有者在装配页给自己的员工自助勾选安装/卸载」。

"开通到自己的账户"就是要**每租户各自有一行**。现在的形状是"目录行是全局单例"，恰好相反：租户不是"开通到自己的账户"，而是**竞争同一行**。附带说明：`credentials`（部署级 OAuth client 与每人的 token）与 `plugin_grants`（主键 `(kind, ref, agent_id)`，`ref` 仍是 `google-drive/search_files`）**已经是按租户隔离的**，缺的只有"服务器行"这一层身份。

## 爆炸半径（今天谁按服务器键引用）

| 位置 | 形状 |
| --- | --- |
| `mcp_servers` | `PRIMARY KEY (id)`；`FOREIGN KEY (credential_id) → credentials(id) ON DELETE RESTRICT` |
| `mcp_tools` | `PRIMARY KEY (server_id, name)`；`FOREIGN KEY (server_id) → mcp_servers(id) ON DELETE CASCADE` |
| `mcp_user_credentials` | `PRIMARY KEY (server_id, user_id)`；`FOREIGN KEY (server_id) → mcp_servers(id) ON DELETE CASCADE` |
| `team_bot_consents.server_id`、`team_bot_consent_defaults.server_id` | 按同一键存文本 |
| `credentials.provider`、`model_registry.provider` | 存**目录键**（厂商语义，不是行身份） |
| `plugin_grants.ref`、`skill_tools.ref` | 存 `<目录键>/<工具>` |

最后一行是选择的关键：**很多地方引用的是"目录键"这一语义**，而不是某一行的身份。

## A. 把主键改成 `(tenant_id, id)`

`mcp_servers` 主键换成 `(tenant_id, id)`，子表的外键与主键都跟着带 `tenant_id`（`mcp_tools (tenant_id, server_id, name)`、`mcp_user_credentials (tenant_id, server_id, user_id)`，两张 consent 表的外键同理）。

- 好处：`id` 继续等于目录键，`credentials.provider`/`plugin_grants.ref` 等"厂商语义"完全不动；读路径里成百的 `where id = <键>` 一字不改（RLS 会替它过滤）。
- 代价：**这是破坏性约束迁移**。要 drop PK、drop FK、补/校对子表的 `tenant_id` 值、再按复合键重建，且 `on delete cascade` 的语义要在复合键下重做一遍。任何一张子表里存在与父行 `tenant_id` 不一致的历史行，重建外键就会当场失败。测试基线（`plugin-user-credential`、`plugin-routes`、`adding a curated server over HTTP`）同时要跟着改夹具。
- 风险窗口：迁移在开发库上"看起来干净"（行少），在真实部署上可能有跨租户残留。这条路的失败方式是**部署期才出现**。

## B. 行身份带租户前缀，目录键另存一列（建议）

- `ALTER TABLE mcp_servers ADD COLUMN catalogue_key text` + 回填（`provenance='first-party'` 的行 `catalogue_key = id`）；
- 加 **`UNIQUE (tenant_id, catalogue_key)`** —— 这正是"每租户每键一行"要的那条约束；
- 添加路径改成写 `id = <本次生成的每租户机器键>`（例如 `${tenantId}:${entry.key}`，或 uuid）且 `catalogue_key = entry.key`；
- **所有按"厂商语义"解析的地方改读 `catalogue_key`**：目录条目查找（`access.ts` 与 `store.ts:1559` 那一句 `entry?.auth.kind !== "user-oauth"`）、`credentials.provider`/`plugin_grants.ref` 的匹配、`listTools` 的展示归属；
- 子表**一行都不用动**：`server_id` 仍指向一个全局唯一的行身份，外键与级联语义原样成立。

好处是它是**纯扩展**：不加不改主键、不 drop 任何约束，旧行（`system`/平台拥有的那些）继续按现状工作，可以先加列、再分批改写入点、最后收缩掉"id 即目录键"的假设。风险集中在**一处**：`where id = <目录键>` 这类查询在新行上不再命中，必须逐一改成按 `catalogue_key`（或按新行身份）查——漏一处的表现是"连接器在列表里、调用时说没有"，可测。

代价是要认真清点读点。清点方法（别靠记忆）：`grep -rn "mcpServers.id" src/` 的每一处都要判定它要的是**行身份**还是**目录键**，判错就是静默查不到。

## 建议与后果

选 **B**，并按这个顺序做，每步都保持绿色：

1. 加列 + 回填 + `UNIQUE (tenant_id, catalogue_key)`（只有扩展，谁都不破坏）。
2. 先把**测试**钉住今天的错行为：两个租户各自加 `google-drive`，断言两行都存在、互相不可见（现在第二个是 500）。这一步产出的是"改完之后必须绿"的靶心，写在 `tickets/028` 的验收里。
3. 改添加路径（新行身份 + `catalogue_key`），改读点（目录键语义那批），一次一批，每批跑 `plugin-routes`、`plugin-user-credential`、`tenant-package` 三个文件。
4. 收缩：删掉"id 等于目录键"的假设与只为此存在的兼容分支。
5. 027 的夹具随新形状改掉——它 9 条失败与全量里 2 条 `(unnamed)` 是本条的症状，不是独立缺陷。
