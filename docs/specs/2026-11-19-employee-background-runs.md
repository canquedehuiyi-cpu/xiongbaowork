# 期九：后台长跑——关掉网页，员工照样把活干完

日期：2026-11-19 · 状态：**规格草稿，等用户拍板**（§8 四个问题）
上级方案：`docs/specs/2026-11-19-codex-grade-employee.md` §5「期九 后台长跑」
基线：`main` 724bb0bf（期六 #708 之后）。期五（#709，后台轮墙钟 25 分钟、工具段数 80）尚未合入；期九的实现排在它合入之后。

## 为什么做

用户希望员工能像 Codex cloud 一样在后台长时间干活：交代完任务就可以关网页、锁手机，回来看结果。2026-11-19 已拍板「做，排在期五之后，先写规格给用户看」。

现在的问题出在**网页（和桌面版）的单聊**：员工在这里用电脑（开网页、点按钮、跑命令、读写文件）时，每一步都要靠用户打开着的那个页面去转一手。页面一关，员工发出的下一步就没人接，任务停在半路；用户回来再发消息，这一步会被记成「没有执行」。

## 用户说过的

- 「我要的是一个跟 codex 一样能力的数字员工的能力。」
- 「我要的不是外形上像 codex，我要整体能力上也要对齐。」
- 期九拍板（2026-11-19）：聊天里的电脑工具改为在服务器执行，前端只负责渲染，关掉页面任务照跑；先写规格给用户看，再分期实现。
- 长期规矩：界面改动先截图给用户确认再推；main 上已有的断言不改，要改先报。

## 1. 目标

1. **关掉也照跑**：网页、桌面版窗口关掉，手机锁屏，网络断开，员工都把这一轮跑完（到时限为止）。
2. **回来看得到全过程**：重新打开对话，看到员工做过的每一步（命令和输出、打开过的页面截图、计划清单、思考块、子代理卡片），还在跑的话接着实时看。
3. **跑完通知**：这一轮结束（做完、出错、需要你）而你不在页面前时，通知你。手机 App 推送；绑定了微信等渠道的，按渠道设置推送。
4. **底线不降**：审批、人工接管、员工权限开关、只读目录、SEC1 底线都和现在一样严。

**不做（这一期）**：
- 不做 Codex cloud 那样的「任务列表」独立页面：后台跑的轮就在原对话里，侧栏会标出来。
- 不改群聊、看板、例程、手机 App、微信这些入口：它们已经由服务器执行（见 §2.1）。
- 电脑以外的浏览器工具（管理员工 / 技能、组件画廊这类）仍由浏览器执行，页面关了就答「页面已关闭，没有执行」。

## 2. 现状（只读摸底，路径均在 `xiongbao/` 下）

### 2.1 哪些入口会因为关页面卡住

| 入口 | 谁在执行电脑工具 | 关掉页面后 |
|---|---|---|
| 网页 / 桌面版**单聊里的普通消息** | **浏览器**（再转发给服务器的电脑接口） | **卡住** |
| 单聊里 @ 别的员工派活 | 服务器（派活队列，`channels/dispatch.ts`） | 继续 |
| 群聊 | 服务器（`index.ts` `groupTurnOptions.toolsForTurn`） | 继续 |
| 看板卡、例程、员工自己定的跟进、目标 | 服务器（`unattendedTurnRunner` 等） | 继续 |
| 手机 App 对话、微信等 IM 渠道 | 服务器（`delivery/router.ts` → `approvalContinuationRunner`） | 继续 |
| 审批通过后的续跑 | 服务器（`approvals/resume-sweep.ts`） | 继续 |

所以要改的只有第一行，但它是用户最常用的入口。期六的对标评测也绕开了它：`scripts/e2e/employee-eval/run-xiongbao.ts` 头部写明「对话里的 `computer_*` 是前端工具……没有页面就没有人执行」，评测改走看板派活。也就是说，**评测量到的是服务器路径，用户在网页单聊里实际用的是另一条路径**。

### 2.2 网页单聊一轮是怎么跑的

1. 浏览器经 AG-UI 向 `/agent/:id/run` 发起一次运行（SSE 流）。服务器的 `PostgresAgentRunner`（`server/src/threads/postgres-runner.ts`）跑模型，事件流回浏览器。
2. 电脑工具在浏览器里注册成「前端工具」（`app/src/lib/copilot/computer-tools.tsx` 368 行起，`useFrontendTool`，共约 20 个）。模型调用其中一个时，服务器这次运行就结束了；中间件 `HeadlessToolsMiddleware` 看到这个工具是浏览器提供的，就不接手（`toolkit/src/headless-tools.ts` 93、184 行 `callerOffers`）。
3. 浏览器里的处理函数其实只是转发：`callComputer` 调服务器的 `/api/computers/:botId/...`（`app/src/lib/computers/call.ts`），真正动手的仍是服务器的电脑网关（`server/src/computer/gateway.ts`）。拿到结果后，浏览器把结果附进消息，**再发起一次新的运行**，模型接着走下一步。一轮里调多少次电脑工具，就往返多少次。
4. 写操作（点击、输入、按键、跑命令、写文件、本地应用、桌面控制）由浏览器先送到服务器的审批门（`app/src/lib/copilot/approval-tools.tsx`，`POST /api/approvals/computer/:botId`）。要问人时服务器回 202，浏览器停下这一轮（188 行 `stopAgent`），**之后由服务器在你批准后执行这一步并接着跑完**，续跑本身就是服务器执行的无头轮。

**断线时会发生什么**：
- 服务器这边的运行不会因为浏览器离开而中断：runner 自己订阅整条流，浏览器拿到的是回放（`postgres-runner.ts` 982～998 行注释「THE SERVER FOLLOWS ITS OWN TURN TO THE END, WHOEVER IS WATCHING」）。所以**纯说话的部分**照样说完、落库。
- 但只要模型调了电脑工具，这次运行就结束在「等浏览器执行」。页面关了，没有人执行，也没有人发起下一次运行，任务就停在这里。
- 用户回来后：重连只会重放「需要人回答」的那类工具，普通前端工具不会重跑（`app/src/components/computer/handoff-resume-notice.tsx` 17 行）。下次发消息时，这个悬空的调用被补上一句「没有执行」（`app/src/lib/copilot/repair-history.ts` 15 行 `UNANSWERED`），员工只能从头再来。
- 例外：页面关闭时正卡在「请人接管」的那一步，同一个浏览器回来时会出现「继续任务」按钮（`handoff-resume.ts`），靠的是存在本机 `localStorage` 里的记号，换台设备就没有。

### 2.3 无头路径怎么执行同一批工具

`server/src/computer/headless-tools.ts` 的 `createHeadlessComputerTools` 给同一批工具（导航、读页、快照、点击、输入、按键、滚动、列目录、读写文件、跑命令、请人协助、请人输密码、请人登录、本地应用、桌面控制、`report_refusal`）各写了一份服务器实现，直接调同一个电脑网关。`HeadlessToolsMiddleware` 在服务器上执行这些调用、把结果接回模型，最多 30 段（期五改 80）。轮次执行器（`toolkit/src/run-turn.ts`）给每轮套 5 分钟墙钟（`toolkit/src/limits.ts` 10 行，期五改 25 分钟）。

和浏览器路径的差别：

| 方面 | 浏览器路径（网页单聊） | 无头路径（群聊、看板等） |
|---|---|---|
| 审批 | 写操作先到审批门；读页、快照为省开销直接发，被规则拦下再补走审批门 | 每个动作都在网关里过审批门；要问人时抛出「挂起」，轮次结束在「等你批准」，批准后服务器续跑 |
| 人工接管、输密码 | 浏览器在工具里一直等（输密码最多 10 分钟，`computer-tools.tsx` 64 行；接管不设上限），人交还后接着跑 | 立即挂起，轮次以「等待」结束、卡进待验收；**没看到交还后自动续跑**（登录请求有续跑，`passwords/resume.ts`） |
| 实时画面 | 浏览器每次转发前报一次「电脑在动」，画面面板自动弹出（`computers/call.ts` 46 行） | 画面本身照样能看（按员工的电脑推流，与谁执行无关），但没有自动弹出的触发 |
| 对话里的页面截图 | 截图在服务器的 `/navigate` 接口里存（`computer/routes.ts` 341 行） | 网关直接导航，**不存截图**，对话里的截图卡片是空的 |
| 预算 | 每次工具往返都是新运行，步数（40 + 续 1 轮）按每次运行算，实际不封顶；没有墙钟 | 段数封顶（30 / 80），每段步数 48，墙钟 5 / 25 分钟 |
| 停止 | 浏览器中止请求 | 轮次执行器中止 |

### 2.4 现有的「刷新后回放」「重连续上流」

- **回放**：一轮结束后，事件逐条写进 `thread_run_events`，消息快照写进 `threads`（`postgres-runner.ts` 1001 行 `persist`）。重新打开对话时，`connectAgent` 先重放，再用存储的历史补齐（`app/src/components/channels/channel-chat.tsx` 约 715～800 行、`thread-messages.ts`、`repair-history.ts` 的 `withStoredAnswers`）。
- **续上流**：打开对话时如果这一轮还在跑，加入线程会一直开着，把后面的事件实时接过来（`app/src/lib/copilot/join-thread.ts`）。服务器跑的无头轮和网页轮用的是同一个 runner（`index.ts` `routineAgentRunner = localThreadRunner`），所以**打开一个正在跑的无头轮也能实时看**。
- 缺口一：**只在一轮结束时才落库**。跑到一半进程重启（发版、崩溃），这一轮的过程全丢。一轮 5 分钟时问题不大，25 分钟以上就是实打实的风险。
- 缺口二：正在跑的轮只在当前进程的内存里。部署成多副本（Helm 图表默认 2 个副本）时，重连落到另一个副本就看不到实时过程。docker-compose 和桌面版是单进程，不受影响。

## 3. 方案对比

### 方案 A：网页单聊也改由服务器执行电脑工具，前端只渲染（推荐）

单聊的运行和群聊一样挂上 `HeadlessToolsMiddleware` + `createHeadlessComputerTools`；浏览器不再注册电脑工具的处理函数，只保留渲染（命令块、截图卡片、接管卡、审批卡）。一轮从头到尾都在服务器跑，浏览器只是观众。

- **好处**
  - 关页面、锁屏、断网都不影响，这正是目标本身。
  - 执行路径合成一条：单聊、群聊、看板、例程、手机、微信、审批续跑全部走同一套工具和同一个审批门，对标评测量到的就是用户实际用到的。
  - 改动比看上去小：浏览器处理函数现在本来就只是转发给服务器的电脑接口（§2.2 第 3 点），真正干活的网关不用动。
  - 一轮内不再每步往返浏览器，少了大量网络往返和重新发起运行的开销，长任务更稳。
  - 评测可以不用浏览器直接走聊天接口（HTTP 客户端即可），冒烟能覆盖用户真实路径。
- **代价**
  - 要补齐 §2.3 表里无头路径缺的几样：接管 / 输密码的等待与续跑、截图存储、实时画面自动弹出。
  - 单聊轮要有墙钟和统一的整轮预算（现在实际不封顶），需要用户定上限（§8 问题 2）。
  - 一轮更长，必须补上「跑到一半也落库」和中断说明。
  - 过渡期要防止同一步被浏览器和服务器各执行一次（见 §7 风险 1）。
- **工作量**：中偏大，4 个服务器期 + 2 个界面期左右（§5）。

### 方案 B：保留浏览器执行，断线后自动转交服务器

页面在时照旧；服务器发现浏览器断开（心跳停了、流断了），就接手悬空的工具调用，用无头方式跑完。

- **好处**：页面开着时体验完全不变。
- **代价**
  - 两条执行路径永久并存，每加一个工具都要写两遍、测两遍。
  - 「断开」很难判准：手机锁屏、标签页休眠时浏览器会冻结计时器，但连接可能还在；网络抖一下又会误判。
  - 最危险的是**重复执行**：服务器接手的同时浏览器醒过来，同一个点击、同一条命令可能跑两次。要给每个调用加全局锁和幂等键，复杂度最高。
  - 评测仍然量不到浏览器路径。
- **工作量**：大，而且长期维护成本最高。

### 方案 C：只给「后台运行」入口用服务器执行

单聊输入框旁加一个「后台运行」开关或按钮，打开后这条消息走现有的派活队列（和 @ 派活同一条路：服务器执行、有看板卡、进程重启有清理）；普通消息照旧。

- **好处**：改动最小，复用派活的队列、租约、重启清理和通知；用户明确知道哪些在后台跑。
- **代价**
  - 要用户事先选，忘了选的普通消息关页面照样卡住，没有解决「关掉照跑」。
  - 两种体验并存：后台那条现在是跑完才刷新进对话（`channels/dispatch.ts` 头部说明），过程看不到实时；每条后台消息都开一张看板卡、扣任务配额。
  - 和用户已拍板的方向（「聊天里的电脑工具改为在服务器执行」）不一致。
- **工作量**：小，1～2 期。

### 推荐

**选 A**，和用户 2026-11-19 拍板的方向一致，也是唯一能让「所有入口都关掉照跑」成立、并让评测量到真实路径的方案。B 的重复执行风险和双路径维护成本不值得；C 可以作为 A 落地前的过渡，但不建议单独做（§8 问题 1）。

A 用部署开关分期上线：先默认关，冒烟和对标评测通过后改为默认开，保留一个版本的回退开关，然后删掉浏览器端的旧处理函数。

## 4. 对现有能力的影响（按方案 A）

| 能力 | 变化 | 底线 |
|---|---|---|
| **审批** | 改为和群聊一样：每个电脑动作在网关里过审批门；要问人时这一轮停在「等你批准」，对话里出审批卡，**你批准后服务器执行这一步并接着跑完**（续跑机制现成）。浏览器路径里「读页直接发、被拦再补审批」的省开销做法取消，开销在服务器内部，不涉及模型。 | 不降。员工权限开关（SEC1 D4）照旧：关掉的工具不提供给模型，被调用也被拒。审批通过前不执行。 |
| **人工接管 / 输密码 / 登录** | 服务器在这一步里等：轮询电脑的控制状态（和浏览器现在的做法一样），最多等 10 分钟，交还或填完后接着跑。超过 10 分钟转为持久等待：这一轮以「需要你」结束并通知你，**你交还后服务器自动续跑**（新增，仿 `passwords/resume.ts`）。不再依赖本机 `localStorage`，换手机、换电脑都能接上。 | 不降。员工永远看不到密码；接管期间员工的动作照旧被拒。 |
| **实时画面** | 画面推流本来就按员工的电脑走，不变。自动弹出改为看流里的工具事件触发（看到 `computer_*` 开始就弹）。不在页面时不推流、不耗流量。 | — |
| **对话里的截图和命令块** | 截图改在网关导航时保存，单聊、群聊、看板的截图卡片都能显示。命令块、文件卡片按工具结果渲染，不变。 | 截图仍按「人 + 员工」归档，一个月后清理。 |
| **桌面设备模式**（`TENANT_RUNTIME=device`） | 电脑工具本来就经服务器转到你配对的电脑，执行方换成服务器不影响。关掉网页或桌面版窗口没关系，但**配对电脑要保持在线**：笔记本合盖、睡眠后，员工的电脑动作会等电脑上线或报告离线（现有行为）。本地应用和桌面控制仍只给员工主人自己的对话。 | 不降。 |
| **时限与预算** | 单聊轮新增墙钟（建议 25 分钟，和期五后台轮一致，待拍板），步数按**整轮累计**、不因每段重置；「已用完 N 步 · 继续」和触顶自动续一轮的语义不变。服务器段数上限沿用期五的 80。 | 月度对话配额照旧计一次；不开看板卡、不扣任务配额。 |
| **费用** | 模型和 token 与现在相同。区别只在于你不在时员工也在花钱，所以墙钟和段数上限是费用兜底；你随时可以在网页、桌面版停止。 | — |
| **停止** | 停止按钮直接中止服务器上正在执行的电脑动作（中止信号一路传到网关）。 | — |
| **同一员工同时跑多轮** | 同一员工共用一台电脑，两段对话同时在后台点网页会互相干扰。建议：同一员工同一时刻只跑一个用电脑的后台轮，第二个排队，对话里写明「排在 X 后面」。（我的建议，不同意可改。） | — |
| **跑的时候发新消息** | 和现在一样排到这一轮结束；想打断就先停止。 | — |
| **旧版桌面客户端** | 服务器只在新前端声明「电脑工具交给服务器」时才接管；旧客户端不声明，照旧由浏览器执行，不会重复。 | — |

## 5. 分期计划

每期单独可验收；服务器期测试全绿即推，**界面期（九·四、九·五）先截图给用户确认再推**。全部期次都在部署开关 `CHAT_SERVER_COMPUTER_TOOLS` 后面（默认关），直到九·六改为默认开。

### 期九·一 服务器执行单聊的电脑工具（服务器，约 1 个 PR）
- 单聊运行挂上 `HeadlessToolsMiddleware`，工具清单和群聊用同一个 `toolsForTurn`（含员工权限关掉的工具、本地应用、登录请求）。
- 前端在运行参数里带一个声明（如 `forwardedProps.openbotComputerTools = "server"`），服务器只接管带声明的运行；不带的照旧交给浏览器，保证新旧前端不会重复执行。
- 截图保存从 `/navigate` 接口挪进网关导航，两条路径都存。
- 单聊轮的整轮预算：步数累计、墙钟（按 §8 问题 2 的结论）、段数 80。
- 停止能中止正在执行的电脑动作。
- 验收：服务器测试，加一个集成用例：无浏览器的 HTTP 客户端发起单聊轮，看到第一个工具调用后断开，这一轮照常跑完、全部工具结果落库、线程里没有「没有执行」。

### 期九·二 长跑耐久（服务器，约 1 个 PR）
- 运行事件边跑边落库（每若干事件或每几秒刷一次），不再只在结束时写。
- 进程重启时在跑的轮：标为「被中断」，对话里写一句说明，附「继续」，**不自动重放**。理由和派活一致：可能已经花了钱、动过电脑，重放会重复执行写操作。

### 期九·三 接管和输密码在后台等、交还后续跑（服务器，约 1 个 PR）

## 6. 验收标准

**能力冒烟（`EVAL_SUITE=smoke`）新增两个场景，走单聊接口，不走看板派活**：
1. `disconnect`「中途断开网页仍完成」：HTTP 客户端发起单聊轮，交代一个要调 8 次以上电脑工具、跑 3～5 分钟的任务（例如在 `smoke/disconnect/` 下逐个生成 5 个文件，再跑给定的校验脚本，退出码 0 才算）。收到第一个工具调用后客户端主动断开，之后只轮询线程和产物。判分：产物齐全且正确；落库的线程有完整的工具调用和结果；没有「没有执行」的结果；这一轮以完成结束；九·五之后还要求记录了一条完成通知。
2. `reconnect`「断开后重连续上流」：同一任务，断开 30 秒后重新连接，能收到后续事件直到运行结束，且和落库的事件一致。

**对标评测**：`run-xiongbao.ts` 加一个执行路径选项（如 `EVAL_PATH=chat`），五道题走单聊接口再跑一遍。要求完成率不低于看板路径那一遍，墙钟、步数、token 同量级。两遍结果并排写进 `docs/acceptance/`。

**底线回归**：
- 现有审批、权限、SEC1、只读目录、设备模式的测试全绿。
- 新增：服务器执行时，写操作出审批卡，批准后服务器执行并续跑，拒绝后员工收到拒绝；关掉的工具不提供给模型；接管期间员工动作被拒。
- 新旧前端各跑一次，同一个工具调用只执行一次。

**真机手动验收**（界面期截图给用户）：网页发一个约 15 分钟的任务 → 关掉标签页 → 手机锁屏 → 收到推送 → 打开对话，能看到每一步（命令输出、页面截图、计划清单）。

全部 CI 绿，main 上已有的断言不改（要改先报用户）。

## 7. 风险

1. **过渡期重复执行**：开关切换期间，浏览器和服务器可能执行同一个调用。对策：以运行参数里的声明为准，服务器只接管带声明的运行；带声明时前端不注册处理函数；新旧前端组合都有测试。
2. **跑到一半进程重启**：现在只在一轮结束时落库。对策：九·二边跑边落库，中断明确告知，不自动重放。
3. **你不在时持续花钱**：对策：墙钟 + 段数 + 月度配额三层兜底；通知里写明用时；随时可停。
4. **配对电脑离线**（设备模式）：后台跑依赖你的电脑开着、联网。对策：离线时员工明确报告、通知里写明，不静默卡住。
5. **多副本部署的实时续流**：九·二写明限制，单副本不受影响。

## 8. 待用户拍板

1. **方案**：按推荐选 A（单聊也改由服务器执行，前端只渲染），还是先做 C（加一个「后台运行」入口）当过渡？我的建议是直接做 A，不做 C。
2. **单聊后台轮的时限**：墙钟 25 分钟（和期五的看板 / 例程一致）还是更长（例如 60 分钟）？到点后是「自动续一轮再停」，还是「直接停下并通知、你点继续」？我的建议：25 分钟，到点停下并通知，你点「继续」再跑一轮。
3. **跑完通知发到哪**：手机 App 推送、已绑定的微信等 IM、网页 / 桌面版系统通知，默认开哪些？只在你不在页面前时通知，还是每次都通知？我的建议：三个都开，只在你不在页面前时通知。
4. **人工接管 / 输密码在后台最多等多久**：我的建议是服务器在这一步里等 10 分钟（和现在网页里输密码的等待时间一样），超时就以「需要你」结束并通知你，你交还后服务器自动续跑。是否同意？
