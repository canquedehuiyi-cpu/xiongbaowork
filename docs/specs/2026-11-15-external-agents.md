# 招入外部智能体当员工（三端联动第 1 步）

日期：2026-11-15 · 状态：待用户确认
设计稿：https://claude.ai/artifact/1oaAV9rkPVwBdnUNYCUbzu （六屏：发现、招聘设置、对话与请求许可、手机在聊天软件里批、手机网页审批、电脑离线；用户确认「可以，写成正式设计文档」）
前置：聊天工作台（PR #610 / #614 / #616）已合入 main；本设计在它的通讯录、对话、名片、状态点上加东西。

## 为什么做

目标客群是 Codex、Claude Code、Hermes、Grok 这类智能体的用户。他们已经有一个很强的智能体，再给一个「也能聊天、也能干活」的智能体打动不了他们。熊宝和它们不一样的地方是**管一个团队**：员工有部门、状态、看板、汇报、审批底线，能在用户自己的电脑上真干活。

所以不跟它们抢，而是**把它们招进来当员工**：它们照样用自己的本事和用户自己的订阅干活，熊宝给它们排班、拉进群组、上任务看板、守审批底线、把需要拍板的事推到手机上。对外一句话：「你的 Codex 缺一个经理」。

## 用户说过的

- 「先做招入外部智能体和日报价值账」（同意先做外部智能体）
- 「要做最好的智能体肯定是 A B 都要有，日后更多的使用场景的竞争应该在手机端……我们需要本地电脑、云端、手机三端联动」
- 「两个都要，手机先做指挥审批，再做操作手机应用」
- 「选 A，国内海外都要照顾」（手机的通知和审批先走用户已经装了的聊天软件）
- 「国内的用户接入：飞书、钉钉、企业微信、微信机器人、QQ 机器人」
- 「选做法一，出设计稿」（桌面端统一用开放协议接）
- 「可以，写成正式设计文档」
- 团队版里外部员工归谁：「选 A」——只归招它的人。
- 长期规矩：改完的东西先给截图，没问题再推。

## 三端联动的拆分（本文只做第 1 步）

| 步 | 内容 | 本文 |
|---|---|---|
| 1 | 外部智能体招进来，在用户电脑上干活；它的「请求许可」进熊宝「等你确认」 | ✅ |
| 1b | 聊天软件通道：海外 Telegram；国内飞书、企业微信先，钉钉、QQ 后，微信 ClawBot 放量后接。每个通道能对话派活、收汇报、点按钮批准 | 另写规格 |
| 2 | 同一批员工也能在云端干活，电脑离线时可转云端 | 另写规格 |
| 3 | 员工操作手机里的应用（安卓原生 App + 国内厂商推送） | 另写规格 |
| 4 | 设置、技能、插件、模型等页面整理 | 另写规格 |

本步做完后，手机上的审批靠现有通道就能用：熊宝手机网页（工作台第五期已有手机布局）、已有的 Slack / Teams 卡片、短信通道。设计稿第 4 屏（飞书里批）属于 1b，本步只保证「等你确认」里的每一条都带足让任何通道画成卡片的信息。

## 目标

1. **从电脑招。** 通讯录「招一位新同事」新增页签「从我的电脑招」：选一台已配对、在线的电脑，熊宝在上面找出装好的 Codex、Claude Code、Hermes，标明「已安装 / 已登录 / 模型待确认」，点「招进来」。没装的列出名字和安装说明；另有「其他支持开放协议的智能体 · 手动添加」（填启动命令）。
2. **招聘设置。** 名字、部门、工作文件夹（它只在这里面干活）、「哪些事要先问你」五项（见「许可规则」），三条底线固定显示不可关。
3. **外部员工就是员工。** 出现在通讯录、组织架构、消息列表、名片；带「外部员工 · Codex」标记；能单聊、能拉进群组、能被 @；每一轮工作照常开任务看板卡片、交付时关卡。
4. **实时过程。** 对话里看得到它一步步做了什么：读了哪些文件、找到什么原因、改了哪些文件（+行数，可展开看改动）、跑了什么命令、测试结果。
5. **请求许可进「等你确认」。** 它执行需要许可的操作前，熊宝按许可规则自动放行、自动拒绝，或者生成一条「等你确认」：在对话里、审批收件箱、手机网页、已接的聊天通道都能批，任何一处批了就算数。三个选项：批准（只这一次）、拒绝、这次对话里都允许。
6. **离线排队。** 电脑离线时，派给它的活排队；名片、消息列表、对话顶栏写明「离线 · N 件排队中」；电脑回来后按顺序继续。用户可以取消排队的活。
7. **看它的屏幕。** 对话顶栏「看它的屏幕」打开该电脑现有的实时画面与接管。

## 不做

- 不在云端跑外部智能体（第 2 步）。
- 不接飞书、钉钉、企业微信、微信、QQ、Telegram（1b）。
- 不把外部智能体的内部工具一一镜像成熊宝工具；熊宝只管它请求许可的那些动作。
- 不做日报（另一个「员工主动汇报」项目）；招聘设置里「每晚发日报」那一项等日报上线再显示。
- 外部员工这一步只接「有人发起」的活：单聊、群里 @、别人把活转给它。例行任务、职责、主动工作、定时触发先不给它（界面上这些入口对外部员工不显示），下一步再开（我的决定：这些活没有人在场批准，等手机通道铺好再开更稳）。
- 不改外部智能体的模型和订阅：它用自己配置的。

## 反目标（做到了也算失败）

- 外部员工能绕过三条底线：付款和下单、删除整个文件夹、对外发消息或邮件。
- 用户的 Codex / Claude / Hermes 登录凭据离开用户的电脑。
- 用户看到的是「熊宝的员工在调用 Codex」，而不是「Codex 就是我的员工」。
- 外部智能体被启动在「全自动不问人」的模式下，导致熊宝看不到也拦不住它的动作。

## 约束

- 多租户：外部员工和普通员工一样受租户隔离；设备只接受本租户、本人员工的工作（现有设备通道已按租户和设备认证）。
- 审批只有一个入口：所有「等你确认」都走现有审批服务（`approvals/`），通道只是投递和回传决定。
- 设备端现状：runner 只有一次性命令（120 秒默认、600 秒上限）和 MCP 工具桥，没有长对话通道；设备 → 服务器的持续帧只有实时画面在用（`devices/screen.ts`）。本步新增一条「智能体会话」帧通道。
- 协议：Agent Client Protocol（ACP），JSON-RPC over stdio。Codex 用 `codex-acp` 适配器，Claude Code 用 `claude-agent-acp` 适配器，Hermes 用自带的 `hermes acp`。适配器版本固定在设备端的清单里，升级走设备端发版。
- 文案：中文，界面统一用「员工」「群组」「等你确认」。

## 做法（用户已选做法一）

1. **桌面端统一用开放协议接（选定）。** runner 里做一个 ACP 客户端，一套接口接住所有支持 ACP 的智能体；许可请求映射到熊宝审批。代价是要新开设备上的长会话通道。
2. 每个智能体单独深度接入（Codex app-server、Claude Agent SDK、Hermes API）。每家都细，但工作量与维护成倍，新智能体要再接一次。未选。
3. 把它们当熊宝员工手里的 MCP 工具。最便宜，但用户看到的是「熊宝员工在用 Codex」，没有实时过程，内部危险操作拦不到，违背反目标第 3 条。未选，可作补充。

第 2 步上云时，同一批适配器放进云端容器里跑，服务器这一侧不变。

## 设计

### 1. 员工的新运行方式

`agents.type` 新增枚举值 `device_acp`（界面叫「外部员工」）。`configuration` 存：

- `deviceId`：在哪台电脑上干活。
- `harness`：`codex` | `claude-code` | `hermes` | `custom`。
- `appRef`：`custom` 时，指向用户在**桌面端**登记的一个本机智能体（启动命令只存在设备上，服务器只拿到引用和显示名，和现有本机应用桥一致）。其余三家的启动方式由设备端清单决定。服务器从不下发命令文本。
- `workdirRef`：工作文件夹，取设备心跳里上报的文件夹之一（现有 `roots`，服务器只存引用，不存路径）。招聘页「选择…」列出这台电脑已共享的文件夹；要用新文件夹，提示用户在桌面端添加（我的决定：沿用「路径不离开电脑」的现有安全模型）。路径是否在工作文件夹内由**设备端**判断，随许可请求一起报上来。
- `permissions`：五项许可规则的选择（见第 4 节）。

**归属（用户选 A）。** 外部员工只归招它的人（`ownerUserId` = 招聘人）：只有他能单聊、派活、改配置、批它的许可。它的可见性固定为私有，不能公开到团队人才市场。招聘人可以把它拉进群组，群里其他人 @ 它也能让它干活，但它的许可请求只推给招聘人批，群里其他人看到的是「等 <招聘人> 确认」。个人版只有一个人，不受影响。

只能在**自己配对的电脑**上招：`registered_devices` 新增 `pairedByUserId`（配对时写入）。老设备没有这一列的值：个人版回填为唯一的用户；团队版留空，界面提示「这台电脑还没认主人，在桌面端重新登录一次即可认领」（我的决定）。

一个外部员工在一台电脑上只有一份配置；换电脑在名片「配置」里改。占用套餐的员工名额，和召唤员工一样计数。不收模型费：这些员工的 token 不走熊宝计量。

### 2. 发现

runner 新增动作 `agents.discover`（非持久、只读）：

- 在 PATH 和常见安装位置找 `codex`、`claude`、`hermes`，读版本号。
- 判断能不能用 ACP：Codex、Claude Code 看对应适配器是否在设备端清单里可启动；Hermes 看 `hermes acp` 是否可用。
- 尽力判断是否已登录（读各自的登录状态命令或配置文件是否存在，**只回传是或否，不回传任何内容**）。读不出来就写「登录状态未知」，不写「未登录」。
- 回传：名字、版本、`installed`、`acpReady`、`signedIn: true | false | null`。

界面上「已安装 / 已登录 / 模型待确认 / 登录状态未知」标签都由这几个字段算出来。

### 3. 会话通道（设备 ↔ 服务器）

在现有 runner WebSocket 上加一类帧，和实时画面一样按「本连接认证的租户 + 设备」归属，帧里任何字段都不能改变归属。

服务器 → 设备：

- `acp.open { agentId, threadId, harness, workdir }`：启动（或复用）该员工在该电脑上的适配器进程，建立 ACP 会话（`session/new`，cwd = workdir）。一个员工一个进程，每个熊宝对话线程一个 ACP 会话。空闲 10 分钟关进程，和 MCP 桥一致。
- `acp.prompt { threadId, turnId, content }`：发一轮。离线时排队，回来后按顺序发，同一 `turnId` 只执行一次（排队规则见下）。
- `acp.cancel { threadId, turnId }`：映射 `session/cancel`。
- `acp.permission.answer { requestId, outcome }`：回答一个许可请求。

设备 → 服务器：

- `acp.update { threadId, turnId, seq, update }`：原样转上来的 `session/update`（文字片段、计划、工具调用、工具调用进展、改动）。`seq` 递增，服务器按序消费、丢重复。
- `acp.permission.request { threadId, turnId, requestId, toolCall, options }`：转上来的 `session/request_permission`。
- `acp.turn.end { threadId, turnId, stopReason }`。

**排队与掉线**（我的决定）：

- 不复用现有电脑动作队列（它一台设备一次一件、2 分钟租约、超时就暂停整台设备）。外部员工的轮次另开一条队列：**按对话线程排序**，不同线程、不同员工可以在同一台电脑上并行；轮次等许可时不占别人的位置，也不会让设备进入暂停。
- 一件排队的活在设备回执「收到并开始」时出队，之后按「轮次」跟踪，直到 `acp.turn.end`。
- 只是网络断开、runner 还在：适配器和这一轮在电脑上继续跑；`acp.update` 在 runner 里按 `seq` 缓存（上限 1000 条或 5 MB，超过只保留最新的计划和最后状态），重连后补发；挂着的许可请求重连后重新报上来。服务器这边的「等你确认」在断开期间标「电脑离线，回来后可批」，不作废。
- runner 退出、电脑关机或睡眠导致适配器进程没了：这一轮记为「中断」，对话里出一张卡：「电脑关机，这件活中断了，重新派？」点了用新的 `turnId` 重新发同样的话；挂着的许可作废。
- 用户可以取消排队中或进行中的轮次（进行中映射 `session/cancel`）。

**对话上下文**（我的决定）：适配器支持 `session/load` 时，新进程用它接回原会话；不支持时，新会话的第一轮带上熊宝这边的上下文：人设、本线程最近 20 条消息、当前任务卡。群组里每一轮都带上「它上次说话之后别人说了什么」和群组成员名单。「这次对话里都允许」记在熊宝的本线程规则里，接回或新开会话后由熊宝继续按它自动放行，不依赖智能体记得。

服务器把 `acp.update` 翻译成对话线程现有的事件流（文字消息、工具调用卡、进度卡），所以消息列表、对话、正在输入、任务看板开关卡、交付物这些都沿用现有逻辑，不为外部员工另写一套。改动（`edit` 类工具调用里的 diff）汇总成交付物里的「改了哪些文件（+/−）」。

### 4. 许可规则与底线

**启动模式。** 适配器一律以「每个非只读动作都请求许可」的模式启动（Codex 的按需审批、Claude Code 的默认权限模式、Hermes 的对应设置）。放不放行由熊宝按规则决定，不交给智能体自己的「全自动」开关。设备端清单里写死每家的启动参数，`custom` 智能体如果从不请求许可，名片上标「这个智能体不会请求许可，熊宝拦不住它的动作」，招聘时要用户再确认一次。

**五项规则**（招聘设置第二栏，名片「配置」里可改）：

| 项 | 怎么认出来（ACP 工具调用的 `kind` 和内容） | 默认 |
|---|---|---|
| 改工作文件夹里的文件 | `edit` / `move`，路径在 workdir 内 | 直接做 |
| 动工作文件夹以外的文件 | `read` / `edit` / `move` / `delete`，路径在 workdir 外 | 先问我 |
| 运行命令 | `execute` | 危险的才问我 |
| 联网下载、装依赖 | `fetch`，或 `execute` 命中包管理器安装命令 | 先问我 |
| 提交并推送代码 | `execute` 命中 `git push` 等推送命令 | 先问我 |

选项：直接做 / 先问我（「运行命令」多一个「危险的才问我」，危险判定复用现有 `agent_security_settings` 的危险命令和敏感路径表）。一个请求命中多项时取最严的那项。

**和现有审批层的关系**（我的决定：外部员工的许可请求作为一种新的动作来源，走同一个策略引擎，不另起一套）。从严到宽依次是：

1. **现有全部底线照样适用**，包括部署级底线：任何删除都问、只给「批准这一次」（#398）；付款、结账、确认收货；对外发送；凭据、安全设置、分享与发布。所以招聘设置里的底线文案改为「付款和下单 · 删除文件 · 对外发消息或邮件」，比设计稿上的「删除整个文件夹」更严，和现有员工一致。
2. 管理员的动作策略（`actionKinds`）、员工级工具权限（SEC1）、用户自定义规则里的「拒绝」：命中就**自动拒绝**，这就是目标 5 里「自动拒绝」的来源。拒绝时对话里写明被哪条规则拒绝。
3. 用户自定义规则里的「先问 / 交给本人」：照样生效。
4. 本员工的五项规则。
5. 用户关掉了审批（审批开关）时，第 4 层的「先问我」视为「直接做」，但第 1、2 层不受影响。

底线和第 2 层都不提供「这次对话里都允许」。

**决定怎么回给智能体。** 熊宝的三个选项映射到 ACP 请求里提供的 `options`：批准 → `allow_once`；这次对话里都允许 → `allow_always`（只在本 ACP 会话内有效，熊宝自己也记一条本线程内的放行规则）；拒绝 → `reject_once`。智能体没提供对应选项时，按最接近的保守选项回。

**等待。** 「等你确认」没人回时一直等，ACP 请求挂着；这轮工作在看板上是「需要操作」，也不占别的轮次的位置。掉线和关机时怎么处理见第 3 节「排队与掉线」。

**每条「等你确认」带的信息**（给通道画卡片用）：员工、在哪台电脑、动作一句话、命令或路径原文、命中了哪条规则或底线、这轮已经做了什么的摘要、改动文件列表。

### 5. 界面

按设计稿六屏实现，沿用工作台的 `--wb-*` 令牌和组件：

- 通讯录「招一位新同事」：页签「人才市场 / 从我的电脑招 / 云端（下一步）」；「云端」页签这一步只显示说明，不能点招。
- 招聘设置页：基本信息、哪些事要先问你、底线、汇报（日报项暂不显示，见「不做」）。
- 员工卡、名片、对话顶栏：「外部员工 · Codex」标记；顶栏副标题「状态 · 此刻 · 在 <电脑名> 上」；按钮「看它的屏幕」「名片」。
- 状态点新增「离线」（灰），文字「离线 · N 件排队中」；电脑在线后回到忙碌 / 空闲。
- 对话：进度卡（步骤列表，完成打勾，进行中圆点）、改动卡（文件 + 行数，展开看改动）、请求许可卡（命令原文、说明、三个按钮、「已同时推到你的手机」一行）。
- 手机网页审批页：设计稿第 5 屏，按钮大、底部固定。
- 消息列表顶部离线提示条：设计稿第 6 屏。

### 6. 群组

外部员工可以被拉进群组、被 @。群里轮到它时，和单聊一样走会话通道，用同一个 ACP 会话（按群组线程开）。它在群里请求许可时，许可卡发在群里，但只有招聘人能批；其他成员看到「等 <招聘人> 确认」，批准按钮不出现。只有招聘人能把它拉进群组或移出群组。

## 测试与验收

- 服务器：`device_acp` 员工的增删改、租户隔离（另一个租户的设备帧不能写进本租户线程）、`acp.update` 乱序和重复、许可规则的每一项和三条底线（含「命中多项取最严」「底线不给这次都允许」）、掉线时许可失效、排队与恢复。
- runner：用一个假的 ACP 智能体（测试里写的小脚本，按剧本发更新和许可请求）跑通打开、一轮、取消、许可往返、进程空闲回收；发现动作在装与没装、登录状态未知时的输出。
- 前端：招聘流程、外部员工标记、离线状态、请求许可卡三个按钮、手机网页审批页。
- 真机验收：在一台 Windows 和一台 macOS 上，分别招 Codex 和 Claude Code，各完成一个「改代码 → 跑测试 → 请求推送 → 手机网页批准 → 推送成功」的来回；电脑断网再恢复，排队的活继续。截图给用户确认后再推。
