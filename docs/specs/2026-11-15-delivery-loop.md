## 为什么做

一个人带一群 AI 员工干活，最常见的失败是活派出去了没人收、没人验：员工说「做完了」就当交付了，后台的活做完了没人看，逾期了也没人知道。开源技能包 solo-to-team-skills 把「已接下 → 已收到成果 → 已验收」、到点核对、开工收工清点、证据先于完成这些做法写成了规矩，方向对，但它全靠模型自觉，没有定时、没有看板、没有通知，会话一长就丢。用户要「采用优势，补齐劣势，融入我们的项目中」。熊宝有看板、服务器定时、审批、推送，能把这些规矩做成产品机制，不靠模型记得。

## 目标

1. **三步收货**：每件活走「派出 → 已接下（预计几点交、验收标准）→ 已交成果（交付物 + 自查）→ 你验收」。只有你验收或你取消才算结束；你可以退回并写原因，活回到员工手里。
2. **证据门**：没有交付物，卡进不了「已交成果」，由服务器判断，不靠模型自觉。被挡回只在对话和流水里留一行，员工自己补齐，不打扰你。
3. **只追加的流水**：每件活记下谁在什么时候做了什么，只追加不改写。
4. **服务器到期核对**：过了预计时间先催员工，再不交就记逾期并通知你；你可以再催、准许延期、换员工接手或取消。
5. **开工 / 收工清点**：按你的作息每天推两条：还有几件没收、最早几点到期、几件等你验收、有没有逾期。没有在跟的活就不发。
6. **外部员工同一套规矩**：派给 Codex、Claude Code、Hermes 的活，第一句话自动带上交付规约；它不按格式回也照样走三步。
7. **界面**：看板四列、任务卡详情、对话里的接活回执 / 延期申请 / 交付卡 / 退回、手机清点页与逾期页、侧栏「目标」块四段进度。

## 不做

- 不让员工自己判断「算不算交付」：交付物在不在由服务器看。
- 不对交付物内容做自动判对错（那是你验收的事）；服务器只核对交付物存在、和验收标准里写明的必需项对得上。
- 不给普通问答走三步：问一句答一句的对话照旧。
- 例行、职责、主动调研、自动化、员工之间互相 @ 的转交、群组流水线，不自动进三步（员工在其中自己调 `accept_task` 才进）。
- 这一期不做 IM 推送本身（飞书、钉钉、企业微信、微信机器人、QQ、Telegram 由 IM 项目做）；逾期和清点先走工作台、手机推送和已绑定的 Slack / Teams / 短信，IM 项目上线时作为同一份内容的另一个出口。
- 不做跨租户可见：群里谁派的活，谁验收。

## 反目标

- 员工没交东西，看板却显示「已交成果」。
- 没人核对过的时段，流水里写成「一直在盯」（不谎报覆盖）。
- 逾期催办变成骚扰：同一件活一天内通知你超过 3 次，或在你的作息时间外推送（作息外的提醒并进下一次开工清点）。
- 普通聊天被三步流程拖慢、塞满看板。
- 交付后再改写原来的预计时间或验收标准，让逾期记录消失。
- 一件活被拆成一串卡：催一次、退回一次、你追问一句，就冒出一张新卡。

## 约束

- 多租户：所有新表带 `tenant_id`，所有读写在租户帧里；核对器按卡片所在租户执行（与现有后台任务一致）。卡片的租户是派活的人（现状：`tasks/routes.ts:514-519`、`channels/group.ts:1246`）。
- 看板的投影原则改一处：过去「执行路径从不读 `tasks`」（`db/schema/tasks.ts:40-46`、`tasks/projector.ts:30-33`）；本项目起，三步收货的三个工具、核对器、退回 / 换人接手会读写**在跟的卡**（`tracked = true`）。不在跟的卡仍只由投影器写、执行路径不读。这条约定的注释同步改写。所有对在跟卡的写入集中在一个新模块（`tasks/delivery.ts`）。
- 中文文案；界面沿用 `--wb-*` 令牌，只作用于默认皮肤。
- 通知频率上限、作息时间都在服务器判断，不在前端。
- 迁移放在 `server/recovery/recovery-20261018-v1/sql/`，接现有编号；只追加的表必须显式 `REVOKE UPDATE, DELETE, TRUNCATE`（`0054_app_role.sql` 的默认权限会自动授予，先例 `0134_waker_flow_versions.sql:57-59`）。

## 设计

### 1. 哪些算一件活

一件活从这三个入口之一开始跟（`tracked = true`）：
- **员工接下**：员工判断这是一件有交付物的活时调用 `accept_task`（第 3 节）。在任何来源的轮次里都可以（单聊、群聊、例行、职责、转交），调了就进三步。
- **你手动跟**：在卡片或对话里点「当作一件活来跟」。卡进「派出 · 待接下」，员工下一轮被要求补接活回执。员工的 `accept_task` 工具被关掉时，这个按钮不显示。
- **外部员工排队的活**：外部员工的活在排队时就进「派出 · 待接下」（第 9 节）。

其余一律不自动跟：普通问答、闲聊照现在的逻辑走（`awaiting_review` → 查收结果 / 已完成），不显示三步，不进清点。

### 2. 一件活一张卡（跨多轮）

现状是一轮一张卡（`threads/postgres-runner.ts:509`「one task per turn」，群聊 `channels/group.ts:1238-1252`，唤醒另开卡 `agents/wake-up.ts:569`）。本项目对在跟的活改为**一件活一张卡**：

- 某个线程里、某位员工有一张未结束的在跟卡时，这个线程里这位员工的后续轮次——你追问、被催醒、退回后接着干、核对器的催办——都挂到这张卡上，不另开卡（复用 `runnerCardSuppressed`，`postgres-runner.ts:400`）。这些轮次在流水里各记一行「进度」，不另扣月度任务配额（卡已经扣过一次）。
- 员工在同一线程里又接下另一件活（再次调用 `accept_task`），开一张新的在跟卡；之后的轮次挂到最新接下的那张。
- 换员工接手时，卡跟着换到新员工的线程（第 7 节）。
- 群里一件活挂在「这位员工 × 派活的人」那条群线程上（`group_bot_threads`），群频道的其他消息不挂进来。

### 3. 卡片状态

现有 `task_status`：`running`、`needs_action`、`awaiting_review`、`done`、`failed`。新增一个值 `cancelled`，并在 `tasks` 加列（不改原有值的含义）：

| 列 | 含义 |
|---|---|
| `tracked boolean default false` | 是否走三步收货 |
| `thread_ref text` | 在跟卡挂的线程（群聊时是那条群线程，不是频道 id） |
| `accepted_at timestamptz` | 员工接下的时间 |
| `due_at timestamptz` | 当前生效的预计交付时间（你改或准许延期后才变；换员工接手时清空，等新员工自己报） |
| `original_due_at timestamptz` | 员工第一次报的预计时间，永不改写 |
| `due_reported boolean` | 员工是否报了预计时间（没报按 2 小时核对） |
| `criteria text` | 验收标准 |
| `overdue_at timestamptz` | 首次记为逾期的时间（交付后也保留；换员工接手时清空，流水里的逾期记录保留） |
| `last_error text` | 上一轮出错的一句话（下一轮成功后清空） |
| `nudges integer default 0` | 催过几次 |
| `returns integer default 0` | 退回过几次 |

看板四列（设计稿 1）由状态和列推出：
- **派出 · 待接下**：在跟、`accepted_at is null`、未结束（`needs_action` 时卡上加「等你操作」）。
- **已接下 · 在做**：在跟、已接下、状态 `running` 或 `needs_action`。上一轮出错时卡上显示红字「上一轮出错：…」。
- **已交成果 · 等你验收**：`awaiting_review`。
- **已验收**：`done`；`cancelled` 在这一列下方折叠显示。
- 不在跟的卡照现在的列显示（进行中 / 查收结果 / 已完成 / 失败）。

**一轮失败不结束一件活（我的决定）**：在跟卡上的一轮出错，卡留在「已接下 · 在做」，记 `last_error` 和流水「这一轮出错了」，核对器照常催（相当于重试）；只有你取消或验收才结束。`failed` 只用于不在跟的卡。

**不被其他路径绕过**：
- 重启回收（`tasks/projector.ts:562-590`、`tasks/reclaim.ts:57-71`）和流水线回收（`pipeline/reap.ts:109-118`）跳过在跟卡。
- 在跟卡上的「归档」（`tasks/routes.ts:525-539`）等于「验收」，记一条流水「验收（从归档）」；不在跟的卡归档照旧。
- `finished()`（`projector.ts:431-444`）遇到在跟卡：不改状态（出错时只记 `last_error`），不覆盖 `deliverableRef`，只记流水「本轮结束」。

### 4. 员工的三个新工具

内置员工默认都有，工具权限里可关（关了等于这位员工不走三步）。工具按「人 × 员工」构造（`index.ts:2602-2622`），运行时用 `currentModelRun()`（`models/token-metering.ts:59`）拿当前 `runId`、`threadId`，找到或新建本线程这位员工的在跟卡。

- `accept_task {title?, due_at?, criteria}`：接活回执。`due_at` 可写相对时间（「40 分钟」「下午三点」，按你的时区换算）；不填则 `due_reported = false`，按 2 小时核对。`criteria` 是员工根据你的话整理的验收标准，一两句，可在末尾用「必需：A、B、C」列出必需项。写流水「接下」，对话里出现接活回执卡（设计稿 3），你可以改预计时间和验收标准——你改的直接生效，`original_due_at` 仍记员工报的。
- `deliver_task {items: [{kind, ref, title}], checks: string[]}`：交付。`kind` 为 `attachment`（本线程附件 id）、`component`（本卡各轮里画过的组件，按组件名 + 工具调用 id）、`link`（http(s) 地址）、`diff`（外部员工改动汇总，见第 9 节）、`note`（只有文字结论）。服务器跑证据门（第 5 节）：过了，卡进 `awaiting_review`，交付物合并进 `deliverableRef`，流水「交付」，对话里出现交付卡；没过，工具把挡回原因返回给员工，流水「被挡回」，对话里一行灰色系统消息，卡不动。
- `request_extension {due_at, reason}`：申请延期。对话里出现延期申请卡；你准许才改 `due_at`；不准许维持原样。

员工的人设提示里加一段固定说明（四条规约，同设计稿 6 的文字），告诉它什么时候用这三个工具；普通问答不要用。

**交付物格式**：扩展现有的 `DeliverableRef`（`projector.ts:131-164`），保持 `kind: "deliverable"`，在 `components`、`attachments` 之外加 `links`、`diffs`、`notes`、`checks`，看板交付物标签和侧栏「输出内容」不会坏，只是多认几类。

### 5. 证据门

`deliver_task` 被调用时，服务器按顺序检查，任一不过即挡回：
1. `items` 至少一项，且每项真实存在、属于本租户和本卡（附件在本卡挂的线程里；组件在本卡某一轮里画过；`link` 是合法 http(s) 地址；`diff` 来自本卡外部员工的轮次）。
2. 只有 `note` 时，`checks` 至少一条。
3. 验收标准里写了「必需：…」时，`items` 的标题或 `checks` 要逐一提到每个必需项；对不上就挡回并说缺哪项（设计稿 3「缺 C 家」）。没写必需项就跳过这一步。
4. 交付后不能再改预计时间和验收标准（`PATCH` 被拒）；退回后可以再改。

### 6. 验收、退回、取消与权限

- **验收**：沿用现有 `reviewed()`（`awaiting_review` → `done`），流水「验收」。
- **退回** `POST /api/tasks/:id/return {reason}`：`awaiting_review` → `running`，`returns + 1`，流水「退回：原因」；服务器以你的名义把原因发进本卡挂的线程并开一轮（参照 `channels/dispatch.ts` 的服务器侧发消息做法）；预计时间不变（已过期的照样算逾期）。
- **取消** `POST /api/tasks/:id/cancel`：任何未结束状态 → `cancelled`，流水「取消」；正在跑的轮次按现有停止逻辑停下；外部员工排队或进行中的轮次一并取消（外部员工规格第 3 节）。
- **权限**：验收、退回、取消、准许延期、改标准、换人、再催，只有卡片所在租户的人（派活的人）能做，沿用看板现有权限。群里也一样，群主不能代验收（我的决定：现在的租户模型下群主看不到别人的卡，跨租户可见这一期不做）。

### 7. 流水

新表 `task_events`（`tenant_id`、`task_id`、`kind`、`actor`（`user:<id>` / `agent:<id>` / `system`）、`detail jsonb`、`created_at`），只插入；迁移里对应用角色显式 `REVOKE UPDATE, DELETE, TRUNCATE`。`kind`：`dispatched`、`accepted`、`progress`、`extension_requested`、`extension_granted`、`extension_denied`、`bounced`、`delivered`、`run_ended`、`run_failed`、`nudged`、`nudge_skipped`、`overdue`、`notified`、`reviewed`、`returned`、`cancelled`、`reassigned`、`edited`。卡片详情（设计稿 2）按时间正序显示。「进度」取员工在本卡某一轮里的第一句回复（截 60 字，每轮一条）。

### 8. 交付核对器（服务器定时）

新后台循环（照 `agents/wake-up.ts` 的认领 + `repeatAfterEach` 模式，`index.ts:4100-4118`），每分钟扫一次所有租户里在跟且未结束的卡，按卡片租户帧执行，行锁认领防多副本重复：

- **待接下**：打开 5 分钟还没接下 → 催员工一次；再过 30 分钟还没接下 → 通知你「小财还没接下『核对发票』」。
- **已接下、到点未交**：`now > due_at + 5 分钟` 且未交付 → 催员工问进度；`now > due_at + 35 分钟` 仍未交 → 记 `overdue_at`（只记第一次）、流水 `overdue`、通知你（设计稿 5）。之后每 2 小时最多再提醒一次，同一件活一天最多通知你 3 次（按你的时区算「一天」）。
- **员工这一轮还在跑**：不催，流水不记，下一分钟再看（避免同一线程并发开轮）。
- **催员工和通知你用同一套规矩（用户 2026-11-15 决定）**：催办轮次只在你的作息内开，同一件活每天（按你的时区）最多催 3 次，你点的「再催」也算在这 3 次里（但不会被它拦下）；外部员工也一样，催办照留，不改成只通知你。
- **你的作息外**：不推送，也不催员工；提醒并进下一次开工清点，催办等作息内的第一次核对。开工清点带上攒下的提醒，就算那天通知过你一次（占当天 3 次中的 1 次，之后照样每 2 小时最多一次）；开工清点能发出的那一小时里，核对器不再单独推攒下的提醒，开工时刻同一件活只告诉你一次；清点没能带上的，过了这一小时由核对器照常推。
- **催办怎么做（我的决定）**：不复用员工自己的唤醒（它会按 `kind:"reply"` 推送你、另开卡、占员工每天 20 个 / 同时 5 个的唤醒额度、扣月度任务配额，`agents/wake-up.ts:43-45, 569, 595-602`）。核对器用一种新的「催办轮次」：在本卡挂的线程里以系统身份开一轮，挂在这张卡上，不另开卡、不推送、不占唤醒额度、不扣任务配额（模型用量照常计量）。催办消息写明是哪件活、到期多久、要它交已做完的部分或申请延期。
- **换员工接手** `POST /api/tasks/:id/reassign {agentId}`：原员工的轮次停下；卡的 `executor_agent_id` 换成新员工，`thread_ref` 换成新员工和你的线程，流水 `reassigned`；在新线程开一轮，交给它原卡的标题、验收标准、已有交付物和原员工最后的进度；新员工要重新 `accept_task`（卡回到「派出 · 待接下」，`original_due_at` 保留第一位员工报的）。新员工按自己的时间核对：预计时间回到「等新员工报」，原员工报的、你给原员工改的、准许原员工延到的都不再生效，新员工没报就按它接下后 2 小时核对；逾期标记、上次催办和上次提醒的时刻、作息外攒下的提醒、当天的催办次数一并清零（流水里的逾期记录保留，换人那一行写明清掉的预计时间和逾期时刻）；当天通知你的次数照算（同一件活一天最多 3 次，不因换人重来）。换人之后你再改的预计时间照样直接生效。

### 9. 外部员工

依赖外部员工第二期（ACP 运行时、`DeviceAcpAgent`）合入；这一块放在第二期服务器的最后一个任务，第二期合入前跳过。

- 外部员工的活在排队时就进「派出 · 待接下」；轮次开始即视为接下（`accepted_at` = 开始时间）。
- 第一轮开始时熊宝在提示前加上交付规约（四条，同设计稿 6 文字），每张卡只加一次。
- 外部员工调不了熊宝的工具，由服务器替它走三步：回复里第一次出现「预计 HH:MM」或「预计 N 分钟 / 小时」时取作 `due_at`（`due_reported = true`），否则按 2 小时核对；轮次结束时，有改动汇总（外部员工规格第 3 节「edit 类工具调用里的 diff 汇总成交付物」）或附件就当作交付物过证据门（自查取回复里「自查」「测试」开头的句子），没有就留在「已接下 · 在做」并在对话里提示「它没交东西」。
- 外部员工第三期界面上线前，交付卡里的改动只显示「改动 N 个文件 · +x −y」。

### 10. 开工 / 收工清点与通知

- **作息设置**放在「我」→ 通知：开工时间（默认 09:00）、收工时间（默认 18:00）、时区、周末是否发（默认不发）。存在 `users.preferences`（jsonb，`user-preferences.ts`），不需要迁移。时区在你第一次登录或打开设置时由浏览器写入，之后你可以改。
- **清点**：到点时，若你有在跟的卡（今天接下的或仍未结束的），生成一条：已验收数、等你验收（列出）、还在做（最早到期的排前）、逾期（时长与催办次数）。开工清点额外带上作息外攒下的提醒。没有在跟的卡不发。
- **送达**：
  - 工作台顶部一条（设计稿 1）；
  - 手机推送：现有推送只能挂在某个对话上、种类只有 `reply|question|approval|attention`（`delivery/types.ts:1-6, 52`）、点开只能跳对话 / 审批 / 需要处理（`delivery/push.ts:14-31`）。新增种类 `briefing` 和 `overdue`，用不绑定具体对话的范围（照 `attention` 把多员工的事折叠成一条的写法），点开跳到清点页或那张卡；
  - 已绑定的 Slack / Teams / 短信：逾期和清点走现有投递路由（同样遵守作息和每天 3 次）。
- **手机端（我的决定）**：清点页和逾期页做在网页端的工作台手机布局里（`/briefing`、卡片详情页），手机网页直接能打开；原生 App（`openbot/mobile`）的推送点开用 `xiongbao://` 深链跳到同一页面。原生 App 需要发新版才有这两种推送，发版由你推标签。

### 11. 接口

- `GET /api/tasks` 返回新增字段（`tracked`、`threadRef`、`acceptedAt`、`dueAt`、`originalDueAt`、`dueReported`、`criteria`、`overdueAt`、`lastError`、`nudges`、`returns`），新增筛选 `?overdue=1`。
- `GET /api/tasks/:id`（单张卡，给深链和手机详情页）、`GET /api/tasks/:id/events` → 流水。
- `POST /api/tasks/:id/return {reason}`、`POST /api/tasks/:id/cancel`、`POST /api/tasks/:id/extension {decision: "grant"|"deny", dueAt?}`、`PATCH /api/tasks/:id {dueAt?, criteria?}`、`POST /api/tasks/:id/track`、`POST /api/tasks/:id/reassign {agentId}`、`POST /api/tasks/:id/nudge`。
- `GET /api/me/briefing?kind=start|end` → 当前清点内容。

### 12. 和对话侧栏的关系

侧栏的 `SidebarGoal.status` 保持看板五种状态不动（侧栏代码按穷举写，`conversation-sidebar.ts:75-81`、`sidebar.ts:143`），加 `cancelled` 一个值，另加独立字段 `stage: "pending_accept" | "accepted" | "delivered" | "reviewed" | null`（不在跟为 null）、`dueAt`、`overdue`、`returns`。`goalOf` 优先取本线程未结束的在跟卡，没有才取最新一张卡；「上次检查」一行改为最近一条流水的一句话。侧栏服务器期若已合入，本项目第一期顺带改这几处；侧栏界面期在本项目之后的话，直接用四段进度条（设计稿 6）。

## 测试与验收

- 服务器：
  - 普通问答、例行、转交不调 `accept_task` 时不在跟，看板行为不变。
  - `accept_task` 后卡在「已接下」；同一线程后续三轮（追问、催办、退回）都挂在同一张卡上，看板只有一张卡，月度任务配额只扣一次。
  - 同一线程再次 `accept_task` 开第二张在跟卡，后续轮次挂到新卡。
  - 一轮结束不进查收结果；一轮出错卡仍在「已接下」并有 `last_error`；重启回收、流水线回收不动在跟卡；在跟卡归档等于验收。
  - 证据门：没有交付物、附件属于别的线程、组件不在本卡、只有文字没有自查、必需项缺一项（说出缺哪项），各自挡回；全部满足进 `awaiting_review`，交付物合并进 `deliverableRef` 且看板标签照常显示。
  - 交付后 `PATCH` 被拒；退回把原因以你的名义发进线程并开一轮，`returns + 1`；取消停掉正在跑的轮次和外部员工排队的活。
  - 延期：申请后不改 `due_at`，准许后改，`original_due_at` 不变。
  - 核对器（注入时钟）：待接下 5 分钟催、35 分钟通知；到期 5 分钟催、35 分钟逾期并通知；每天最多通知 3 次、最多催 3 次（按用户时区）；作息外不推、不催，提醒并进开工清点；轮次在跑时跳过；多副本只认领一次；催办不另开卡、不推送、不占唤醒额度。
  - 换人接手：原轮次停、卡换执行人和线程、新员工需重新接下、`original_due_at` 保留。
  - 流水只能追加（应用角色 UPDATE / DELETE 被拒）。
  - 清点：有在跟的卡才发，数字和看板一致；推送新种类点开落在正确页面。
  - 外部员工：规约每张卡只加一次，「预计」取值，没交东西不进已交成果。
  - 权限与租户：别人看不到的卡 404，群主不能代验收，所有查询带租户帧。
- 界面：设计稿六屏逐一对照截图（暗色真实系统，桌面和手机），给用户确认后再推。

## 我的决定

随设计稿已确认：
- 「派出 · 待接下」单独一列；员工 5 分钟没接下会再叫一次。
- 被挡回不打扰你，只在对话和流水里留一行，员工自己补齐。
- 验收标准在派活时就写下：员工接活时根据你的话整理，你可以改。
- 第一次催办在到期后 5 分钟；再过 30 分钟还没交才记逾期并通知你。

审阅后新定（请重点看）：
- 只有员工接下、你手动跟、外部员工排队这三种进三步；例行、职责、转交、群组流水线不自动进（免得看板和清点被塞满）。
- 一件活一张卡：后续追问、催办、退回的轮次都挂在原卡上，不另开卡、不另扣配额。
- 一轮出错不结束一件活，留在「在做」显示出错原因，核对器照常催；只有你验收或取消才结束。
- 催办用专门的「催办轮次」，不推送、不占员工唤醒额度、不扣任务配额。
- 催办只在你的作息内进行，同一件活每天最多催 3 次（2026-11-15 整期审查后用户拍板）。
- 群里谁派的活谁验收，群主不能代验收。
- 手机清点页和逾期页做在网页端，原生 App 推送深链到同一页面（App 需发新版）。
- 外部员工那部分等外部员工第二期合入后再做。
