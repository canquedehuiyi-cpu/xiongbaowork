## 一、意图

同一个设置散在很多地方，人找不到，也不知道哪一处算数：

1. 审批有 5 处：设置 › 审批、`/approvals`、管理 › 审批、每位员工的「审批与权限」、首次引导；「改动前先问」这个开关有 3 个名字（做任何改动前都先问我、改动前先问我、员工动手之前）。
2. 模型有 5 处：能力 › 模型库、管理 › 模型提供方、企业管控里藏着的模型白名单、员工设置、对话里的模型选择器。
3. 主动巡检 5 处，设备 4 处；技能、插件、密钥各有个人和管理员两份页面。
4. 企业管控只能靠输入地址进去；约 18 个只做重定向的旧地址；上游留下的英文分区没人挂载；团队版专属的入口出现在个人版里。

审计和实测又指出另一面的成本：
- 人已经连好了网盘，员工还是说没有权限。实测「v0.2.16 首轮」§9 百度网盘：连接页显示「已连接」「已授予 1 位员工」，被 @ 的员工却回复自己没有被授予百度网盘的工具权限。
- 模型「已绑定」「能连上」「部署允许运行」分在三个入口。实测「v0.2.16 首轮」§2 模型库：三条模型测试结果分别是 HTTP 503、通过、HTTP 401，而入口在「工作台 → 能力 → 模型库」。「DeepSeek 单独重跑」§4 普通对话：员工运行被 HTTP 403 拒绝，原因是模型不在允许的模型里。
- 从「想交办一件事」到发出第一条消息要来回好几个页面。实测「v0.2.16 首轮」§3 新建测试员工：角色必填，最后一步要选运行位置，表单没有模型字段，模型要建好后再去绑。
- 员工自己画的「批准」卡被当成了真审批。实测「白名单关闭后」§5 工具和审批 ›「开启审批 · 确实弹出批准卡片」：点「批准」后卡片显示「已批准」，命令仍是「没有运行」，审批队列里也没有对应的一项。系统审批卡的按钮是「允许一次」，不是「批准」。

本项目做两件事：把设置收成七个话题页，每个设置只剩一个控制、一个名字；在这些话题页和发送区上，把「这位员工现在能不能干这件事、卡在哪一层、下一步找谁」说清楚，并把第一次交办的路缩短。

## 二、目标、非目标、反目标

**目标**
- G1 设置只有一个入口（设置侧栏），下面七个话题，一个话题一页。话题页之外不再有第二个页面能改同一个设置。
- G2 每个可写的设置在全应用只渲染一个控制，只有一个名字；改名清单见 5.8。
- G3 管理员专属的控制放在对应话题页的「团队的……」一节，只有团队版管理员看得到；管理后台（`/admin` 概览、管理侧栏、企业管控）解散。
- G4 团队版专属的入口和内容在个人版隐藏；个人版专属的在团队版隐藏。门控规则集中到一处判断（5.1）。
- G5 旧地址都还能打开，重定向到新话题页对应的那一节；外部系统依赖的地址照旧可用。
- G6 删除没人挂载的死代码和合并后多出来的重复实现（第八节）。
- G7 「员工与模型」「连接与技能」两个话题页显示有效状态：模型能不能派发、应用是否已连接、是否授予这位员工、是否被规则拦住、是否需要在线设备，并给出下一步（审计 4.4）。
- G8 员工自己画的审批样式卡不会再被当成系统审批：工具说明和工具门控挡住误用，系统审批卡在外观上与之明显不同（5.6）。
- G9 第一次交办：首页给可编辑的起点，建员工时说明下一步，发送区一行写清收件员工、执行环境和相关能力，工作台首页先摆「等你处理」「可验收」「正在运行」（审计 5.1、5.2）。

**非目标**
- 不改服务器的接口、数据和行为（唯一可能的例外见第十四节问题 3）。
- 不重做审批续跑、交付终态、产物预览与下载（审计 4.1–4.3，#843–#846 已修）。只在界面缺显示时补显示。
- 不动每位员工自己的设置页（`/bots/$agentId` 及其分页、员工弹窗）：话题页可以链过去，不把每员工设置搬进全局设置。
- 不动工作页：任务看板、自主工作、长期职责、定时任务、@Waker、组团流程、团队 Bot、人才市场、能力里的知识库 / WakerFlow / 公开项目 / 记忆与信息源 / 角色模板 / 我的。
- 不做审计第六节：群聊分工、分身移交、岗位模板复用、长期职责复盘（列为后续阶段）。
- 不做语言切换、账号密码修改、头像（今天都没有，也不在这次范围）。
- 审计 7.2 的验收矩阵是 v0.2.17 的生产验收，不是本项目的验收。

**反目标**（做成了也算失败）
- 任何一个设置改了含义或默认值。
- 搬页面时丢了一个控制，或者一个控制在新页面上写到了别的数据。
- 旧地址打开是空页、404，或者丢了回跳参数：厂商授权回跳、`/plans` 的升级链接、微信里的审批链接、服务器发来的「去某页」链接。
- 非管理员看到了管理员一节，或者个人版出现团队版的东西；读不到版本时的回退变了（今天读不到按团队版）。
- 有效状态摘要说「能用」，实际运行被拒；或者说「不能用」，实际能跑。
- 员工画的卡仍然能写出「批准」「允许一次」，或者长得和系统审批卡一样。
- 删数据。

## 三、约束

### 3.1 只改前端（控制方判断，可推翻）

服务器的接口、数据和行为不变。两个界面写同一份数据的，只留一个控制；写不同数据的（比如本人的审批偏好和团队的审批设置），两个都留，作为同一页上的「你的……」一节和「团队的……」一节，名字要让人看出差别。服务器的英文文案、服务器发来的页面地址都不改，前端接住。

## 四、做法的取舍

- **甲（采用，用户选定）：一套按话题组织的设置。** 七个话题各一页；管理员控制是同页的「团队的……」一节；管理后台解散。好处：人只需要记一个入口；同一件事的个人设置和团队设置并排，差别一眼看出；「同一个设置只有一处」可以用测试锁住。代价：一次性搬动大量页面；管理员失去「管理」这个集中入口，要靠每页的团队一节；能力页的设计稿（05 资源中心六格）要改。
- **乙：保留「我的设置」+「管理后台」两套，各自内部去重。** 改动小，管理员习惯不变。但同一件事仍分在两套导航里（审批、技能、密钥、电脑、模型都是），人还是要先猜「这算我的还是管理的」；个人版没有管理后台，今天靠 `personalAdminRedirect` 和 `managePaths` 把一套组件挂到两处地址，这层间接还在。否决。
- **丙：不搬页面，只加一个设置搜索和一张「这个设置在哪」的总表。** 最省事，也确实能帮人找到。但不解决「同一个设置三个开关、三个名字」，也不解决个人版里的团队入口；搜索结果仍然把人带到两三个页面。否决，可作为甲完成后的补充。

甲胜在它直接对应用户那句话：同类的放在一个页面或一个按钮下面。乙和丙都留下了「两个地方都能改」。

## 五、设计

### 5.1 话题页的规则

1. **一个话题一页，一页一个地址。** 小的设置直接是行；大的列表（应用格子、技能库、审计记录、边界规则、成员）是这个话题的子页，只从话题页的一行进入（「摘要 + 箭头」），子页用 `backButton` 回话题页，地址在话题地址下面。子页不出现在侧栏，也不从别处另开入口。
2. **一节一种受众。** 每节声明：受众（所有人 / 团队版管理员）、版本（两个版本 / 只团队版 / 只个人版）。团队版管理员的节一律叫「团队的……」，排在本人的节后面，描述第一句是「只有管理员看得到。改动对所有成员生效。」个人版没有「团队的……」节；个人版专属的节叫「你的……」。
3. **门控集中。** 新增 `lib/settings/audience.ts`：`useSettingsAudience()` 返回 `{ edition, isAdmin, maySetUp, ready }`，`ready` 之前不画受众受限的节（不闪）；读不到版本仍按团队版。话题页与子页的路由守卫也从这里取：只团队版管理员的子页（`/settings/team/*`、边界规则、动作推演、试验台、自动审查的指引、团队规则描述、平台管理）非管理员送回所在话题页，个人版送回 `/settings`；只个人版的子页团队版送回所在话题页（团队版管理员另有入口的，如密钥，例外，见 5.3.4）。组件里零散的 `edition === "personal"` 判断，凡是决定一节画不画的，改为读这里。
4. **侧栏亮哪一项。** 侧栏项加 `owns`（同 `NAVIGATION.owns`）：账户与外观在 `/settings`（精确匹配），并认领 `/settings/plans`、`/settings/about`，个人版和不是管理员但 `maySetUp` 的人还认领 `/settings/setup`；团队版管理员的 `/settings/setup` 归团队管理。其余话题的子页都在自己的地址前缀下。
5. **每个可写控制带 `data-setting-key`。** 键名取它写的数据（如 `approvals.enabled`、`approvals.team.enforceAutoReview`、`enterprise.modelAllowlist`、`capability.proactive`），供第十节「只渲染一处」测试用。只读状态行不带。
6. **旧地址集中在一张表。** 新增 `lib/settings/moves.ts` 的 `SETTINGS_MOVES`（旧地址模式 → 新地址#锚点，带哪些参数），所有重定向路由都读它，测试也读它。`personalAdminRedirect`、`MOVED`、`managePaths` 里指向 `/admin` 的部分由它取代。
7. **应用内链接直接指新地址。** 不靠重定向中转。服务器发来的旧地址（3.2 的动作推演、部署清单）在前端按 `SETTINGS_MOVES` 换成新地址再画链接。

### 5.5 有效状态（审计 4.4）

话题页上的状态摘要和发送区、会话里的说法用同一套原因词。判定顺序照服务器运行入口：先看有没有，再看连不连得上，再看准不准用，最后看在哪儿跑。

**模型**（员工与模型 › 员工能不能跑、模型库）。401 和 503 两行的依据：实测「v0.2.16 首轮」§2 模型库。允许的模型那一行的依据：实测「DeepSeek 单独重跑」§4 普通对话的运行 403。

| 状态 | 条件（数据来源） | 显示 | 下一步 |
|---|---|---|---|
| 可派发 | 绑定的模型在目录里、未被白名单拦、最近一次测试通过 | 可以派活 · <模型> · 来自<来源> | 无 |
| 没有绑定模型 | 员工的 `modelRef` 空且没有部署默认模型 | 这位员工还没选模型 | 「选模型」→ 员工设置 |
| 密钥不对 | 模型库连通测试 401 | 模型服务商不认这把密钥 | 「改密钥」（有权时）/「告诉管理员」 |
| 暂时不可用 | 测试 503 / 上游限流 | 模型服务商暂时没回应 | 「再测一次」 |
| 不在允许的模型里 | 团队版白名单开着，模型不在名单（运行时 403） | 管理员没有允许这个模型 | 「换一个允许的模型」/ 管理员：「去允许」 |
| 套餐不支持自带模型 | 套餐 `customModels` 为假 | 当前套餐只能用部署自带的模型 | 「查看套餐」 |
| 需要在线设备 | 员工运行在已配对电脑上，电脑离线 | 它要用的电脑现在不在线 | 「查看设备」 |

**应用与能力**（连接与技能 › 应用的有效状态；同样的行也进员工自己的「技能与应用」页，那页不搬）。「已连接，员工未获授予」一行的依据：实测「v0.2.16 首轮」§9 百度网盘。连接页把「你已连接」和「已授予 1 位员工」并列，没说授予的是谁。新的状态行必须按员工写，写成「测试-Gemini 还不能用百度网盘」，不写一个总数。

| 场景 | 显示 | 下一步 |
|---|---|---|
| 个人账号未连接 | <应用>尚未连接 | 有权时「去连接」 |
| 已连接，员工未获授予 | 这位员工还不能用<应用> | 「查看可用员工」或「申请管理员授权」 |
| 已授予（只读 / 会改动） | 可以读取<应用> / 可以使用<应用> | 发原任务或缩小资料范围 |
| 员工工具要用离线设备 | 这项能力需要在线设备 | 「查看设备」或改选获准环境 |
| 规则阻止当前操作 | 当前动作受团队规则限制 | 「查看原因」，或按授权流程申请 |

工具名、过滤原因码（如 `FILTER_REASON_NO_EXTENSION_MODE`）、请求 ID 收在每行可展开的「诊断详情」里，只给管理员（个人版给那一个人），可复制，已脱敏。日常用户只看见能做的那一步。

**数据从哪来。** 能从现有读取拼出来的（模型目录与白名单 `availableModelsQueryOptions`、模型库测试结果、员工资料里的授权、`connectionsQueryOptions`、设备在线、能力开关），前端拼。但审计要求「与运行入口同一判定」（`server/src/admin/gate.ts:248` `governRun`），前端照抄会和服务器漂移。是否加一个只读接口见第十四节问题 3；在答复之前，PR 3、PR 4 先按前端拼装做，状态行标「据当前设置判断」，运行时以服务器结果为准。

共享使用读取要分清三种情况。实测「v0.2.16 首轮」§3 新建测试员工里，员工页读 `/api/plugins/shared-use/bot/<id>` 两次都是 404，正文只有 `404 Not Found`。状态行要区分：
- 确实没有记录：显示空态；
- 身份不符；
- 接口出错：显示「读不到」，并在诊断详情里给原因。

这三种不能互相冒充，也不能当成「未授予」（审计 4.4）。路由为什么 404 由实施者在 PR 4 核对。

### 5.6 员工画的审批样式卡（控制方判断，可推翻）

**问题。** 系统拦下受保护动作时，会话里画的是系统审批卡（`components/approvals/inline-approval.tsx`，读审批收件箱，按钮「允许一次」「拒绝」，批准后服务器执行一次）。员工另有一个生成式界面工具 `askApproval`（`shared/decision-tools.ts`，卡片 `components/gallery/decisions.tsx` 的 `ApprovalCard`），默认按钮就是「批准」「拒绝」。生产里员工自己画的「批准」卡被当成了真审批，点了只是回答了员工，什么也没执行。证据见实测「白名单关闭后」§5 工具和审批 ›「开启审批 · 确实弹出批准卡片」：卡片名「新建测试文件」，按钮「批准」，点后显示「已批准」，命令仍是「没有运行」，审批队列里没有对应项。底层的审批关联已由 #843 修好；这一节防的是两种卡被混为一谈。

**挡住误用（工具说明 + 工具门控，都在浏览器一侧，服务器不改）：**
1. 工具说明（`decisions.tsx` 里 `askApproval` 的 `description`）改为：只用于只有本人能做的业务决定（如「给这笔订单退款吗」）；明确写「不要用它请求写文件、运行命令、改动应用或网站：这些由系统审批，系统会自己问」；「被系统拦下时不要再画这张卡，等系统审批的结果」。卡片标题 `title` 从 Approval 改成「向你确认」。
2. 工具门控：浏览器的人在环工具处理函数里，若这一轮已有待处理的系统审批（同一 `runId` 在审批收件箱里有 pending），或者这次 `askApproval` 的参数里出现受保护动作的工具名、文件路径或命令（复用卡片今天就会解析的 `command` 字段），不画卡，直接回给员工一句固定结果：「这一步由系统审批，已经在等本人处理，不要重复请求。」这样运行也不会因为一张没人该点的卡挂起。
3. 卡片自己的按钮词不能冒充系统：`approveLabel`、`rejectLabel` 落在「批准、允许、允许一次、同意执行」这类词上时一律换成默认词；默认词从「批准 / 拒绝」改成「同意 / 不同意」。

**外观区分：**
- 系统审批卡：顶部固定一条「系统审批」标签（盾牌图标 `IconShieldCheck`），写动作、对象、运行位置和批准范围（4.1 已有的动作摘要），按钮只有「允许一次」「拒绝」（以及规则允许时的范围选项）；卡片外框用审批专用的强调色。这些只能由 `InlineApproval` 画，生成式组件拿不到。
- 员工提问卡：顶部写「<员工名>在问你」（不带盾牌），底部一行小字「这是员工的提问，不是系统审批。受保护的动作由系统另行审批。」外框用普通卡片样式。
- 两种卡各有一条视觉回归截图（5.10）。

## 十一、风险

- **授权回跳多一跳。** `/connections*` 和 `/admin/plugins/$key` 都变成重定向。参数丢一个，用户就看不到「已连接」或失败原因。10.1 逐参数锁住；上线后看授权完成率。
- **两个大组件合并。** 应用页（`connections.$key.tsx` 792 行）和 `plugin-page.tsx`（1999 行）合成一页带管理员节，回退面大。PR 4 可拆；个人版今天的合并形态是参照。
- **管理员找不到东西。** 没了「管理」入口，管理员要知道控制在哪个话题。缓解：每个团队节统一叫「团队的……」；工作台首页管理磁贴保留；服务器发来的旧地址都接得住。
- **用户的肌肉记忆和设计稿。** 能力页从六格变三格，工作台「连接」变快捷入口，「审批」变「待审批」。这改了 05 资源中心的设计稿和 M5b 时用户定过的导航（`lib/navigation.ts` 注释）。问题 2 让用户拍板。
- **两套实现留一套。** 密钥页、电脑页各删一份，删掉的那份若有独有行为就丢了。实施者逐行对照后再删，不确定的先保留并在 PR 里写明。
- **有效状态和运行结果对不上。** 前端拼装可能与 `governRun` 漂移（问题 3）。
- **门控闪烁和回退。** 话题页受众判断集中后，读版本失败按团队版的规则不能变；10.2 有专门用例。
- **服务器文案指错地方。** 4 句服务器文字写着旧位置（5.8 末），不改就会指向不存在的「已连接的账号」。
- **测试与工具锁住了旧地址。** parity 截图路由表、i18n 路由表、遗留路由测试都按旧地址写，要同步改。
- **和并行工作冲突。** 设置、管理、连接这几十个文件动得多；排在 v0.2.17 之后，开工前和正在进行的去品牌后续任务对一下文件。
- **员工卡门控误伤。** 合法的业务确认（退款、发布环境）被当成受保护动作挡掉。门控只看同一轮有没有待处理系统审批和参数里的受保护工具名、路径、命令；其余照常画。

## 十四、需要用户拍板的问题

1. **「等你处理」的待办放哪？**
   - A（推荐）：待办留在 工作台 › 待审批（`/approvals`，含管理员的访问申请、团队账号使用申请）；设置 › 审批与安全只放设置。理由：待办是每天要处理的事，不是设置；手机审批详情、微信链接本来就在 `/approvals`。
   - B：待办和设置都在 设置 › 审批与安全，工作台「审批」变成指过去的快捷入口。
   选 B 时改动：D02、N15、N16 改去审批与安全，U41 取消，工作台首页「等你处理」改指设置页。
2. **设置以外指向已搬走内容的入口怎么处理？**（工作台「连接」、能力的插件 / 技能 / 模型库 / 组件四格、工作台首页三张管理磁贴）
   - A（推荐）：工作台「连接」和首页管理磁贴留作快捷入口，指向设置里的唯一页面；能力四格去掉（页签点了跳出能力页会让人迷路）。
   - B：全部留作快捷入口。
   - C：全部去掉，只从设置进。
3. **有效状态要不要一个只读的服务端接口？**
   - A：只用现有读取在前端拼，服务器零改动；状态行标「据当前设置判断」，可能与运行时的判定有出入。
   - B（推荐）：加一个只读接口（如 `GET /api/agents/:id/readiness`），直接调用运行入口的同一判定（`governRun` 和授权检查），不改任何行为和数据。这是对「只改前端」（3.1）的一个窄例外。理由：审计 4.4 要求「与运行入口同一判定」，A 做不到这一点。

**用户答复（2026-11-27：「全部按推荐」）**
- 问题 1 选 A：待办留在 工作台 › 待审批，设置 › 审批与安全只放设置。
- 问题 2 选 A：工作台「连接」和首页管理磁贴留作快捷入口，能力四格去掉。
- 问题 3 选 B，并加两条：
  - 只读接口 `GET /api/agents/:id/readiness` 调用运行入口的同一判定。成员本人能读到自己是否被规则拦住，不需要管理员的动作推演接口。
  - 服务器记下每个模型最近一次「测试」的结果：时间、通过或失败、HTTP 状态和一句话原因，不存正文或密钥。readiness 读这份记录。打开状态页不自动探测（每次探测都会真实调用服务商、计费、可能被限流）。没测过显示「未测」并给「测试」按钮。「可派发」的条件是「最近一次测试通过，或没测过但其余条件都满足」，后一种标「未测」。
- 问题 4 选 A：员工画的「向你确认」卡保留，外观与系统审批卡明显区分，标「员工在问你，不是系统审批」。
  - 同一个动作已有待处理的系统审批时不画。判断用前端已有的 `threadId` 加 `toolCallId`（`toolCallId` 对得上的那张），不用 `runId`。
  - 工作台「待审批」数字只计系统审批，员工卡单独计。这要改 `shared/decision-tools.ts` 的归类和 `server/src/approvals/decision-waits.ts` 的计数。
  - `ApprovalCardProps.command` 和活动里的「被拒的命令」保留。

据此，3.1「只改前端」的例外共三处，都不改现有行为：readiness 只读接口、模型测试结果落库、员工卡与系统审批分开计数。5.5、5.6 与上述冲突处以本节为准。
