# 聊天软件通道：在飞书里派活、收汇报、点按钮批准

日期：2026-11-16 · 状态：待用户确认
前序：外部员工规格（`docs/specs/2026-11-15-external-agents.md`）里的「1b」；交付闭环规格（`docs/specs/2026-11-15-delivery-loop.md`）把「IM 推送」留给本项目。

## 为什么做

熊宝的员工在电脑上、云端干活，真正需要人的时候只有三种：派活、看汇报、拍板。这三件事现在只能在熊宝网页或手机网页里做；国内团队每天开着的是飞书、企业微信、钉钉，不会为了批一个操作专门去开熊宝。

用户要求「手机的通知和审批先走用户已经装了的聊天软件」，国内要接「飞书、钉钉、企业微信、微信机器人、QQ 机器人」。外部员工规格把它定为 1b：「每个通道能对话派活、收汇报、点按钮批准」。

## 用户说过的

- 「选 A，国内海外都要照顾」（手机的通知和审批先走用户已经装了的聊天软件）
- 「国内的用户接入：飞书、钉钉、企业微信、微信机器人、QQ 机器人」
- 外部员工规格 1b：海外 Telegram；国内飞书、企业微信先，钉钉、QQ 后，微信 ClawBot 放量后接。
- 交付闭环：IM 上线时作为同一份内容（逾期、清点）的另一个出口；同样遵守作息和每天 3 次。
- 「等你确认」在对话、审批收件箱、手机网页、已接的聊天通道都能批，任何一处批了就算数；三个选项：批准一次 / 拒绝 / 这次对话里都允许。
- 2026-11-16：选做法 B（每家客户填自己的企业自建应用），先接飞书，再企业微信，之后钉钉（「按照你的建议执行」）。

## 现状（摸底）

- 真接上的外部通道只有 Slack、Teams（经 OpenTag）、短信（Twilio）、手机推送（Expo）。国内平台投递层一个都没有；OpenTag 上游只支持 Slack/Teams，借不了它。
- 投递核心在 `server/src/delivery/`：`router.ts`（notify / notifyAttention / 发件箱清扫）、`store.ts`（绑定、收发件箱）、`types.ts`。`TextTransport` 只能发纯文本；`ChatTransport` 是写死的联合类型，加一个通道约改 12 处（含前端 3 处）。
- 身份：`delivery_bindings` 唯一键 (transport, realm, identity)，一个聊天账号只绑一个「对话 × 员工」，所以现在没法在聊天里给不同员工派活。关联码 `link <uuid>` 只在私聊兑现。
- 审批卡只在「OpenTag 正在进行的那一轮」里画；轮次外的审批、逾期、清点推到 Slack/Teams/短信都是纯文本、无按钮、无链接。
- 安全约定已经成形：先验签（常量时间）→ 发送者只取验签过的结构化字段 → 绑定在平台帧查、行租户帧执行 → notify 只在本人帧 → 发前再 authoriseScope → 私密性未知按共享处理 → 结果不确定记 unknown、不重发 → 审批只经 approvals 服务、底线不给「总是允许」。
- **租户是「人」**：`tenant_id = users.id`，一个人一个租户（`CONTEXT.md`，决策 D12），另有一个共享的 `team` 租户（`server/src/db/schema/tenant.ts`）放全队共用的行。代码里没有「企业 / 组织」这一层，管理员是部署级的角色。一个部署服务一家客户（京东云就是这样独立部署的）。
- 凭据目前都是部署级环境变量；租户级要进保险库（`server/src/credentials.ts`，AES-GCM v2，AAD 绑行；新 credential kind 要迁移）。租户可填的地址必须走 `server/src/net/outbound-guard.ts` 的 `guardedFetch`。

## 目标

1. **客户自己接飞书。** 部署的管理员在「工作台 › 管理 › 聊天软件」里填自家飞书「企业自建应用」的 App ID 和 App Secret（一个部署接一个飞书应用，见「待你拍板」），熊宝测一次连接，显示「已连接 · 应用名」。页面附图文指引：在飞书开放平台建应用、开哪些权限、发布版本。
2. **人和飞书账号绑定。** 每个人在「我 › 通知」里点「绑定飞书」，在飞书里给熊宝应用发一条关联码，绑好后显示飞书名字。一个飞书账号绑一个熊宝的**人**（不再是「一个对话 × 一个员工」）。
3. **在飞书里派活、聊天。** 私聊熊宝应用：
   - 开头写「@员工名」就交给那位员工（名字按这个人能看到的员工匹配，重名时回一张选人卡）；
   - 不写就交给这个人上一次在飞书里聊的员工；第一次用时回一张「找谁？」卡，列出最近的 5 位员工；
   - 员工的回复、进度摘要、交付卡回到同一个飞书私聊，每条标明是哪位员工说的。
4. **在飞书里拍板。** 「等你确认」推到飞书时是一张卡片：谁、想做什么、为什么（一句中文，来自 `approvalPhrase`），三个按钮「批准一次 / 拒绝 / 这次对话里都允许」（底线类只有前两个），外加「在熊宝里看详情」链接。点了就算数；别处先批了，卡片更新为「已由 某某 在 网页 批准」，按钮失效。
5. **交付闭环出口。** 逾期、开工 / 收工清点、交付待验收推到飞书时也是卡片：逾期卡有「再催 / 准许延期 / 换人 / 取消」，交付卡有「验收 / 退回（写原因）」，清点卡列数字并带「打开看板」。同样遵守作息和「同一件活每天最多 3 次」；作息外的并进下一次开工清点。
6. **企业微信、钉钉照同一套接。** 飞书做完后，企业微信、钉钉各写一个适配器，复用入口层、卡片模型、回调处理，不再改业务代码。

## 不做（这一期）

- 不把飞书群映射成熊宝群组，不在飞书群里 @ 员工派活。群里的分享检查、成员与可见性比私聊复杂得多，单独做（见「以后」）。
- 不上飞书 / 企业微信应用市场（服务商模式，做法 C）。这是商务决定，B 跑通后再说。
- 不接 QQ、微信 ClawBot、Telegram。适配器层留好位置，排在后面。
- 不做语音、图片、文件消息的派活：收到非文字消息回一句「目前只认文字，图片和文件请在熊宝里发」。员工交付的附件只发链接，不把文件传到飞书。
- 不改 Slack / Teams：它们继续走 OpenTag，只是同样用上新的卡片出口（见「卡片出口」）。
- 不在飞书里做配置：招人、改规则、改作息都回熊宝网页。

## 反目标（做到了也算失败）

- 一个人的飞书消息、审批、卡片落到另一个人那里；或绑定时冒认了别人的飞书账号。
- 在飞书里能绕过三条底线，或底线操作出现「这次对话里都允许」。
- 同一条审批在飞书和网页各批了一次，两次都生效；或者网页已经拒绝，飞书卡片仍能点批准。
- 飞书重复投递同一条消息，员工收到两遍活。
- 应用凭据（App Secret、token）出现在日志、错误信息、前端响应里。
- 通知变成骚扰：超过交付闭环规定的频率，或作息外推送。

## 约束

- 租户：飞书连接是**部署级**的，连接行和它的凭据记在 `team` 租户下（与共享 MCP 凭据同一种放法：`credentials.ts` 现在只允许 `mcp`、`mcp_oauth_client` 写到 `team`，`chat_app` 加进这个名单），只有管理员能写，后台在平台帧读。人级的身份、路由、入站收件箱带这个人的 `tenant_id`。入站在平台帧按连接和发送者 open_id 找到本人，之后一律在本人帧里执行；出站在本人帧里，发前再 `authoriseScope`。
- 凭据进保险库：新增 credential kind `chat_app`（迁移），AES-GCM v2，AAD 绑行。只存 App ID（明文，便于显示）和 App Secret（密文）；`tenant_access_token` 只放内存，到期前刷新，不落库。
- 出站地址固定：飞书只连 `open.feishu.cn` 和它为长连接返回的 wss 地址（国际版 Lark 这一期不做）。地址写在代码里或由飞书返回，不让人填，所以不经 `guardedFetch` 的自定义地址路径；服务器端目前没有统一的出站主机白名单，这一期也不新建。
- 中文文案；卡片里的员工名、动作说法用 `shortName()` 和 `approvalPhrase`，不出现内部名字和上游品牌。
- 新表、新路由按现有规矩：迁移放 `server/recovery/recovery-20261018-v1/sql/`，接现有编号；入站收件箱只追加。

## 做法（用户已选 B）

- **A 部署级应用**：整个部署只接一个飞书应用，凭据写在服务器配置里。最快，但多租户下只能服务一家企业。未选。
- **B 每家客户填自己的企业自建应用（选定）**：客户在自家飞书后台建一次应用，管理员在熊宝界面里填进来；熊宝把凭据加密存进保险库，按发送者找到本人。不需要平台服务商资质，国内 SaaS 常用。代价是多一层租户凭据和路由，客户要自己建一次应用（给图文指引）。
- **C 上架应用市场（服务商模式）**：一键安装，体验最好，但要先办服务商资质和审核，周期长。B 跑通后再评估。

## 怎么做

### 1. 通用聊天入口层（与平台无关）

把 `delivery/opentag-agent.ts` 里与平台无关的逻辑抽成 `delivery/chat/` 下的通用模块，OpenTag 和新适配器都调它：

- **关联**：关联码兑现、`ownedBinding`（按发送者找到本人绑定）；
- **路由**：解析「@员工名」、记住「上一次聊的员工」、重名时出选人卡；
- **分流**：私聊照常交给员工开一轮；收到群消息这一期只回一句「目前只在私聊里工作」；
- **回答**：员工的提问、审批、交付在这一轮里怎么回到聊天；
- **会话**：从飞书交给某位员工的活，跑在这个人和这位员工的**默认单聊**里（网页上「消息」里的那一段），所以熊宝里同样能看到，「这次对话里都允许」也按这段单聊记；`decideAsBinding` 里「审批属于这段对话」的校验改成「审批属于本人、且在本人能看到的对话里」；
- **决定**：卡片按钮回调统一走 `decideAsBinding`，再进 approvals 服务（底线、并发、谁先批谁算数都在那里判）。

### 2. 绑定改成「人」级

- 新表 `chat_identities`：(tenant_id, connection_id, platform_user_id) → user_id，唯一键 (connection_id, platform_user_id)。飞书的 open_id 是「每个应用一个」，所以必须带连接 ID。
- 新表 `chat_routes`：(tenant_id, user_id, connection_id) → last_agent_id，记「上一次聊的员工」。
- 旧的 `delivery_bindings` 不动，Slack / Teams / 短信照旧；以后再把它们迁到人级（见「以后」）。

### 3. 连接与凭据

- 新表 `chat_connections`：tenant_id、platform（`feishu` | `wecom` | `dingtalk`）、app_id、凭据引用、状态（已连接 / 连接失败 + 原因 / 已停用）、最近一次成功时间。一个租户每个平台一个连接（这一期）。
- 管理员保存凭据时，服务器先用它换一次 `tenant_access_token` 并读应用信息，成功才保存，失败把飞书返回的原因翻成中文告诉管理员。
- 停用或删除连接：立即断开长连接，作废内存里的 token，已发出的卡片按钮点了回复「这个连接已停用」。

### 4. 飞书适配器

- **开工第一步先实测网络**：在京东云的服务器上连一次飞书长连接（换 wss 地址、保持 10 分钟）。连不上或会被切断，就改走 HTTP 回调：需要公网地址，按飞书规则验签和解密，其余不变。
- **收消息用长连接**（飞书「长连接」事件订阅）：服务器不需要公网回调地址，也不用验签回调请求。每个已连接的租户一条长连接；进程启动时为所有「已连接」的连接各建一条，断线指数退避重连。
- **多副本**：飞书对同一应用的多条长连接是随机投递一条（不广播），所以多个服务器副本各连一条也不会重复收；仍用消息 ID 去重兜底（入站收件箱唯一键 (connection_id, message_id)）。**开工前核实**这一行为和每应用连接数上限，不成立就改为选主：只有一个副本持有某个连接。
- **事件**：`im.message.receive_v1`（私聊文字）、卡片按钮回调（同样经长连接）。只取验签后的结构化字段：发送者 open_id、会话类型、消息 ID、文本。
- **发消息**：文本和交互卡片（飞书卡片 JSON）；卡片更新用飞书「更新卡片」接口，按钮回调响应里直接返回新卡片。
- **权限清单**（写进图文指引，**开工前按飞书开放平台当前文档核实**）：接收单聊消息、以应用身份发消息、读取用户基本信息（取名字用于绑定显示）。

### 5. 卡片出口（所有通道共用）

发件箱支持结构化卡片 payload，而不只是文本。卡片模型与平台无关，各适配器负责渲染：

| 卡片 | 内容 | 按钮 |
|---|---|---|
| 等你确认 | 员工名、想做什么（`approvalPhrase` 的中文）、在哪个对话 | 批准一次 / 拒绝 / 这次对话里都允许（底线类只有前两个）；在熊宝里看详情 |
| 交付待验收 | 活的标题、交付物摘要（附件只给链接）、自查 | 验收 / 退回（弹出输入原因）/ 打开卡片 |
| 逾期 | 活的标题、原定时间、核对经过一句话 | 再催 / 准许延期 / 换人 / 取消 / 打开卡片 |
| 开工 / 收工清点 | 几件没收、最早几点到期、几件等你验收、几件逾期 | 打开看板 |
| 选员工 | 「找谁？」/ 重名候选 | 每位员工一个按钮 |

- 按钮回调携带不透明的动作令牌（服务器签发、短期有效、绑定 卡片 × 动作 × 本人），不在按钮里放审批 ID 之类的内部编号。
- 逾期、延期、换人、取消这些按钮映射到现有 tasks 路由的同一套服务函数；「准许延期」「退回」需要输入时，用飞书卡片的输入框，不跳网页。
- 卡片状态随事实更新：别处已处理的卡片，按钮作废，正文写结果和处理人。
- Slack / Teams 这一期不接卡片：它们的主动投递走 OpenTag 的 `/openbot/deliver`，只收纯文本，轮次外点按钮也没有回调通路，而 OpenTag 不在本仓库。这一期只给它们的文本加上「在熊宝里处理」链接；短信同样是文本加链接。

### 5b. 什么推到飞书、什么时候推

- **推**：所有「等你确认」；交付闭环的交付待验收、逾期、开工 / 收工清点；从飞书发起的那几轮里员工的回复和进度摘要。
- **不推**：在网页里发起的对话里的普通回复（打开熊宝就能看到，推过去只会刷屏）。
- **作息和每天 3 次**：只管主动提醒（逾期、清点、催办），与交付闭环相同。审批和对你刚发起的活的回复是你在等的事，实时推，不受作息限制。
- **多个出口**：飞书加进现有的按种类选出口（`resolveUpdateRoute`）。绑了飞书的人，审批和交付闭环默认走飞书；手机推送照常；短信在绑了飞书后不再发这几类。「我 › 通知」里可以按种类改。

### 6. 网页里的入口（界面期，先截图再推）

- **工作台 › 管理 › 聊天软件**（管理员）：飞书一行，未接时「接入飞书」，接上后显示应用名、状态、最近一次连接时间、「停用」。点开是填 App ID / App Secret 的对话框和图文指引。
- **我 › 通知**（每个人）：「飞书」一行，未绑时「绑定飞书」（显示关联码和步骤），已绑显示飞书名字和「解绑」。管理员没接飞书时这一行写「管理员还没接入飞书」。
- 员工名片、对话顶栏不加东西：在飞书里聊的内容照常出现在熊宝的对话里，带「来自飞书」小字。

### 7. 企业微信、钉钉（之后两期）

- **钉钉**：用 Stream 模式（长连接），结构与飞书相同。
- **企业微信**：自建应用收消息必须配一个**回调地址**，平台对回调域名和调用来源 IP 有限制（可信域名、企业可信 IP；新建应用的回调域名要求与企业主体相关）。**开工前必须核实**：如果要求客户自己的域名，B 在企业微信上不可行，需要改走「服务商代开发」或让客户在自己域名上做转发。这一点核实后再写企业微信的细节，不影响飞书期。

## 验收

- 同一个飞书应用下两个人各自绑定，互相收不到对方的回复、审批和卡片；用别人的关联码、伪造 open_id 都绑不上，测试里构造不出串号。
- 私聊「@代码熊 帮我看看今天的报错」→ 代码熊开一轮，回复回到飞书，熊宝对话里同样能看到。
- 员工请求许可 → 飞书收到卡片 → 点「批准一次」→ 员工继续；同一条在网页上已经显示「已由 某某 在 飞书 批准」。反过来先在网页拒绝，飞书卡片按钮作废。
- 底线类操作的飞书卡片只有「批准一次 / 拒绝」。
- 同一条飞书消息重复投递，员工只收到一次。
- 逾期卡点「准许延期」并填时间 → 卡片更新、看板上的预计时间改变、流水记一条。
- 主动提醒（逾期、清点、催办）作息外不推、同一件活一天最多 3 次；审批作息外照常实时推。
- App Secret 不出现在任何日志、错误和接口响应里（测试里搜原文）。

## 待你拍板

**一个部署接几个飞书应用？**代码里租户是「人」，没有「企业」这一层；一个部署服务一家客户。所以「每家客户填自己的应用」落到代码上，就是**每个部署的管理员在界面里接自家的一个飞书应用**。我按这个写了全文。

- 如果你打算让**多家企业共用同一个部署**（比如一个京东云实例卖给好几家公司），就要先补出「企业」这一层：哪些人属于哪家企业、哪个管理员管哪个连接、绑定时怎么核实这个人属于这家企业的飞书。这是另一个项目，工作量会成倍增加，飞书要等它做完。
- 我的建议：这一期按「一个部署一个飞书应用」做；多企业共用部署等真有这个需求再单独立项。
