# 本机应用自动发现：员工在对话中发现、用户一句话启用（数字员工操控本机应用 · 子项目三）

日期：2026-11-08
状态：草稿，待用户审阅

上游：
- 子项目一「本机 MCP 桥接」已上线（v0.2.2 / device-v0.2.2-rc.1），见 `docs/specs/2026-11-07-device-mcp-bridge.md`。
- 子项目二「桌面操控」的规格是 `docs/specs/2026-11-07-desktop-control.md`（#314），与本项目并行推进。

用户反馈（2026-11-08 真机验收）：
- 在设备端表单里填「命令 / 参数 / 环境变量」对普通用户太难，而且第一次就失败了。失败原因是 Windows 上用带引号的方式调用 `npx.cmd` 时，`%~dp0` 会取错目录，修复见 `fix/runner-win-cmd-shim-path`。
- 用户希望：**员工能在对话中自动识别本机有哪些应用可用，用户不需要做任何配置。**

用户已定的方向：
- 发现来源三项都要：其他 AI 工具的 MCP 配置、内置的常用软件清单、本机已安装软件列表。
- 与桌面操控两个项目一起做。

## 1. 目标

**目标**：用户不填任何表单。员工在对话里说出「本机有哪些应用可用」，用户在审批卡片上点一下「允许」，就能启用。

**成功标准**：
1. 新增设备动作 `apps.discover`，返回本机的候选应用。每个候选包含名称、来源、类型（启动命令或本机地址）、是否已启用，以及一个不透明编号。**命令行、参数、环境变量、文件路径都不离开本机。**
2. 员工调用 `computer_apps` 时，返回分为三组：
   - 已启用：沿用现有内容；
   - 可启用：发现到但还没启用的 MCP；
   - 已安装、没有 MCP 的软件：只给名字，并提示这类软件可以走「桌面操控」。
3. 新增工具 `computer_app_enable(candidate)`，这是写操作，一律走审批。审批卡片显示应用名称和来源，例如「允许员工使用本机应用「Figma」？来源：内置清单，检测到 Figma 正在运行」。批准后由设备端把候选写入 `runner-apps.json` 并测试连接，测试通过后返回工具列表。员工紧接着就能调用这个应用。
4. 常用的 npm 类 MCP 不要求用户自己装 Node.js：设备端用自带的 Bun 运行时执行 `bunx`。
5. 设备端窗口的「本机应用」区域改为列出「发现的应用」，每项一个启用开关；原来的表单收进「高级：手动添加」。
6. 真机验收（用户的 Windows 电脑）：
   - 说「我电脑上有哪些可以用的应用」，员工能列出发现结果；
   - 说「启用文件助手」（或内置清单里检测到的某个应用），弹出审批，批准后员工直接使用；
   - 整个过程不需要打开设备端窗口填写任何东西。

**不做的**：
- 自动安装软件或插件，比如替用户安装 Blender 的 MCP 插件。只做提示。
- 访问本机回环地址以外的服务。
- macOS / Linux 的发现规则：第一期只做 Windows，其他平台返回空的候选列表。

## 2. 发现来源（设备端 `runner/src/discover.ts`）

都只读，每次 `apps.discover` 时现扫。某个来源出错就跳过它，不影响其他来源。

### 2.1 其他 AI 工具的 MCP 配置
| 工具 | 文件（Windows） | 字段 |
|---|---|---|
| Claude Desktop | `%APPDATA%\Claude\claude_desktop_config.json` | `mcpServers` |
| Claude Code | `%USERPROFILE%\.claude.json` | `mcpServers`（含各项目下的） |
| Cursor | `%USERPROFILE%\.cursor\mcp.json` | `mcpServers` |
| VS Code | `%APPDATA%\Code\User\mcp.json`；`settings.json` 的 `mcp.servers` | `servers` |
| Windsurf | `%USERPROFILE%\.codeium\windsurf\mcp_config.json` | `mcpServers` |

- **字段取舍**：只取 `command/args/env/cwd` 或 `url`，`url` 只接受回环地址。读不懂的字段直接忽略。
- **去重**：同一个「命令 + 参数」或同一个 url 只保留一条。
- **密钥处理**：环境变量里的密钥只在启用时复制进本机的 `runner-apps.json`。发现结果里只带变量名，不带变量值。

### 2.2 内置常用软件清单（`runner/src/discover-catalog.json`）
- **条目内容**：软件名、检测规则、启动方式。
  - 检测规则：已安装程序名的正则、可执行文件路径、回环端口探测（发一次 MCP `initialize` 握手）。
  - 启动方式：`bunx <npm 包>`，或者回环 url。
- **首批条目**：每一条都要在实现时真机验证，验证不了就不收录。候选有：
  - Figma 桌面版的 Dev Mode MCP（本机地址）；
  - JetBrains IDE 自带的 MCP；
  - 基于 npm 的常用工具，例如文件系统、Excel/Office 文件读写类。
- **维护方式**：清单随设备端版本发布，不从网络下载。

### 2.3 本机已安装软件列表
- **来源**：读注册表 `HKLM/HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall`，包括 `WOW6432Node`，只取 `DisplayName`。
- **用途**：一是用来匹配内置清单；二是作为「没有 MCP 的软件」名单返回，供桌面操控参考。
- **过滤**：去掉系统组件和更新补丁（`SystemComponent=1`、`ParentKeyName`、带 KB 编号的条目），最多返回 200 个。

## 3. 运行时：设备端自带 Bun
- runner 本身就是 `bun build --compile` 打包出来的可执行文件。启动 npm 类 MCP 时，用 runner 自身加上 `BUN_BE_BUN=1` 充当 `bun x`。这个用法要先确认当前 Bun 版本支持；如果不支持，就把 bun 可执行文件随设备端一起打包。
- 发现结果里的 `npx`、`bunx` 命令，启用时统一改写成自带运行时。用户自己装了 Node.js 也不影响。
- `uvx` 这类 Python 工具不自带运行时。用户没装 `uv` 时，候选标注「需要先安装 uv」，并且不能启用。

## 4. 服务器与审批
- **`computer_apps`**：沿用现有规则，仍然只读，仍然只有员工主人本人的运行能用，仍受「查看本机应用」开关管。返回值加上「可启用」「已安装无 MCP」两组。
- **`computer_app_enable`**：
  - 审批：一律走审批。审批摘要绑定候选编号和应用名称，参照 MCP 桥接里 C1 的规则：摘要里不放会变化的描述。
  - 权限：受团队「电脑上运行命令」上限约束，上限是「从不」时直接拒绝。
  - 前置检查：设备离线时提示「设备不在线」，不进入排队。
- **候选编号的有效期**：由设备端在 `apps.discover` 时生成，10 分钟内有效。过期后启用会失败，提示「请重新查看本机应用」。

## 5. 安全
1. 发现到的东西只是候选，启用必须经过人工审批，不会自动启用。
2. 命令行、路径、环境变量值都不发给服务器，审计里只记录应用名称和来源。
3. 已安装软件名会进入模型上下文，所以受员工级「查看本机应用」开关控制。这个开关默认开，可以设为「从不」。
4. 启用的应用沿用 MCP 桥接已有的保护：只读工具不弹审批，写工具要审批；结果不明的调用会暂停设备。

## 6. 分期
- **第 1 期**：`apps.discover` 做来源 2.1 和 2.3；`computer_apps` 返回三组；对话里能列出结果。
- **第 2 期**：`computer_app_enable` 加审批；自带 Bun 运行时；设备端窗口改成「发现的应用 + 启用开关」，手动表单收进「高级」。
- **第 3 期**：内置清单（2.2）逐条真机验证后收录。
- **真机验收**：就是 §1 的第 6 条。

## 7. 风险
- **其他工具的配置格式会变**：解析容错，出错只跳过对应来源。每个格式都有固定样例测试。
- **`BUN_BE_BUN` 不可用**：退回到随设备端附带 bun，安装包会大约 50 MB。
- **已安装软件名属于隐私**：受开关控制，而且只在主人本人发起的运行里返回。
