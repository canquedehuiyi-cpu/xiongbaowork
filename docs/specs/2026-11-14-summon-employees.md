# 召唤员工：会话从空开始、翻卡召唤、按员工安装技能

日期：2026-11-14 · 状态：用户 2026-11-14 已确认（原话「没问题」）

## 为什么做

熊宝做的是「一人公司」（OPC）：一个人带一队数字员工把公司开起来。预设员工不是一上来就在岗的人，而是**等着被招来的员工**。用户召唤谁，谁才进到自己的会话里；召来以后，用户再给他一个个装技能、装插件、选模型。

现在的做法跟这个相反：
- 新用户一登录，会话列表里已经有「通用助手」「研发流水线」等会话，还有「我的分身」；
- 包里预设的技能在开通时就自动装到各个员工身上，看起来「默认全装了」；
- 预设员工没有配熊宝形象，显示的是按名字生成的圆球；
- 员工会话页顶部的大头像卡片是消息列表的第一条，聊多了就被顶走。

## 用户说过的（原话或原意）

- 「会话里没有，必须在员工列表进行召唤才可以」
- 「召唤员工要有一个翻卡动画，炫酷一点，类似游戏一样的召唤效果，图像或者翻卡形象用我们预设的那些头像」
- 「预设的员工要有我们已经预设好的头像」
- 「我们预设的员工就是等待招聘的员工，每个员工用户召唤好之后，可以给每个员工安装技能、插件、模型」
- 「能力内的技能与插件，市场预设的需要安装才可以使用，目前的技能是默认全安装了」
- 「这个头像还是没有固定住……我要他固定」
- 方案选 A（员工列表里分「已召唤 / 待召唤」，在原有员工和安装机制上改）。
- 2026-11-14 修订（用户「可以，按这个改」）：召唤时给用户复制一份**自己的**员工，因为预设员工是全系统共用的一份、只有管理员能改，不复制的话用户没法给自己的员工装技能、插件、选模型。

## 目标

1. **会话列表从空开始。** 新用户开通后，会话列表里没有任何会话；「我的分身」会话也不再在第一次打开会话列表时自动建。
2. **在员工列表召唤。** 员工列表分两栏：「已召唤」和「待召唤」。
   - **待召唤**：28 个预设员工（人才库，所有人看到的一样），外加还没召唤过的「我的分身」（熊宝小跟班）。
   - **召唤一个预设员工**：照着预设给本人复制一个员工（名字、职务、人设、提示词、熊宝头像相同，归本人所有、仅本人可见），建本人和这个新员工的一对一会话，播翻卡动画，结束后进入会话。
   - **召唤分身**：分身本来就归本人，不复制，只建一对一会话。
   - **已召唤**：本人召唤来的员工、分身，以及本人自己建的员工。按钮是「进入会话」。
   - 同一个预设员工每人只能召唤一次：已经召唤过的，预设卡上显示「已召唤」，点它直接进那份员工的会话。
3. **翻卡召唤动画。** 游戏抽卡式：卡背（熊宝纹样）→ 光效聚拢、卡片轻颤 → 翻转露出员工的熊宝头像、名字、职务 → 光芒/粒子迸发 + 「召唤成功」→ 进入会话。约 2 秒，点击任意处可跳过；系统开了「减少动态效果」时直接显示结果卡，不播动画。
4. **预设员工配熊宝头像。** 包里每个预设员工（`examples/xiongbao/agents.yaml` 的 5 个和 `agents/` 目录下的 23 个）按职业从现有 50 张预设头像里各配一张，写在包里新的 `portrait:` 字段。待召唤卡片、召唤出来的那份员工都用这张。对应表随实现 PR 给用户过目。
5. **召唤来的员工从空开始，由用户自己装。** 复制出来的员工不带任何技能、插件；用户在这个员工的配置页（装配页）勾技能、装插件、选模型，只影响本人这一份。个人版「每个技能自动装给每个员工一次」的默认行为对召唤来的员工不生效。「能力 › 技能」页每张技能卡显示「已装到你的 N 个员工 / 未安装」。
6. **会话页顶部员工卡固定。** 员工一对一会话页的顶部固定一张紧凑卡片：头像、名字、职务一行、可见范围标签（如「仅自己」），消息怎么滚它都在。消息列表开头的大介绍卡保留不动（它是开场白）。

## 不做的

- 不把预设员工改成「人才市场」岗位模板（方案 B）。
- 不改插件的上架与安装流程，不改模型选择本身。
- 不改群组：多人会话照旧在「群组」里用「新建群组」建。
- 不动单机试用模式（`singleUser`）里包频道的按人副本：部署出去的多用户产品里，包频道本来就只有一份平台副本、不进任何人的会话列表；单机试用的行为留着，免得删掉已有会话。

## 绝不能出现的

- **老用户的东西被动了。** 已有的会话、聊天记录、员工身上已装的技能和插件一律保留；共用预设员工身上包装好的技能也不收回（老会话还在用）。
- 召唤失败却显示「召唤成功」，或者连点两下复制出两份。召唤要幂等：同一个人同一个预设只会有一份（数据库唯一约束兜底）。
- 动画卡住页面：超过约 3 秒、不能跳过，或者网络慢时动画放完了员工还没建好就跳进一个空页面。
- 套餐名额满了还能召唤：召唤和「复制员工」一样占名额，满了就提示升级，卡片退回待召唤。

## 方案

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（用户选定，2026-11-14 修订）** | 预设员工留在员工列表的「待召唤」；召唤 = 给本人复制一份员工 + 建一对一会话 + 动画 | 复用现有「复制员工」（`profile-store.ts` 的 `duplicate`）、建一对一会话（`ChannelStore.direct`）、安装（`plugin_grants`）；老用户不迁移；每人配置互不影响 |
| A 原版（已放弃） | 召唤只建会话，不复制 | 预设员工全系统共用、只有管理员能改，用户装不了技能，管理员一装所有人都变 |
| B | 预设员工改成岗位模板（ROLE1 `role_templates`），招聘时实例化 | 要把预设员工迁成模板，改动大，也不是用户说的「在员工列表召唤」 |

## 已定的做法（标「判断」的是我的判断，用户已整体确认）

- **记录「从哪个预设召唤来」**：员工资料表（`agent_profiles`）加一列 `summoned_from`（预设员工 id），加「同一主人 + 同一预设、未删除」唯一约束。「这个预设我召唤过没有」就查这一列。
- **预设头像存哪**：员工资料表再加一列 `preset_portrait`（预设头像键），包同步时从 `portrait:` 写进预设员工这一行，员工列表接口带出来；召唤时在本人名下给复制出来的员工写一行 `portraits`（预设）。不往平台租户写 `portraits`，免得行级权限不通。
- **召唤接口**：新加 `POST /api/agents/:agentId/summon`。对预设员工：已召唤过就返回已有那份；没有就复制（占名额、走和复制员工一样的检查）。对分身和本人自己的员工：不复制。最后都用 `direct` 找到或建一对一会话，返回 `{ agent, channelId, created }`。
- **熊宝小跟班也要召唤**（判断）：分身会话不再自动建（去掉 `GET /api/channels` 里调 `ensureAvatarConversation` 那一步），分身排在「待召唤」第一位。分身身上自带的「造员工、写技能」两项技能和招聘与组群工具照旧默认带着。
- **包技能授予不动**（判断）：包同步照旧给共用预设员工授予包技能（老会话靠它），复制出来的员工不继承任何授予，所以「召唤来的员工从空开始」自然成立，也不会触发重新部署时的收回逻辑。
- **会话删了以后**（判断）：一对一会话删了，员工本身还在「已召唤」里，点「进入会话」重新建一个会话（`direct` 不复用已删的）。员工本人删了，对应的预设退回「待召唤」，可以再召唤一份。
- **召唤出来的员工可见范围**：仅本人（复制员工本来就是 `private`）。顶部卡片的标签沿用介绍卡现有逻辑。
- **顶部固定卡放哪**：做进会话页现有的固定标题栏（`channel/$channelId.tsx` 里 `data-slot="conversation-header"`），带头像、名字、职务、标签，不另起一层。
- **头像对应表**（判断）：50 张够 28 个员工各配一张；对应表随实现 PR 给用户看，不阻塞实现。
