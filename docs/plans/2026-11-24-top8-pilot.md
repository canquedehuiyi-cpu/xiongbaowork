## 已知现实限制（报告里如实写）

- `model-e2e.yml` 的真实模型评测只能从 main 触发（`github.ref == 'refs/heads/main'`），试点分支不合 main 就**跑不了真实模型 A/B**。试点只能交付：代码 + 离线测试 + 模拟模式评测；真实模型对比需用户决定是否把「默认关」的开关合入 main 后再跑。
- 本机网络只放行少数主机：Firecrawl 对比只能用本机起的测试页（静态页、JS 渲染页、长文、表格），不能抓真实互联网页面。
- open-code-review 的 native 模式需要模型 key，本机没有；改用 delegation 模式（宿主智能体用自己的模型执行，OCR 负责文件选择、规则、覆盖与结构化报告），宿主由控制方派出的子智能体担任。

## 试点 1：open-code-review —— PR 预审（只出报告）

- 产物：
  - `.github/workflows/ocr-review.yml`（仓库根）：只在 `workflow_dispatch` 与带标签 `ocr-review` 的 PR 上跑，`continue-on-error: true`，只上传报告 artifact，不评论、不拦合并、不碰合并按钮；模型 key 取 Environment secret（同 model-e2e 的写法），缺 key 时跳过并写原因。actions 按仓库惯例钉完整 commit SHA。
  - `xiongbao/scripts/review/ocr/`：运行脚本（安装固定版本 `@alibaba-group/open-code-review`，调用 `ocr review --from <base> --to <head> --format json`）、规则模板（熊宝的审查重点：越权/RLS/租户帧、注入、路径穿越、审批绕过、品牌词、断言改动）。
  - 评测集：`xiongbao/scripts/review/ocr/benchmark/`：取 #804–#810、#812 这几个 PR 的 diff，以及控制方审查报告里已确认的 Critical/Important（文件:行 + 一句话）作为金标（报告在 `.superpowers/sdd/2026-11-23-deliverables-ready/*review*.md`）。写一个打分脚本：给定 OCR 的 JSON 报告，按文件 + 行区间（±10 行）+ 主题匹配算召回/精度。
  - 实测：本机用 delegation 模式（`ocr delegate`）在至少 3 个历史 PR 上跑出报告，用打分脚本算召回与精度，写进报告；漏报逐条列出。
- 验证：打分脚本单测；工作流 YAML 能解析、有 workflow 结构测试（照 `server/tests/model-e2e-workflow.test.ts` 的写法：不出现 pull_request_target、密钥只经 Environment、不能写评论、`permissions: contents: read`）。

## 试点 4：superpowers 缩小版 —— 计划须批准 + 交付前评审（单员工）

- 产物（开关 `XIONGBAO_PILOT_PLAN_APPROVAL`，默认关；只对工作手册里声明了试点的员工生效）：
  - 长任务（看板卡或单聊中员工第一次调用 `update_plan` 且计划 ≥ 4 步）时，计划作为一条「需要批准」的事项进审批箱（复用 ask_person / 审批服务的现有机制，不新造通道），批准前不执行有副作用的工具；批准/修改意见作为下一轮回到会话。
  - 编码类卡片交付前：派一个只读子代理按固定清单（测试是否跑过、改动是否超出卡片范围、有无删除既有断言）评审，结论附在交付里；评审只出意见，不挡交付（第一版）。
  - 试点员工的工作手册模板（ROLE1 的 handbook）：熊宝版流程，按任务类型分：编码（计划→实现→验证→评审→交付）、调研（来源清单→交叉核对→结论带出处）、回消息（确认意图→起草→发送前过审批）、做报表（数据来源→口径确认→校验合计→交付文件）。写成工作手册文本，不进全局提示。
- 验证：开关关时提示与行为不变（prompt-budget 测试不动）；计划须批准的服务器测试（批准前副作用工具被挡、批准后继续、驳回带意见回到会话）；评审子代理清单测试。
