## 0. 一页纸摘要

**目标**：交付一个**能对外发布的单租户/多租户私有化部署包 v0.1**——从干净克隆构建出的镜像，打开就是"熊宝数字员工"，接上一家真实模型能完成对话，任务看板每张卡都点得开，`bun run test` 与 GitHub CI 都是绿的。

**不在 v0.1 里**：对标原版的插件/技能市场、知识库创建、WakerFlow、桌面客户端、IM 接入、Credits 计量。它们列在阶段 5，等你拍板范围（§2 决策 D-6）。

## 3. 贯穿全程的工作约定

1. **分支与提交**：每个工作包一个分支 `fix/<wp-id>-<slug>` 或 `feat/…`，一个 PR；PR 描述写"问题 → 改动 → 证据"。一张屏的文案改动与它的测试**同一个提交**。
2. **测试怎么跑**（沿用 `docs/deployment-qoderwake.md` §5/§5b，不要在 Windows 宿主直接跑 server 测试）：
   - server：`run-shards.sh` 同法，**用独立库**（例如 `openbot_wp12`），不要碰共享的 `openbot` / `openbot_test`，以免和其他会话互相踩。
   - app：容器内 `bun run --cwd .. generate:app-config && bun test`。
   - lint：`biome lint --error-on-warnings .`（全仓）；`biome check --write` 只对改动文件。
3. **判回归比"失败名字多重集"，不比总数**。阶段 0 的基线名单就是比对对象。
4. **不写共享栈**：3010 那套 G2 栈是别的会话在用的；验证一律起自己的一次性容器（审计用过的 `docker run --env-file … openbot:<tag>` 配方，见附录 B），用完删掉。
5. **证据先于结论**：每个工作包的"验收"一栏，没有贴出命令输出或截图就不算完成。
6. **并发提醒（已解除）**：另一会话在主检出改的 `wakers.tsx`（解散二次确认）已作为 `ddfd4e4` 合入 main 并在活体上验过，WP-2.3 可直接开工。仍要求所有工作走分支与 PR。
7. **Windows 宿主不是交付路径**：`scripts/start.sh` 用宿主进程起 API，而 Windows 原生 bun 跑 server 的模块链会在 import 期挂死（不写一行日志）。交付与验收一律走镜像（附录 B）或 Linux/WSL；`docs/deployment-qoderwake.md` 与 README 必须把这条写明，不要留"照做跑不通"的坑。
8. **CI 里别放 `scripts/check-new-values-keys.ts`**：它按仓库根拼 chart 路径（`charts/openbot/...`），而本 fork 的 chart 在 `openbot/` 子目录下，本地与根工作流调用必挂。要么先改成相对本仓路径，要么在 WP-0.2 的四个 job 里明确不调它。

### 阶段 0：基线与护栏（1 天）

#### WP-0.1 冻结红灯基线 · 0.25 天

- 审计当天的数字可作为预期：server 4145 pass / 19 fail（14 个唯一名字），app 1062 / 52（逐文件单跑后 6 个文件 20 条）。
- **验收**：两个名单文件入库；后续每个 PR 的描述里附"与基线的差集"。

#### WP-0.2 让 CI 真的跑起来（N6）· 0.5 天
- **根因**：仓库根目录没有 `.github/`，上游的 6 个工作流嵌在 `openbot/.github/workflows/` 下，GitHub 只认根目录，所以 fork 上一次运行记录都没有。
- **做法**：新建根目录 `.github/workflows/ci.yml`，`defaults.run.working-directory: openbot`。**不要整份照搬上游 660 行的 `ci.yml`**（mobile、chart、python-harness、desktop 这些 job 与本产品无关，且上游测试用超级用户连库，会让 RLS 测试失真）。首版只要四个 job：
  1. `static`：`bun install --frozen-lockfile` → lint → typecheck（app 走 `bun run typecheck`，带 `pretypecheck`）。
  2. `server-test`：`services.postgres`（pgvector/pg17），先以 owner 跑迁移，再以 `openbot_app` 跑测试；`strategy.matrix.shard: [1..6]`，每片一个进程（与 `run-shards.sh` 同口径，避免连接槽耗尽）。
  3. `app-test`：`cd app && bun run --cwd .. generate:app-config && bun test`（Linux runner 上没有 Windows 宿主的 import 挂死问题，不必进容器）。
  4. `image`：`docker build`，起容器，断言 `/health` 200、`/api/capabilities` 可读（阶段 1 之后再加品牌与 RLS 断言）。
- 阶段 0 允许 `server-test` / `app-test` 是红的（`continue-on-error: true` 并在 job 摘要里列出与基线的差集）；**阶段 3 结束时去掉 `continue-on-error`**。
- `openbot/.github/` 保留不动（方便以后同步上游），在根 `ci.yml` 顶部注释写明"上游工作流不在本仓执行"。
- **验收**：Actions 页能看到对 `main` 的一次运行，四个 job 都执行了。

#### WP-0.3 纠正本机配置（审计 N3 的配置一半）· 0.25 天，**由你或运维执行**
- 主检出的 `openbot/.env` 里 `OPENAI_MODEL=deepseek-chat` **全仓没有任何代码读它**。改为 `BOT_MODEL=<供应商支持的模型名>`（DeepSeek 在审计当天返回的可用名是 `deepseek-flash`、`deepseek-v4-pro`）。`BOT_MODEL` 只在设置了 `OPENAI_BASE_URL` 时生效（`server/src/copilot.ts:227-235`），你的 `.env` 已经设了。
- 改完要重启读这个 `.env` 的 server 进程才生效（3010 的 G2 栈 server 是 33 小时前起的，所以它报的是"未配置凭据"）。重启共享栈前先和在用它的会话打招呼。
- **更正一条此前说错的话**：本会话早前对"往 `.env` 写 `OPENAI_MODEL` 后，意外调用也会走你选的 provider"的说法只对一半——`OPENAI_BASE_URL` 生效，**模型名不生效**（全仓无人读 `OPENAI_MODEL`，只有 `BOT_MODEL`）。该说法以审计 N3 为准。

### 阶段 1：P0 阻断项（6.5 天）

#### WP-1.1 任务卡"打开"死链（N1）· 1 天 · 依赖 WP-0.1
- **问题**：看板上对话来源的卡把**线程 id** 存进 `channelRef`（`server/src/threads/postgres-runner.ts:141`），交接卡同样存线程 id（`agents/handoff-delivery.ts:405`），而看板按**频道 id** 拼 `/channel/$channelId`（`app/src/routes/_authed/_app/tasks.tsx:224-228`）。审计时 15 张卡的"打开"全部 404。
- **方案：读时解析，不改写入**。理由：解析在读侧做，历史卡片不需要数据迁移就能一起修好；写入侧的四种来源（例行写频道 id、群聊写频道 id、对话与交接写线程 id、流水线不写）保持原样。
  1. 在 `server/src/tasks/routes.ts` 加一个与 `modelsForRuns` 同形的批量函数 `openTargetsFor(database, rows)`，一次查询解出每张卡的落点：
     - `channelRef` 本身就是 `channels.id` → 该频道；
     - 否则查 `intelligence_channel_mappings.thread_id`（1:1 对话）与 `group_bot_threads.thread_id`（群聊里某员工的线程）→ 对应频道；
     - `source = 'group_run'` → `{ kind: "pipeline", runId }`（父卡用自己的 `runRef`，步骤卡沿 `parentTaskId` 找父卡的 `runRef`）；
     - 都找不到 → `null`。
     - 频道类型用**侧栏同一判据**：参与员工 > 1 走 `/group/`，否则 `/channel/`（`app/src/components/app-sidebar/channel.tsx:112-117`）。
  2. 列表响应每张卡多一个 `open: { kind: "channel" | "group" | "pipeline"; id: string } | null`。
  3. `tasks.tsx` 按 `open` 渲染链接；`null` 时不渲染"打开"，改为一行灰字"对话已不在"。
  4. `pipelines.tsx` 现在把选中的运行放在组件 state（第 76 行），没有深链。加 `validateSearch({ run?: string })`，`/pipelines?run=<id>` 直接打开那次运行的面板。

#### WP-1.2 无人值守的一轮重复开卡、重复计额度（N10，新发现）· 1.5 天 · 依赖 WP-0.1，**且必须先于 WP-1.3 的 DoD-4 冒烟断言**
- **问题（疑似，代码与数据双指向，第一步先用测试钉死）**：
  - 所有无人值守的一轮——例行、职责、流水线步骤、审批续跑、主动巡检、唤醒——都走同一个 `routineAgentRunner = localThreadRunner`（`server/src/index.ts:1846`），而 `PostgresAgentRunner.stream()` 对**每一轮无条件开一张 `source: "chat"` 的卡**（`postgres-runner.ts:131-145`）。
  - 与此同时，业务层自己也开卡：例行 `routines/runner.ts:243`（`source: "routine"`）、流水线步骤 `pipeline/store.ts:535`（`group_run`）、职责 `responsibilities/engine.ts:158`。交接走 `copilotRuntime.threadRunner()`（`index.ts:2938`），同形，待测试确认。
  - `projector.opened` 是纯 INSERT 且每次都 `quota.recordTask`（`tasks/projector.ts:119-132`），所以**每次无人值守的工作在看板上两张卡、月度任务额度扣两次**（Free 档 50 次/月实际只够 25 次）。
  - 数据旁证：共享库里那 11 张标题为 "One of your routines is firing right now…"、`channelRef = group-run-…` 的 `chat` 卡，正是流水线步骤那一轮在 runner 里被多开的那一张。
- **方案**：
  1. **先写失败测试**（`tests/unattended-single-card.integration.test.ts`）：用真实 `PostgresAgentRunner` + 真实投影器跑一次例行触发与一次流水线步骤，断言每次只有一张卡、`usage_counters` 只 +1。预期当前为红。
  2. 修法：无人值守的入口已经知道"这一轮由谁记账"。在 `createTurnRunner` 发往 runner 的请求上带一个标记（例如 `forwardedProps.boardOwned = true`，或 runner 侧的 `AsyncLocalStorage` 作用域），`PostgresAgentRunner.stream()` 见到标记就**不开卡、不计额度**，只做持久化；由业务层那张卡负责 `finished`。额度检查（`run()` 里的 `assertCapacity`）对带标记的请求同样跳过——业务层在开工前已经问过一次（`routines/runner.ts:221-230`）。
