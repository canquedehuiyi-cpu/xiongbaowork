# 2026-11-24 Firecrawl 抓取质量对比（试点 6，只出报告）

## 结论

- 在 6 个本机测试页上，Firecrawl Local 比熊宝现有的 web_fetch 多做成两件事：**脚本渲染页**（熊宝只拿到「正在加载」，Firecrawl 正文召回 1、事实全到）和 **PDF**（熊宝按设计只描述不返回正文，Firecrawl 正文与 12 行表格全部读到）。
- 静态文章与 80 行长表格上，两边正文召回都是 1、表格单元格与行保真都是 1，没有差别。
- 两个噪声页上，两边正文召回都是 1，但**熊宝更干净**：带语义标签的页噪声率熊宝 0、Firecrawl 0.3（留下了「猜你喜欢」相关链接列表）；全是 div、没有语义标签的页熊宝 0.2、Firecrawl 0.8（促销条、广告块、订阅框、Cookie 条、相关链接、分享条基本都留下了）。
- 耗时：不起浏览器的页，熊宝在进程内 3–23 毫秒，Firecrawl 每次是一次进程启动，8–25 毫秒（长表格上 Firecrawl 更快，其余页熊宝更快）；脚本渲染页 Firecrawl 约 1.1 秒（拉起本机 Chrome）。两者口径不同，只作量级参考。
- 对熊宝的实际帮助：补的是 PDF 和脚本渲染这两个空白，不是正文抽取质量。熊宝已经有 Crawl4AI 渲染接入（本机没有该服务，这次没法对比）。**本报告不建议把 Firecrawl 接入默认链路**；如果要补 PDF/脚本页，可作为可选的外部 sidecar 再单独评估（见「接入方式与 AGPL」）。这是基于 6 个合成页、一台机器的结论，不代表真实互联网页面上的表现。

## 方法

- 工具：
  - 熊宝：直接调用 `server/src/web/` 的导出函数，顺序是 `fetchPublicPage` -> `pageKind` -> `decodeBody` -> `extractReadable`。`web_fetch` 里做这些的 `describePage` 没导出，所以按同样顺序重做这四步，不含最后的字数截断。不经模型、不经员工工具调用。
  - Firecrawl Local：`firecrawl-local scrape <url> --markdown`，外部二进制，不改源码。
- 测试页：全部在本机 127.0.0.1 起（bun 静态服务器，端口由系统分配），页面确定生成。共 6 页：静态文章、脚本渲染页（正文只在脚本数据里，150 毫秒后才写进页面）、80 行 x 5 列长表格、带导航/广告/Cookie 条/页脚的噪声页、同内容但全是 div 的噪声页、PDF（用本机 LibreOffice 从 HTML 生成，含 4 段正文和 12 行表格）。
- 标准答案：每页的正文段落、关键事实（日期、编号、数字）、表格单元格、噪声词，写在 `pages.ts` 里，先于任何输出。单测校验这些答案确实写在各页源码里。
- 评分（`score.ts`，脚本计算，不靠肉眼）：比较前两边都只留汉字、字母、数字。
  - 正文召回：标准段落里连续 6 个字符的片段，出现在输出里的比例。
  - 事实召回：关键事实原样出现的比例。
  - 噪声率：噪声词句出现在输出里的比例，越低越好；没有噪声词的页不适用。
  - 单元格召回：表格单元格出现的比例。行保真：一行的全部单元格按列顺序出现在输出的同一行文字里才算保住，输出把表格拆成一格一行时这一项会掉。
  - 脚本页是否拿到正文：正文召回至少 0.8 且事实全到。
- 耗时：每页每工具先跑 1 次预热不计时，再计时 5 次，取中位数，括号里是最小到最大。
- 网络隔离：整个对比在只有回环网卡的网络命名空间里运行（`isolated.sh`），外网一律不通。设了 `FIRECRAWL_CLOUD=off`，没有任何 key，脚本拒绝非 127.0.0.1 的地址。这一步的原因见「跑的时候发现的事」。
- 熊宝一侧的一个差别：`fetchPublicPage` 有 SSRF 防护，直接拒绝 127.0.0.1，也没有放行开关。照 `server/tests/web-tools.test.ts` 的做法，地址写成 `pilot.test`，解析器注入一个公网地址，再注入 `fetchImpl` 把请求改道到本机端口。校验、重定向、字节上限、请求头都是真实代码在走，差别只是连的是本机端口。

## Firecrawl Local 的来源、许可证与安装

- crates.io 上存在 `firecrawl-local`，版本 0.1.1（2026-11-19 发布，共 2 个版本），仓库字段 `https://github.com/firecrawl/firecrawl`，主页 firecrawl.dev，所有者是 mogery 与 ericciarla（Firecrawl 团队成员账号），源码包 128 KB。**许可证 AGPL-3.0**；包里只有 `src`、`build.rs`、`README.md`，没有单独的 LICENSE 文件。我没有逐行审计源码，只读了 README、`Cargo.toml` 和与云端相关的配置代码。
- 安装：`cargo install firecrawl-local --version 0.1.1 --locked`，目标目录放在会话临时目录。387 个依赖，release 构建（fat LTO）5 分 49 秒，构建目录约 1.0 GB，二进制 23.9 MB，sha256 `ee425d0fb364a154d364e835ca1f191f7dfc571ca2cdfa96743404951c495ea3`。构建成功，没有 Docker，没有云 key。
- 关闭云端的真实方式：环境变量 `FIRECRAWL_CLOUD=off`（取值 `auto` 默认、`search`、`off`；不认识的值也按 off）。README 的说明：默认 `auto` 时，搜索、本机取不到的页面会回落 Firecrawl 云端，所以必须设 off。

读输出时看到、分数里体现不出来的几点：

- 噪声（带语义标签页）：Firecrawl 把页尾「猜你喜欢」整块相关链接（带完整地址的 Markdown 链接）当作正文留下，熊宝没有；导航、广告、Cookie 条、页脚两边都去掉了。
- 噪声（全 div 页）：熊宝只留下了「分享到 微信 微博 复制链接」一行和「猜你喜欢」标题；Firecrawl 留下了 10 条噪声词句里的 8 条。
- 静态页上唯一的差别：Firecrawl 保留了署名行（「调度中心新闻办 · 2026 年 3 月 12 日」），熊宝的 Readability 把它当元信息去掉了。这一行不在标准答案里，不影响分数。

## 跑的时候发现的事

- **Firecrawl 渲染脚本页时，被拉起的 Chrome 会自己联网。** 在没有隔离的网络里，用 strace 观察到渲染脚本页那次运行有对 8.8.8.8:53 的 DNS 查询，以及对解析到 google.com、googleapis.com 的地址的 443 连接；只抓静态页（不起 Chrome）时没有任何非回环连接；单独起同一个 Chromium 打开同一个本机页时只有 DNS 查询。我没有进一步归因是 Firecrawl 给 Chrome 的启动参数造成，还是 Chrome 自身的后台请求；抓取内容本身只是本机合成页，没有真实数据可发。但这说明「FIRECRAWL_CLOUD=off」只管 Firecrawl 自己的云端回落，管不到 Chrome 的联网。因此后面的正式运行都放进只有回环网卡的网络命名空间（`isolated.sh`），再用 strace 记录：外连尝试全部是 DNS（8.8.8.8、8.8.4.4）且全部返回 ENETUNREACH，渲染脚本页照常成功。**排查阶段有两三次未隔离的运行，期间 Chrome 的上述后台连接确实发生过。**
- 同步等待 Firecrawl 子进程会把同进程里的测试页服务器一起堵死（第一版脚本就是这样超时的），所以改成异步起进程。这只是脚本问题，不影响结果。

## 没做、跑不通、不能下结论的部分

- **熊宝的脚本渲染路径没测。** 熊宝让脚本页变成可读正文要走 Crawl4AI 服务（`crawl4ai.ts` 的 `render_js`），本机没有这个服务，也没有 Docker 守护进程来起它。所以「熊宝加 Crawl4AI 之后与 Firecrawl 在脚本页上谁更好」没有数据；表里熊宝的脚本页成绩只代表不渲染的那条路。
- **没测 crawl/map、搜索、云端回落、Alexandria 数据源。** 本次只测 `scrape`。云端部分按用户要求不碰。
- **没抓任何真实互联网页面。** 联网抓取属于对外动作，要先过审批，本次也没有放行的主机；所以反爬、跨站编码（GBK 等）、超大页、登录态、动态加载更复杂的站点都没覆盖。
- **测试页偏简单。** 合成页和标准答案都是我写的，除脚本页和 PDF 外正文召回几乎都是 1，说明这些页在正文完整度上分不出差别，不是说两边在真实页面上一样好；噪声页只有两个，噪声词句是我挑的。
- 耗时只在一台机器上测，Firecrawl 一侧含进程启动，熊宝一侧是进程内调用。
- 没有审计 Firecrawl 源码，没有测内存占用，没有测并发。

## 接入方式与 AGPL 影响（不是法律意见，接入前需要法务确认）

- 接入方式的两种可能：
  1. 外部二进制或 sidecar：`firecrawl-local serve` 在本机回环端口提供 Firecrawl v2 API，熊宝通过 HTTP 调用。不改源码，不进 `package.json`，与熊宝代码在不同进程。
  2. 让现有 Crawl4AI 路径补上 PDF 解析，而不引入 Firecrawl。这次对比里 Firecrawl 的价值主要在 PDF 与脚本渲染，两者都有别的补法。
- AGPL-3.0 要点：它的网络条款（第 13 条）针对「修改过的版本」让网络上的用户拿到对应源码；我们不改源码、只当独立外部进程通过 HTTP 调用，不把它的代码链接进熊宝，常见理解是不会让熊宝自己的代码受 AGPL 约束。但如果要把这个二进制或含它的镜像随熊宝一起分发给客户，就要遵守分发时附许可证文本与源码获取方式的义务（这个 crate 包里没有单独的 LICENSE 文件，需要从上游仓库补）。一旦将来要改它的源码（比如去掉联网行为），就进入「修改版」的范围，义务会明显变重。
- 接入前还要对齐的事：`serve` 默认拒绝回环和内网地址，要抓内网需要 `--allow-private`，这与熊宝的 SSRF 策略要一致；渲染脚本页要本机有 Chrome，上面看到 Chrome 会自己联网，部署时需要出口控制；Firecrawl 的取数不经过熊宝的 `fetchPublicPage`，熊宝现有的逐跳 SSRF 校验、字节上限、爬虫身份（User-Agent、robots）需要在 sidecar 前面重新保证。
- 对外联网始终按用户的要求过审批、不无限制爬；这次对比没有对外联网。
