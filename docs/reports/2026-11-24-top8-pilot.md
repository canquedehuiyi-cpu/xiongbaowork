## 试点 1：open-code-review —— PR 预审（只出报告）

### 试点范围

- 给熊宝加一条只出报告的 PR 预审：用 [open-code-review](https://github.com/alibaba/open-code-review)（Apache-2.0，固定 1.14.2，下称 OCR）对一段提交范围做评审，报告作为 artifact 留存。
- 不评论、不批准、不打标签、不碰合并按钮；失败不影响 PR 检查。默认关：只有手动触发，或给**本仓库**里的 PR 打标签 `ocr-review` 才会跑；fork 来的 PR 不跑。没有产品运行时代码改动，所以没有 `XIONGBAO_PILOT_*` 开关，开关就是这个标签加 Environment `ocr-review` 里的 secret。
- 用历史审查结论做评测集（#807 第 5 期、#810、#812 三个 PR，修复前被审查的版本），用打分脚本算召回与精度。
- 本机没有模型 key，native 模式跑不了，评测走 delegation 模式：OCR 负责文件选择、规则解析、覆盖要求，评审由控制方派出的评审子智能体做。所以测到的是「OCR 的确定性工程 + 宿主模型」，OCR 自己的评审单元隔离、反思、定位模块没有跑。

### 怎么跑通

- 开法：建 GitHub Environment `ocr-review`（建议设必需审阅者），加 secret `OCR_API_KEY`，可选 variable `OCR_PROVIDER`（默认 deepseek）、`OCR_MODEL`（默认 deepseek-v4-flash）、`OCR_TOKEN_BUDGET`（默认 1500000）；然后手动触发或给 PR 打 `ocr-review` 标签。缺 key 时运行成功，artifact 里是 `skipped.json` 和 `SKIPPED.txt`，写明原因。
- 本机实测到的：`npm install @alibaba-group/open-code-review@1.14.2 --ignore-scripts` 能装（63MB，平台二进制来自包自带的可选依赖），`ocr --version` 正常；用假 key 跑 `run-review.sh`，真二进制接受了全部参数，进入评审阶段（`files_reviewed: 5`），在调模型时失败（没有可用的 key 与出口），脚本照常退出 0 并留下报告与日志，key 不在任何产出里。
- 官网文档（open-codereview.ai）本机访问不了（代理 403），规则文件格式、delegation 流程取自仓库里的 README、`skills/*/SKILL.md` 与 `pages/src/content/docs/en/review-rules.md`（raw.githubusercontent.com 可访问）。

**评测（三个 PR，OCR delegation 模式，盲审）**

评审由一个**没读过金标**的子智能体做：只给它规则文件、`delegate-pack.ts` 打出的材料和 `git show <to>:<path>`，明确禁止打开 `benchmark/`、`docs/reports/`、`.superpowers/` 和任何审查报告，也不看三个范围之后的提交；它交回报告时自述没有越界。测试文件用 `--exclude '**/tests/**,**/*.test.*'` 排除。

精度 = 命中任何一条金标（含 Minor）的评论占比；严格精度只算命中 Critical/Important 的评论。打分规则：同文件、行区间 ±10 行、主题关键词交叉。结果文件在 `xiongbao/scripts/review/ocr/benchmark/results/`。

先做的一轮评审者读过金标，测出召回 9/9、精度 21/24，**作废**，原始文件留在 `results/upper-bound/` 只作对照，不作结论。那一轮另做过两组对照证明打分脚本有区分力：评论行号整体平移 200 行，召回降到 1/9；评论文字换成无关句子，召回 0/9。

其余未命中的：`artifact-access-store.ts` 只交程序没文件时 run 范围返回 null、`artifact-preview.tsx` iframe 同源脚本、`evidence-gate.ts` 程序串行探测最坏阻塞 5 分钟、`delivery-tools.ts` 把 ref 改成可选、#810 `chat-server-tools.ts` 清单流的 personId、#812 评测把 RUN_ERROR 原文写进失败详情——有的是已接受的设计（iframe 同源是用户决定），有的值得再看，没有逐条核实。

**结论**：盲审下 Critical/Important 召回约一半（5/9），漏的 4 条里 3 条集中在第 5 期转发这一块最长、最复杂的 diff；严格精度 28%，意味着每 4 条评论里约 1 条是已确认的重要问题，另有几条是人工审查也漏掉的真问题。它适合当「多一双眼睛」的只出报告预审，不能代替人工审查，更不能用来拦合并——和计划定的用法一致。这是 delegation 模式、宿主为 sonnet 子智能体的数字，不是 OCR native 模式的数字。

OCR 自己的确定性部分观察到的：测试文件被内置排除规则挡掉（`**/*.test.*`、`**/tests/**`、`**/fixtures/**` 等），要读测试必须在规则里写 `include`，规则模板里写了；评测时再用 `--exclude` 排除测试，控制工作量。评测之后规则模板里的品牌词条目改过一次写法（避免品牌扫描命中字面旧名），金标里没有品牌词条目，结果不受影响。系统内置的 TS 规则偏前端（React hooks 等），后端代码用熊宝规则整个替换它，前端与工作流用 `merge_system_rule` 叠加。

### 没做完什么

- native 模式真跑：没有模型 key。工作流从没在 GitHub 上跑过（不推送、不合 main），只做了离线验证：YAML 解析与结构测试、运行脚本用桩 `ocr` 的流程测试、真二进制加假 key 的冒烟。第一次真跑需要用户建 Environment、加 secret、手动触发。
- 真实召回率：需要用户在配好 key 的 Environment 里对三个 PR 的范围手动触发（范围见 `gold.json` 的 `range`），再用 `score.ts` 打分。native 报告里评论字段的确切形状本机没跑出来（假 key 下 `comments` 为 null），打分脚本按常见字段别名做了容错，没核实。
- `delegate-pack.ts`、`delegate-report.ts` 的命令行入口没有单测（核心逻辑在 `delegate-lib.ts`，有单测；打包脚本用真二进制手动跑过）。
- 没有把打分接进工作流；没有做 OCR 的 `scan`（全量扫描）和 session 续跑。

### 风险

- **代码外发**：native 模式会把 PR 的 diff 与相关文件内容发给模型提供方（默认 deepseek）。默认关、只在标签或手动触发时跑、只用 Environment 里的 key，但一旦开了，代码就离开本仓库。只在用户确认可以外发的仓库和范围上开。
- **标签 PR 跑的是它自己合并提交里的脚本**：有写权限的人可以在 PR 里改脚本把 key 发走。所以文档建议给 Environment `ocr-review` 设必需审阅者；不用 `pull_request_target`，fork PR 一律不跑。
- **成本**：`--max-tokens-budget` 默认 1,500,000，是一次评审的上限；真实花费取决于范围大小，没有实测。
- **打分宽松**：匹配靠 ±10 行加关键词，宽范围的金标（如 `forward.ts:365-421`）容易命中，锚在定义处还是调用处、代码还是文档会导致真发现被算成未命中。样本只有 3 个 PR、9 条 Critical/Important，数字的置信区间很宽。
- **召回有意取舍**：OCR 的 README 说明召回率低于通用智能体，页面没给数字；盲审 5/9 与这一说法相符，但测的是 delegation 模式。
- **版本**：固定 1.14.2，升级要手工改 `run-review.sh` 的一处；平台二进制来自 npm 可选依赖，没有额外做校验和核对。
