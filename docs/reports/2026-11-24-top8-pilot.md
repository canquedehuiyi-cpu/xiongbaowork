## 试点 1：open-code-review —— PR 预审（只出报告）

### 试点范围

- 给熊宝加一条只出报告的 PR 预审：用 [open-code-review](https://github.com/alibaba/open-code-review)（Apache-2.0，固定 1.14.2，下称 OCR）对一段提交范围做评审，报告作为 artifact 留存。
- 不评论、不批准、不打标签、不碰合并按钮；失败不影响 PR 检查。默认关：只有**手动触发，并且只能从 `main` 触发**（写法同 `model-e2e.yml`），没有 `pull_request`、标签或定时触发；审查范围由输入 `base`/`head` 指定，脚本与规则来自 main 的检出，被审分支的内容只作为 git 对象被读取。没有产品运行时代码改动，所以没有 `XIONGBAO_PILOT_*` 开关，开关就是手动触发加 Environment `ocr-review` 里的 secret 与必需审阅者（已在 `xiongbao/docs/configuration.md` 的「试点开关」一节写明）。
- 用历史审查结论做评测集（#807 第 5 期、#810、#812 三个 PR，修复前被审查的版本），用打分脚本算召回与精度。
- 本机没有模型 key，native 模式跑不了，评测走 delegation 模式：OCR 负责文件选择、规则解析、覆盖要求，评审由控制方派出的评审子智能体做。所以测到的是「OCR 的确定性工程 + 宿主模型」，OCR 自己的评审单元隔离、反思、定位模块没有跑。

### 怎么跑通

- 开法：建 GitHub Environment `ocr-review`，**必须设必需审阅者（开通前提，不是建议）**，部署分支限定为 `main`，再加 secret `OCR_API_KEY`、variable `OCR_PROVIDER`（**必须设，没有默认**，它决定代码发给谁）、可选 `OCR_MODEL`（默认 deepseek-v4-flash）、`OCR_TOKEN_BUDGET`（默认 1500000）；然后在 Actions 里选分支 `main` 手动触发，填 `base`、`head`（本仓库里的分支名或提交；fork 来的 PR 审不了）。缺 key 或没设 `OCR_PROVIDER` 时运行成功，artifact 里是 `skipped.json` 和 `SKIPPED.txt`，写明原因。不要把它设为必需检查。
- 没有提供 `pull/<n>/head` 输入：checkout 带的是 `persist-credentials: false`，之后再 fetch PR 的 ref 要凭据，而把凭据留给带 key 的步骤不值得；要审一个 PR，填它的分支名即可。
- 本机实测到的：`npm install @alibaba-group/open-code-review@1.14.2 --ignore-scripts` 能装（63MB，平台二进制来自包自带的可选依赖），`ocr --version` 正常；用假 key 跑 `run-review.sh`，真二进制接受了全部参数，进入评审阶段（`files_reviewed: 5`），在调模型时失败（没有可用的 key 与出口），脚本照常退出 0 并留下报告与日志，key 不在任何产出里。
- 官网文档（open-codereview.ai）本机访问不了（代理 403），规则文件格式、delegation 流程取自仓库里的 README、`skills/*/SKILL.md` 与 `pages/src/content/docs/en/review-rules.md`（raw.githubusercontent.com 可访问）。

OCR 自己的确定性部分观察到的：测试文件被内置排除规则挡掉（`**/*.test.*`、`**/tests/**`、`**/fixtures/**` 等），要读测试必须在规则里写 `include`，规则模板里写了；评测时再用 `--exclude` 排除测试，控制工作量。评测之后规则模板里的品牌词条目改过一次写法（避免品牌扫描命中字面旧名），金标里没有品牌词条目，结果不受影响。系统内置的 TS 规则偏前端（React hooks 等），后端代码用熊宝规则整个替换它，前端与工作流用 `merge_system_rule` 叠加。

### 没做完什么

- native 模式真跑：没有模型 key。工作流从没在 GitHub 上跑过（不推送、不合 main），只做了离线验证：YAML 解析与结构测试、运行脚本用桩 `ocr` 的流程测试、真二进制加假 key 的冒烟。第一次真跑需要用户建 Environment（设必需审阅者）、加 secret 与 `OCR_PROVIDER`、在 main 上手动触发；而且工作流文件要先进 main，`workflow_dispatch` 才能选 main。
- 真实召回率：需要用户在配好 key 的 Environment 里对三个 PR 的范围手动触发（范围见 `gold.json` 的 `range`），再用 `score.ts` 打分。native 报告里评论字段的确切形状本机没跑出来（假 key 下 `comments` 为 null），打分脚本按常见字段别名做了容错，没核实。
- `delegate-pack.ts`、`delegate-report.ts` 的命令行入口没有单测（核心逻辑在 `delegate-lib.ts`，有单测；打包脚本用真二进制手动跑过）。
- 没有把打分接进工作流；没有做 OCR 的 `scan`（全量扫描）和 session 续跑。

### 风险

- **代码外发**：native 模式会把 PR 的 diff 与相关文件内容发给模型提供方（由 `OCR_PROVIDER` 指定，没有默认，没设就不跑）。默认关、只在 main 上手动触发时跑、需要 Environment 必需审阅者批准、只用 Environment 里的 key，但一旦开了，代码就离开本仓库。只在用户确认可以外发的仓库和范围上开。
- **谁的脚本拿到 key**：只有 main 上的工作流文件与脚本（job 限定 `github.ref == 'refs/heads/main'`，没有 `pull_request`/标签触发），PR 分支里改过的脚本拿不到 key；Environment `ocr-review` 的必需审阅者是**开通前提**，结构测试挡住了去掉这道限定、加外发命令、多出触发器这几种改动。被审的范围只作为 git 对象被 `ocr review` 读取，`ocr` 读取它们时的内部行为没有逐项核实。
- **key 在命令行上**：`ocr config set providers.<名>.api_key <key>` 运行期间 key 出现在进程参数里（单租户 runner，日志里 GitHub 会遮掩，artifact 里按原文删文件有测试）；`npm install` 那一步已去掉 key。`ocr` 二进制里有 `OCR_LLM_TOKEN` 之类的环境变量名，能否改用环境变量传 key 没有核实。遥测：二进制里有 `OCR_ENABLE_TELEMETRY`，语义与默认值没核实，脚本显式设为 0 以防默认开。
- **成本**：`--max-tokens-budget` 默认 1,500,000，是一次评审的上限；真实花费取决于范围大小，没有实测。
- **打分是机械匹配**：一对一分配与收窄后的关键词去掉了旧版的重复记功，但匹配仍靠 ±10 行加关键词，宽范围的金标（如 `forward.ts:365-421`）容易命中，锚在定义处还是调用处、代码还是文档会导致真发现被算成未命中，「部分命中」不计分。要看人工核对列。样本只有 3 个 PR、9 条 Critical/Important，数字的置信区间很宽。
- **召回有意取舍**：OCR 的 README 说明召回率低于通用智能体，页面没给数字；规则受污染的盲审里人工核对的 2/9 到 4/9 与这一说法相符，但测的是 delegation 模式。
- **版本**：固定 1.14.2，升级要手工改 `run-review.sh` 的一处；平台二进制来自 npm 可选依赖，没有额外做校验和核对。

## 试点 2：AG-UI —— 缺口盘点表 + 看板实时推送

### 试点范围

- 缺口盘点表：`docs/reports/2026-11-24-agui-gap.md`。对照本地 `@ag-ui/core` 1.0.2 的 31 个事件（八个家族），每行给熊宝的真实 `文件:行`；自定义 CUSTOM 名单逐个判断能否映射到标准事件，并估改造成本。盘点结果：已有 23、缺失 8；`RUN_FINISHED` 的 `cancelled` 结局熊宝没发过；`openbot.headless.waiting` 与 `on_interrupt` 是同一件事的旧通道，最容易先收掉。
- 看板实时推送（开关 `XIONGBAO_PILOT_BOARD_PUSH`，默认 `off`）：经看板投影器写入的卡片状态一变，服务器经已有的 Postgres `NOTIFY` 与频道 WebSocket（`/api/channels/events`）给卡片所属租户的本人发 AG-UI `STATE_DELTA`（JSON Patch，只含卡片 id 与状态）。一次变动读满 40 张时不点名，只发「整板变了」（`replace /tasks`）。页面收到后重读看板统计，整板变了时再重读列表。**看板轮询不放慢，开关开不开都是 5 秒。**
- **结论要先说在前面：这个试点的增量有限。** main 上本来就有粗推送——`announceTaskUpdate` 发 `taskUpdated`，页面据此重读 `["tasks"]`（`server/src/channels/events.ts`、`app/src/lib/channels/use-channel-events.ts`），看板本来就是准实时。试点没有动它。试点多出的只有：标准形状的消息、带卡片 id 与状态、顺带重读统计（`["tasks-summary"]` 不被 `["tasks"]` 前缀覆盖）、以及服务器订阅恢复时把看板也重读一次。验证的是通道、形状和隔离，不是体验提升。
- **页面只把推送当「有变化」的信号**，没有用 delta 里的卡片 id 做局部更新（没有按 id 刷新单张卡）。所以服务器那边的 id、add/replace 区分只是被测试和消息形状验证，没有被页面行为用到。
- 界面没有任何可见变化，没有加新元素，所以没有截图。

### 怎么跑通

- 开：服务器环境里设 `XIONGBAO_PILOT_BOARD_PUSH=on`，重启。不用动页面配置，页面经 `/api/capabilities` 得知。
- 关（默认）：服务器不发 `STATE_DELTA`，`/api/capabilities` 没有 `boardPush` 字段，看板轮询仍是 5 秒、统计 30 秒，`resync` 的处理与 main 相同。
- 鉴权与租户隔离照现有频道事件的做法：谁能收由写入的一侧决定（`memberIds`）。这里在这个人自己的租户帧里读卡，行级安全和 `tenant_id` 条件各挡一次（两层单独拿掉其中任一层，测试都会红）；读不到的卡（被移给别人、被删）不进推送，别人的卡进不了他的推送，共享的 `system` 行也不推。推送只带卡片 id 和状态，不带标题等正文；页面收到后用自己的会话重读，走的是原来的 `/api/tasks`。
- 一个已知的口径：卡片的「可见」在这个产品里就是「属于这个租户」，没有更细的成员关系。所以「被移出」测的是卡不再属于他（改租户）；一张卡被删，推送里也不会再有它，但页面要等下一次轮询才知道它没了（`STATE_DELTA` 里没有删除操作）。

### 没做完什么

- 真实模型对比跑不了：`model-e2e.yml` 的真实模型评测只能从 main 触发（`github.ref == 'refs/heads/main'`），试点分支不合 main 就没有真实模型 A/B。而且这个试点的改动（看板推送）本来也不经模型，评测测不到它。
- 没有在真实浏览器里端到端看过：页面这一半是组件测试（假 socket、假 fetch），服务器这一半是真库真 LISTEN。两半之间的真实 WebSocket 握手与鉴权，靠的是现有 `/api/channels/events` 路由没改。
- **直接写 `tasks` 的地方不推送**（本轮没给它们接推送，因为那会改开关关时的 `taskUpdated` 行为），所以开关开着时这些状态变化也只靠 5 秒轮询：`xiongbao/server/src/tasks/delivery.ts`（交成果 → 待验收、验收 → 完成、退回）、`xiongbao/server/src/tasks/delivery-checker.ts`、`xiongbao/server/src/tasks/nudge-run.ts`、`xiongbao/server/src/wakerflows/recovery.ts`（→ 失败）、`xiongbao/server/src/tasks/briefing.ts`；`createDelivery(database)` 在 `xiongbao/server/src/index.ts` 里没有通知回调。这也是看板轮询不放慢的原因。
- 看板里一张卡被删、被归档后的消失，推送不覆盖，仍靠轮询。
- 同一次变化页面会收到两条：旧的 `taskUpdated`（重读列表）和新的 `STATE_DELTA`（重读统计）；列表不再读两遍。
- `xiongbao/server/src/index.ts` 里 `enabled: config.pilotBoardPush` 这一处接线没有单独的测试（它在一个几千行的启动函数里，起整个服务代价过大）；开关的行为靠 `createBoardPush` 的 `enabled` 与配置读取各自的测试，接线写错（比如写成 `enabled: true`）不会被抓住。
- 缺口盘点表只读了类型定义和熊宝自己的代码，没在真实运行时上验证任何映射。

### 风险

- **多一次读**：每次投影器变动，开着开关时服务器多读一次（两条带 `tenant_id` 与 `updated_at` 条件的查询）。现有索引是 `(tenant_id, status, updated_at)`，`status` 夹在中间，对 `updated_at` 的范围扫描用不全。**转正前需要加 `(tenant_id, updated_at)` 索引，或让投影器直接传卡片 id、不再回读。**
- **载荷上限**：`NOTIFY` 约 8 kB，一条最多 40 张卡；读满时改发整板失效，剩下的在下一次推送继续按游标报出。
- **时钟**：`updated_at` 由写入进程的时钟盖章，进程间偏差超过 2 秒时，晚于游标才写入、却盖着更早时间的卡可能被漏报；因为页面不用 delta 内容、列表另有 `taskUpdated` 和 5 秒轮询兜底，这只影响 delta 的内容，不影响用户看到的板。游标在进程内存里，重启或换副本后第一次推送回看 10 秒。
- **旧页面**：不认识 `STATE_DELTA` 的旧页面会把它当成没有 `channelId` 的消息丢掉，不出错。
- **`resync` 的判断**：页面用「收到过推送」或「已缓存的能力说开着」判断开关，二者都没有时（刚打开页面就遇到 `resync`）会少读一次看板，由 5 秒轮询补上。
