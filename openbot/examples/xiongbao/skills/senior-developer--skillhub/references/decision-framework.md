# 技术开发决策框架

> 教科书告诉你「怎么做」，但没告诉你「什么时候不该做」。
> 本文档记录资深开发工程师在技术选型、架构决策中的隐性判断经验。

---

## 一、技术选型的「反共识」指南

### 什么时候不该用最新框架

| 场景 | 直觉反应 | 专家判断 | 原因 |
|------|---------|---------|------|
| 新项目启动 | 「用最新版Laravel/Vue」| 「先用团队最熟的版本」 | 踩坑成本 > 新特性收益 |
| 老板说「要用AI」 | 「接入GPT API」 | 「先搞清楚要解决什么问题」 | AI不是锤子，问题不是钉子 |
| 看到酷炫Demo | 「也要做成这样」 | 「性能预算够吗？」 | 60fps vs 30fps的用户留存差20% |
| 同事推荐新库 | 「试试」 | 「这个库last commit是什么时候？」 | 弃维护的库 = 技术债 |

**核心原则**：技术选型的第一问题是「团队能不能驾驭」，不是「这个技术牛不牛」。

## 二、性能优化的优先级决策

### 「该先优化哪里」的决策树

```
用户抱怨「慢」→ 
├── 是首屏慢？ → 优化加载链（图片/JS分段/CDN）
├── 是交互慢？ → 优化JS执行（debounce/heavy计算移到Web Worker）
├── 是动画卡？ → 优化渲染（GPU加速/reduce repaint）
└── 是数据加载慢？ → 优化API（缓存/分页/GraphQL）

如果以上都做了还慢 → 
   → 是不是功能太多？砍功能比优化更有效
```

### 常见的「伪优化」（浪费时间的行为）

| 行为 | 为什么是伪优化 | 该做什么 |
|------|--------------|---------|
| 过度压缩图片到极限 | 肉眼看不出区别，但维护成本大增 | 压到WebP 80%质量就够了 |
| 把所有JS都Tree-shaking | 节省<10KB，但构建时间翻倍 | 只对有大量未使用代码的库做 |
| 手写汇编级优化代码 | 现代编译器比你更懂优化 | 改算法复杂度，别改常量系数 |
| 过度使用缓存 | 缓存失效Bug比性能问题更难查 | 只在真的有性能瓶颈的地方加缓存 |

## 三、代码质量的「适度」原则

### 过度工程化 vs 欠工程化

| 维度 | 欠工程化 | 适度 | 过度工程化 |
|------|---------|------|-----------|
| 抽象层级 | 所有逻辑写在一个函数 | 按职责拆成2-3个类/函数 | 每层抽象只做一件事，层层嵌套 |
| 测试覆盖 | 没测试 | 核心逻辑有单元测试 | 连getter/setter都有mock测试 |
| 错误处理 | ignored | try-catch关键路径 | 每个函数都throw custom Exception |
| 注释 | 没注释 | 复杂逻辑有注释 | 每行代码上面都有注释 |

**专家判断**：适度 = 当下的团队规模 × 1.5倍。代码是为未来6个月的团队写的，不是为5年后的谷歌写的。

## 四、Laravel 开发中的「坑点」决策

### 什么时候不该用 Eloquent

Eloquent 很方便，但不是万能的：

| 场景 | Eloquent做法 | 专家建议 | 原因 |
|------|-------------|---------|------|
| 大量数据导出 | `$users = User::all()` | `DB::table('users')->select(...)->cursor()` | 内存爆炸 |
| 复杂报表查询 | Eloquent Relationship链式调用 | 直接写SQL或使用Query Builder | 可读性更好，性能可控 |
| 批量更新10000条 | foreach + save() | `update()` 批量操作 | N+1问题 |
| 多表JOIN | Eloquent with() | 视情况，复杂JOIN直接SQL | Eloquent的JOIN有时候生成奇怪的SQL |

### N+1 问题的快速识别

```php
// ❌ 经典N+1
$posts = Post::all();
foreach ($posts as $post) {
    echo $post->author->name; // 每个$post都查一次数据库
}

// ✅ 预加载
$posts = Post::with('author')->get();
```

**判断技巧**：如果页面加载时Network面板里出现了「同一个API被调用N次」，就是N+1。

## 五、Three.js 的「用与不用」决策

### 什么时候该用 Three.js

| 场景 | 用Three.js | 不用Three.js（替代方案） |
|------|-----------|------------------------|
| 产品3D展示 | ✅ 值得 | ❌ CSS 3D transform也能做简单旋转 |
| 粒子背景装饰 | ⚠️ 性能敏感 | ✅ CSS动画或Canvas 2D |
| 数据可视化 | ✅ 3D图表 | ⚠️ D3.js或ECharts够了 |
| 游戏/强交互 | ✅ 必须 | ❌ 不适用 |
| 炫酷着陆页 | ⚠️ 小心性能 | ✅ 视频或GIF可能更好 |

### Three.js 性能预算

```
移动端：< 500个三角形，< 3个光源，不使用实时阴影
桌面端：< 50000个三角形，< 10个光源

超过这个预算 → 用户设备会发热 + 掉帧 → 体验反而更差
```

## 六、CSS/动画的「适度」决策

### 什么时候CSS动画不够，需要JS

| 需求 | CSS | JS（GSAP等） |
|------|-----|--------------|
| 简单过渡/悬停效果 | ✅ `transition` | ❌ 过度 |
| 滚动触发动画 | ⚠️ `scroll-timeline`（新）| ✅ IntersectionObserver + GSAP |
| 复杂时间线动画 | ❌ 难以控制 | ✅ GSAP Timeline |
| 物理效果（弹性/惯性） | ❌ | ✅ GSAP或物理引擎 |

### `will-change` 的滥用与正确使用

```css
/* ❌ 滥用 - 什么都加will-change */
.bad { will-change: transform, opacity, box-shadow; }

/* ✅ 只在确实需要优化时 */
.good { 
    will-change: transform; /* 这个元素会频繁transform */
}
.good.animated {
    transform: translateX(100px);
}
.good { will-change: auto; } /* 动画结束后清除 */
```

**原因**：`will-change` 会占用GPU内存，滥用反而让性能更差。

## 七、技术债的管理决策

### 什么时候该还技术债

| 信号 | 行动 |
|------|------|
| 新功能开发时间 > 预估的2倍 | 先做重构，再开发 |
| Bug数量月度环比增加 > 30% | 暂停新功能，专门修Bug+重构 |
| 新人入职后适应期 > 2周 | 代码可读性有问题，该重构了 |
| 你害怕改某块代码 | 这块代码已经没人懂了，急需重构/重写的临界点 |

### 如何向产品/老板申请「重构时间」

**错误说法**：「这段代码写得太烂了，需要重构」（产品：那又不影响用户）

**正确说法**：
> 「最近两个月，开发新功能的速度越来越慢，主要原因是XX模块的代码结构不合理。如果现在花2周重构，未来每个新功能的开发时间能减少30%。您觉得是现在重构，还是继续按当前速度推进？」

**核心**：把技术债翻译成「业务成本」。

## 八、AI 辅助编程的正确姿势

### 什么时候该用 Copilot/Claude 辅助

| 场景 | 用AI | 不用AI |
|------|------|--------|
| 写样板代码（CRUD） | ✅ 省时间 | - |
| 学习新框架的Hello World | ✅ 快速上手 | - |
| 核心业务逻辑 | ⚠️ 人工Review必须做 | ❌ 直接粘贴 = 埋雷 |
| 安全相关代码（认证/加密） | ❌ | ✅ 必须人工写+Review |
| 性能关键路径 | ⚠️ AI生成的代码通常不过性能优化 | ✅ 人工优化 |

### AI 生成代码的「三步检验法」

```
1. 跑一遍，看能不能运行（基础功能）
2. 看边界条件处理（NULL/空数组/超大数据）
3. 看安全漏洞（SQL注入/XSS/未授权访问）

任何一步没通过 → 不用，重写
```

---

*技术决策的本质不是在「对」和「错」之间选，而是在「合适」和「不合适」之间选。*
