## A5 留下的那一格

A5 让"没成"看得见，但它在途时什么都不说：一张卡的归档请求还在空中，人可以再点一次、也可以把它拖进已结束——两次写都会真的发出去。A5 只补了闸的一半（`retry: false` 让库不重放），**人手重复提交这一半没人管**。A6 只关这一格：同一张卡在写未 settle 期间，本页不再接受第二次入口；不同卡照常并发。

## 为什么闸放在 ref、呈现另用一份 state

`useMutation` 在这一页只有**一个实例**，而它有七个入口（拖放 1＋需要关注 2＋列表 2＋泳道 2，行号为 A5 冻结态：720／793-794／931-932／974-975）。所以：

- `act.isPending` 描述的是**这个 hook**，官方文档原话 "The mutation is currently running"。拿它当闸，一张卡提交会把整页卡片一起变暗——那不是"抑制同卡"，那是把板子锁了。
- `act.variables` 只反映**最后一次** `mutate` 的入参。用它当身份，先发的请求仍在途时闸已被后发那张卡占名；后发者先回来就会替先发者解锁。
- 因此入口闸是 `useRef(new Set<string>())`：**同一个同步 handler 内先查后写**，不给两次点击之间留任何渲染间隙。屏幕要的"哪张卡在忙"由一份**独立的 state Set 副本**呈现；两者不能合一，因为 state 更新是异步的，用它当闸等于让第二次点击赶上第一次还没生效的那一帧。
- 解锁只发生在 hook 级 `onSettled: (_data, _error, variables)`——**variables 是第三个参数**（第二个是 error；草案那个 `onSettled(_, s) => s.id` 会把 error 当成 variables，已由 Root 51667447 纠正并废掉）。每次 settle 用**自己那次调用的 variables.id** 解自己的闸；官方并发说明见 https://tanstack.com/query/latest/docs/framework/react/guides/mutations#consecutive-mutations ，完成顺序与调用顺序可以不同，所以"谁回来"不能当成"谁被解锁"。
- 不用 per-call callback 解锁（它们只为最近一次调用触发），也不在异步 `onMutate` 里设闸。

## 状态语义（与用例一一对应）

| 情形 | 闸 | 屏幕 | 网络 |
| --- | --- | --- | --- |
| 同卡再点／再拖（含同一 act 批次内连发） | 入口直接返回 | 该卡各视图仍"归档中…／查收中…" | 不新增 POST |
| 另一张卡操作 | 不受影响 | 只有它自己变忙 | 它自己的 1 次 POST |
| 后发先至 | 只解后发那张 | 先发那张仍忙 | 各 1 次 |
| 404／409 拒绝 | 立即释放 | alert 显示服务端原句，按钮恢复可用 | 失败不重放 |
| 点`刷新任务` | **不动仍在途的闸** | 清掉旧展示，只读 | 只 GET，POST 数不变 |
| POST 已 settle、refetch 未回 | 已释放 | 不再显示在途 | pending 绑 settle，不绑 refetch |

"各视图一致"不是额外功能：`pendingIds` 经 props 下到 `TaskCard`，同一张卡在需要关注区与看板里读同一个集合，用例① 断的是"该卡出现的每一行都同时忙、同时改文案"。
