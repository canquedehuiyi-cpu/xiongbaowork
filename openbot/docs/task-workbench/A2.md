## 改了什么（四行，全是属性）

1. 状态徽章加 `data-status={task.status}`。未命中 `STATUS_LABEL` 时文本本来就落原值，但机器拿不到那个原值；现在“未知枚举看得见原值”可以被断言。
2. 状态胶囊（`FILTERS`）、周期胶囊（`PERIODS`）、形状切换（列表／泳道）各加 `aria-pressed`。三者以前只靠颜色表示选中，读屏与测试都判不出“当前 URL 选了哪个”；统计卡早有 `aria-pressed`，本轮把剩下的控件补到同一口径。

没有改：`laneOf`／`boardStats`／`shownForStatus`／`archivesOnDrop`／`attentionGroups`／`cardLinkOf` 的行为与语义、导出名单、轮询间隔、请求参数、权限动作范围。本包有意不抽组件（Root 51664019 裁定一），所以 `Task` 仍是 route 内的局部类型，无新目录、无循环导入。

## 为什么两个形状必须共用一次读

两种形状仍读同一个 `list = shownForStatus(tasks.data ?? [], status)`（route 649 行），并且 `view` 不在任何 queryKey 里。新测试把这句话变成可验的事实：切完形状后结果行数不变、每张卡自述的 status 不变、未动的五轴保留，而且 `/api/tasks` 的请求数一个也没多。

## 新测试盖了什么（7 例，39 条断言）

- 切形状：同一批身份与状态、六轴全保留、无第二次读。
- 统计自己的读：实际请求不含 `status=` 也不含 `q=`，但带 period／deviceId／executors。
- 满窗：199 running + 1 failed 时总数说 `200+`，而进行中仍给准确数 199；区分“看了多少”与“库里有多少”。
- 四张数：6／1／1／3。`已结束` 按 D-1 含 done+failed+awaiting_review，`需要操作` 只含 needs_action，因此 awaiting_review 不会被记成 needs_action、failed 不会被记成 running。
- 泳道分区：进行中=[running]，需要关注=[failed, needs, review]，已结束=[done]；三个注意态都不在已结束里，done 也不在另一列里。
- 未知枚举：列表形状里卡显示原值 `scheduling`（文本与 `data-status` 都是），三列泳道都没有它；同时用导出的 `laneOf` 把边界讲清楚（scheduling 得空数组）。
- 轮询合同：从查询完成后的活缓存读 `options.refetchInterval`，得 5000 与 30000；并断两条 queryKey 形状（汇总那条确实不带 status／q）。

## 一条要记录的既有边界（本包不改）

未知状态在列表形状里可见、在泳道形状里被丢弃。这是 `laneOf` 分区定义的直接结果（状态不在任何列的 statuses 里就不渲染），不是本包引入的。把它改成“未知也占一列”会改业务分区语义，属 A3／A4 或 Root 另行裁定；本轮只让它可被断言、并被本文件如实记下。
