# Changelog

What changed, for somebody deciding whether to upgrade. Written for the person running 熊宝, not
for the person who wrote the commit: a line belongs here when a deployment behaves differently
afterwards, and does not when only the code moved.

Newest first. `Unreleased` is what is on `main` and not yet tagged.

## Unreleased

- **员工能认出你对它的纠正了。** 你指出员工做错并说明该怎样（「不是这样，要……」「我说过别……」「以后……」），自动记下的那条会标成「纠正」并记下纠正过几次；同一件事再纠正一次只加次数，不再多一条。和已有记忆冲突的纠正会写明「将取代：<旧条>」，你确认（或改过）它之后旧条才被删除、旧条内容记进新条的来源，确认前旧条一字不动。员工的上下文里，待确认的纠正排在其他待确认记忆之前，并带上「以这条为准」「纠正过 N 次」「已被取代」的说明。设 `XIONGBAO_MEMORY_CORRECTIONS=off` 可关掉纠正这一类，其余自动记忆照旧。本项带迁移 `0001_memory_corrections`（`personal_memories` 加三列，旧数据不回填；它是基线之后的第一条迁移，合进 main 时编号 0242，从 v0.2.16 升级时在接管基线之后紧接着执行）。
- **员工交付时，服务器会在它的电脑上把它声明的核对命令再跑一次。** `deliver_task` 多了 `rerun`（至多 3 条，每条 120 秒）：员工原样写这张卡里跑过、能证明结果的命令，服务器复跑后和这张卡里最近一次比，退出码从 0 变成非 0、或输出里的数字偏差超过 10%（耗时、日期、时刻不算）就挡回；同一张卡因此挡回满 2 次后第 3 次照收，卡片交付详情顶部写「复跑结果和员工说的不一致，验收时请留意」，每条命令显示「复核通过 / 复核不一致 / 未复核（原因）」。自查或结论里说测过、却没写 `rerun` 也没写「无法复跑：原因」的，每轮第一次交付挡回一次。复跑从不弹审批：按现在的规则要审批的、当初经审批才执行的、会改动文件或对外写入的命令，以及配对的个人电脑、设备模式、电脑不在线时，都记「未复核」，不挡回。外部员工不受影响。`XIONGBAO_DELIVERY_RERUN=off` 关掉复跑，`XIONGBAO_DELIVERY_RERUN_CLAIM_GATE=off` 关掉「说测过」那道门，默认都开。本项不带迁移（结果记在卡片原有的交付内容字段里）。
- **员工能认出你对它的纠正了。** 你指出员工做错并说明该怎样（「不是这样，要……」「我说过别……」「以后……」），自动记下的那条会标成「纠正」并记下纠正过几次；同一件事再纠正一次只加次数，不再多一条。和已有记忆冲突的纠正会写明「将取代：<旧条>」，你确认（或改过）它之后旧条才被删除、旧条内容记进新条的来源，确认前旧条一字不动。员工的上下文里，待确认的纠正排在其他待确认记忆之前，并带上「以这条为准」「纠正过 N 次」「已被取代」的说明。设 `XIONGBAO_MEMORY_CORRECTIONS=off` 可关掉纠正这一类，其余自动记忆照旧。本项带迁移 0242（`personal_memories` 加三列，旧数据不回填）。
- **看板卡一轮没做完时，会自动给下一轮留一份「失败交接」，下一轮从断点接着做。** 跟进中的卡某一轮出错或被停下（步数到顶、超时、提前结束）时，服务器从这一轮的记录里拼出停在哪、卡上最近的进度、最后 5 次工具调用和这一轮写过的文件（至多 10 个），不调模型，至多 1500 字，经过脱敏，密钥不会进卡片历史；卡片流水里显示为可展开的「失败交接」。这张卡下一次开新一轮（催办、再催、退回、换人接手）时，给员工的开头消息最前面附上这份交接，带过一次就不再带；之后有一轮正常做完的，旧交接也不再带。被后来一轮接替的那一轮不写。子代理没做完时，交回的结果里也带上它最后几次工具调用和写过的文件（同样脱敏、至多 1500 字），员工可以接着做。本项不带迁移。
- **（运维）镜像发布流程修了 v0.2.16 踩到的三个坑：只设在 `release` Environment 里的变量不会再让同步自有仓库被悄悄跳过、让 G7 失败；后面的 job 失败后重跑不再重新构建镜像，而是核对 provenance 后复用此提交已构建并验证过的 digest（`promote` 仍然绝不移动版本标签和 `sha-` 标签）；G7 干净部署始终匿名拉取公开的 GHCR 镜像，不再去拉需要登录的 JCR；GitHub Release 已存在时（同一标签、同一提交）重跑改为用 `--clobber` 重新上传清单而不是失败，指向别的提交则报错。** 发布流程现在不需要任何仓库级变量，`XB_*` 变量放 `release` Environment 即可；设备端发布同样改为在 `device-release` Environment 里判断下载页，`XB_DOWNLOAD_*` 要设在该 Environment，不再需要仓库级的 `XB_DOWNLOAD_BUCKET`；成对的变量只设一半时，发布会在打标签之前报错并写明缺哪个。当时为绕过问题加的仓库级 `XB_REGISTRY`、`XB_IMAGE_REPOSITORY` 可以删掉。手动运行 G7（`clean-deploy.yml`）时，用自有下载页要自己填 `download_base_url`。详见 `docs/releasing.md` 的「变量放在哪一级」。本项不带迁移。
- **数据库迁移合成了一条基线，从 v0.2.16 升级时第一次启动会先核对数据库结构。** v0.2.16 之前的 222 条迁移合成了 `server/drizzle/0000_baseline.sql` 一条，新装直接跑它。v0.2.16 的库第一次用这一版启动时，迁移器先确认库已经做完 v0.2.16 的改名升级，再把库的结构（表、列、约束、索引、行级安全策略、给应用角色的授权、函数、触发器等）和基线逐项比对：一致就在同一个事务里把迁移记录（`drizzle.__drizzle_migrations`）改写成基线一条，原来的记录留在 `drizzle.__drizzle_migrations_before_baseline`，启动日志打印一行 `{"type":"migration-baseline-adopted","replaced":222}`；之后再启动什么都不做。**不一致就不改写、不迁移、不启动，日志逐项打印差异（`-` 是基线里的样子，`+` 是库里的样子），数据库没有任何改动**：这时这个库原样还能用 v0.2.16 的镜像启动，先换回 v0.2.16 保持服务；差异是手工改过库（加过索引、改过列或授权）的，改回 v0.2.16 的样子再升级；说不清来历的，把这段日志交给维护者，不要手工改迁移记录表。升级后要回到 v0.2.16：先撤掉基线之后的迁移（每条迁移头注释里「回滚：」下的语句，倒序执行；在源码 `server/` 下运行 `bun scripts/rollback-after-baseline.ts` 会打印出来，这一版只有 `0001_memory_corrections` 的三条 `DROP COLUMN`，撤掉会丢掉纠正记录的标记），否则之后再升级时结构对不上会被拒；再把留下的记录放回去、换镜像：`BEGIN; DELETE FROM drizzle.__drizzle_migrations; INSERT INTO drizzle.__drizzle_migrations (id, hash, created_at) SELECT id, hash, created_at FROM drizzle.__drizzle_migrations_before_baseline; COMMIT;`。新装的内置库超级用户与库直接叫 `xiongbao`（不再先用旧名建、首启再改名）；开发 Compose 的超级用户、口令与 `.env.example` 的公开默认口令都改为 `xiongbao`（旧的公开默认口令在生产环境照样被拒绝）：已有的开发 Compose 数据卷是旧超级用户建的，要删卷重建（`docker compose down -v`）。外接数据库的迁移 owner 不再要求特定名字。**Helm 用内置数据库（`postgresql.enabled`）的已有 release：** chart 的默认库名改成了 `xiongbao`，但 PostgreSQL 不会给已有的库改名，升级时要在 values 里保留原来的库名（`--set postgresql.auth.database=<原库名>`，以后每次升级都带上；原库名的查法见 charts README 的 Upgrades 一节）。`helm upgrade` 发现库名对不上会直接拒绝并给出原库名；用 `helm template`（如 Argo CD）的部署检查不到，迁移 Job 会因连不上库而失败，数据库不受影响，补上这一项再同步即可。外接数据库的迁移角色要能建角色（基线会建两个应用角色），不再需要 `vector` 扩展。
- **批准之后，员工以交付收尾时不会再把同一张卡反复交付好几次，批准卡片也不会一直停在「正在运行」。** 以前批准最后一个动作后，员工接着做完、交付被接受就直接收尾不再说话，服务器把这一轮当成「什么也没说」的失败，每 10 秒从同一处重跑一遍，同一张卡交付 5～6 次，审批记录一直停在进行中。现在这一轮里交付被接受、之后不说话，算正常完成（交付发生在批准之前也一样），群聊页面会随之刷新。续跑一旦开始，后面出了任何错也不再从同一处重跑（重跑会把已经做过的动作再做一遍），只有还没开始就失败的才重试；开始后失败的，单聊里会写一句「这一轮没能做完。发一条消息，让它接着做。」并通知到做决定的地方，等着它的例行任务、自动任务和团队步骤都记为失败。看板任务轮交付后不说话、被当成失败重跑的同一问题也一并修好。本项不带迁移。
- **网页单聊里需要先批准的动作，又能弹出批准卡片了。** 以前在镜像部署里，「改动之前先问」开着（或有规则要求先问）时，员工写文件、跑命令会被直接拒绝，工具结果是「This action needs your approval, but it was not started from a conversation that can ask you」，页面上也没有批准卡片；不打包直接跑源码时没有这个问题，所以测试一直没发现。原因是服务器有几处用相对路径引用 toolkit，镜像打包（`bun build --packages=external`）时被内联成第二份，执行工具和审批各读一份上下文。现在服务器对 toolkit 一律用包名引用，并加了按镜像方式打包后再跑的回归测试和禁止相对引用的检查。同一原因也让后台例行任务、找回密码续跑里「等人批准」的暂停认不出来，一并修好。本项不带迁移。
- **交付卡里的文件，经过审批的活也能预览、下载了。** 以前活里有一步是批准后才执行的（比如批准后写文件），交付卡「已交成果 · 等你验收」里点「预览」或下载会提示「没有这个员工」（`404 There is no such Bot.`）。原因是服务器要从这张卡的某一轮记录里找文件在哪台电脑上，而批准后执行的写入不在任何一轮里，找不到就拒绝。现在员工交付时，服务器把文件所在的电脑记在卡片上，预览按它找，仍然只有能看这张卡的人才能打开卡上列出的文件。以前交付的卡没记电脑的，员工在本人自己的电脑上干活时也能打开了；员工单独用一台电脑（勾了「隔离」）的旧卡仍打不开，让员工重新交付一次即可。本项不带迁移（电脑记在卡片原有的交付内容字段里）。
- **每个员工用自己的系统用户时（镜像默认 `COMPUTER_PER_BOT_USERS=on`），又能预览、下载默认员工以外的员工工作区里的文件了。** 以前点预览或下载会得到 503「The Bot's computer sent back a file that couldn't be read.」：员工电脑在这种模式下按流发文件，Bun 发流时把 `Content-Length` 丢了，服务器因为拿不到长度就拒收。现在员工电脑另用一个头报出文件长度，服务器边读边核对，多一个字节或少一个字节都照样拒绝，员工电脑那边的下载大小上限不变。员工电脑和服务器要一起升级（同一个镜像里的本来就是一起的）。本项不带迁移。
- **许可证只放一处。** 镜像 `/licenses/` 与设备端安装包里不再有 `NOTICE`：产品最初所基于代码的 MIT 版权行与许可原文改放在 `THIRD-PARTY-NOTICES.md` 的开头，`LICENSE` 是熊宝自己的 MIT 许可。关于页「第三方依赖」里那一行照旧可以展开看到版权行与 MIT 全文；产品版权串（关于页、设备端安装包）只写公司名。本项不带迁移。

## 0.2.16

这一版把系统里剩下的上游旧名字统一换成熊宝自己的名字（数据库、配置名、凭据格式、对话历史里系统写的名字、发布记录），并删掉了熊宝用不上的浏览器录制扩展与云端学习。是过渡版：旧名在这一版仍然被认，到 v0.2.17 才删。

**从 v0.2.15 升级先看这几条**（逐条说明在下面各项里；交付容器的完整步骤见部署手册 6.4）：

- **第一次启动会自动改名，改名前自动备份。** 用内置库的交付容器，v0.2.16 首次启动先做前置检查，再把数据库备份到数据库卷上的 `/var/lib/postgresql/backup/pre-rebrand-<UTC 时间>.dump`（0600），然后在一个事务里改业务库、最后改超级用户与库名，才启动服务。**还有待审批、未完成的续跑，或数据库卷可用空间不到库大小的 2 倍时拒绝启动**，数据不动。升级前在 v0.2.15 上跑一次只读自查 `pre-upgrade-check.sh`（v0.2.16 标签里附带）。第二次启动起什么都不做，也不再备份。
- **回滚不再是换回旧 digest。** 改名完成后 v0.2.15 用旧名登录不了这个库：回滚要用上面那份备份还原到新卷、再用 v0.2.15 镜像起来（镜像里带还原脚本 `rebrand-restore.sh`），**备份之后写进去的数据会丢**。启动失败且日志说「业务库没有改动」时不用还原，直接换回 v0.2.15 用原来的卷。备份留到 v0.2.17 稳定后再删。
- **配置名统一用 `XIONGBAO_` 前缀。** env 文件里旧前缀的配置名这一版仍然认（启动日志点名提醒），v0.2.17 不再认；新旧都写了且值不同时以新名为准。本版附带的改写脚本 `rewrite-env.sh` 一次改完（先留 0600 备份，不打印任何值）。
- **外接数据库、Helm、自己写了 `DATABASE_URL` / `ROLE_WRITER_DATABASE_URL` 的部署要多做几步：** 迁移把两个应用角色改名为 `xiongbao_app`、`xiongbao_role_writer`，连接串里的用户名要改；角色口令是 md5 格式的，改名会清空口令，要重设；迁移环境要带 API 用的同一个 `KEY_ENCRYPTION_KEY`（重新加密已存凭据）；先停掉全部 v0.2.15 副本再迁移；外接库不自动备份，迁移前自己做整实例快照。Helm 从 v0.2.15 的 chart 升级要在 values 里把 `nameOverride` 设成 v0.2.15 chart 的旧名（chart 改名了）。见部署手册第 4 节与 6.3 第 8 条。
- **浏览器扩展删除了，设备端要重装。** 「教员工做事」的浏览器录制、录制扩展和给本人开的熊宝浏览器整块删除：装过扩展的从浏览器里移除即可，没有新扩展要装。服务器、员工电脑、设备端这一版一起换名，设备端请重装 v0.2.16；先升服务器、过一会儿再升设备端没关系，旧设备端在这期间照常连得上。
- **自己单独运行的员工框架镜像（`agent-*`）要和服务器一起升级**：服务器发给它们的鉴权头、运行参数和上下文标题都换成了新名。
- **只有用到下面这些的才要重新连接或配置：** 带签名的自动化钩子（签名密钥的派生换了名字，重新生成密钥交给调用方）；开了 `WEB_BOT_AUTH` 又没设 `WEB_BOT_AUTH_KEY` 的（公钥和 keyid 变了，到 Cloudflare 重新登记）；接了 OpenTag 的（对端要认 `/xiongbao/membership`、`/xiongbao/deliver` 和 `xiongbao.sender`）。用 Composio、控制台里有名字以旧后缀结尾的 auth config 的，这一版照常能用，v0.2.17 之前在 Composio 控制台把后缀改掉。
- **升级后把已经打开的网页刷新一次。**
- **发布记录变了：** `container-images.json` 的 `images` 里只剩 `xiongbao`（配了自有仓库时是同步过去的那份），发布构建出的 GHCR 镜像在顶层 `ghcr`。读 `images` 里旧名那一项 `reference` 的脚本改成 `(.ghcr // .images.xiongbao).reference`。

### 名字统一

- **数据库**：内置库的超级用户与库改名为 `xiongbao`（口令不变；新装的卷也在首次启动时改好）；应用角色改名为 `xiongbao_app`、`xiongbao_role_writer`；十几个数据库函数与触发器、审计保留天数的库级设置、系统写下的来源标记（插件授权、企业设置等的旧前缀）、默认皮肤值、租户包 id、平台模型池记着的密钥变量名（改为 `XIONGBAO_POOL_<X>`）、运行错误码都换成新名。**新对话的线程 id 前缀与升级前相同**（库里只记了旧部署名的摘要）。审计记录只追加、不改，旧审计行照常显示。
- **已存凭据**：用原来的 `KEY_ENCRYPTION_KEY` 解开、按新格式重新加密，凭据内容和修改时间不变；有一条解不开就整个迁移回滚、拒绝启动并点名是哪一条，数据不动。
- **对话历史**：只改系统写进去的名字（等待事件名、运行参数键、上下文标题、卡片标记、生成式界面的目录 id、规则里的工具引用前缀），用户消息、模型回复、工具参数、记忆正文一个字都不动；被摘要或回执覆盖的记录原样保留，读取时新旧都认。
- **审批精确输入**两张表若有数据，改名迁移拒绝执行（现网为 0 行），按日志换回 v0.2.15 并联系开发者。
- 签名域、共享账号身份前缀、OpenTag 路径、桌面登录的 OAuth client id、Helm chart（`charts/xiongbao`，K8s 标签前缀 `xiongbao.dev/`）、开发 Compose 的 SPIRE 信任域（`xiongbao.local`）、员工电脑镜像默认名都换成新名。旧版移动端的回调 scheme 永久保留，已装的手机照常登录。

### 删掉的功能

- **浏览器录制与熊宝浏览器**：「教员工做事」页（`/browser`）、设置里的「浏览器」页、录制扩展、员工电脑里的录制器和给本人开的浏览器都删了；员工浏览器只保留浏览器栏。

- **员工做的网页可以在浏览器里直接打开：新增「内容源」。** 对话或交付卡里员工做出的静态网页目录（里面有 `index.html`），用 `POST /api/computers/:botId/open`（`kind: "dir"`）换一条 30 分钟的链接，在浏览器新标签页或右侧栏里看；工作区根目录、以 `.` 开头的目录不给开，目录必须真的存在且有 `index.html`。网页不和应用同源，所以要配内容源，两种方式二选一，都不设就没有这个功能（点「打开」提示没有配置内容源，其余功能不变）：`XIONGBAO_CONTENT_PORT`（1024 到 65535，不能与 API、应用端口相同；另起一个只答内容源的端口，IP 访问也能用）或 `XIONGBAO_CONTENT_DOMAIN`（泛子域名，只写主机名，每个网页一个子域，不能是 IP；两项都设时以域名为准，不再单独监听端口）。内容源只认自己的 HttpOnly cookie `xb_content`（不设 `Domain`），不读应用的登录 cookie；页面带 `sandbox` 安全头；链接里的令牌 30 分钟有效，换成 cookie 后每次请求都确认你仍是成员、员工仍在、卡片仍可见（同一授权的结果缓存 1 分钟，同时到达的请求合并成一次查询），不通过就 404 并清 cookie，被移出对话的人约 1 分钟内失去访问；cookie 用满一半续期 30 分钟，从第一次打开起最长 12 小时；页面地址 `/u/<令牌>/` 的令牌与 cookie 分开签名，过期后在同一个浏览器里刷新会自动换新，别的情况（比如换了浏览器）404、重新点「打开」；启动时若内容域名等于或是应用主机名的上级则拒绝启动；每次成功打开写一条审计 `content.opened`（员工、目录、对话或卡片、方式，不含令牌或链接）。链接等同凭据，请勿转发；反代访问日志里 `/__open/` 与 `/u/` 开头的路径要关掉或脱敏。**用端口方式的部署要做三件事：容器映射 3773（`docker-compose.yml` 已设 `XIONGBAO_CONTENT_PORT=3773` 并映射 `127.0.0.1:3773`；`docker/compose.delivery.yml` 已带映射，但要在 `.env.delivery` 里加 `XIONGBAO_CONTENT_PORT=3773` 才会监听；两者默认都只绑本机，对外要把绑定改成对外地址，交付版用 `XIONGBAO_CONTENT_BIND=0.0.0.0`），云安全组和主机防火墙放行 3773/TCP（入方向），应用的反代保留 `Host`。** 泛子域名方式要泛域名解析、泛域名证书和保留 `Host` 的反代，内容域名请用与应用不同的可注册域。Helm chart 本版不带内容源的端口和变量。详见部署手册 3.1。本项不带迁移。
- **员工在电脑上跑的程序，可以从对话里点「打开」直接用。** 员工交付时用 `app` 项（见「交付要查实物」）列出程序的端口和首页路径，交付卡上的程序行出现「打开」按钮（和「下载」「预览」同款样式），在右侧栏里用，没有侧栏的页面（任务页）开新标签页；也可以直接 `POST /api/computers/:botId/open`（`kind: "app"`，带 `port`、`path`）。要先配好内容源，没配时按钮置灰、写明原因。请求的路径是：浏览器 → 服务器的内容源 → 员工电脑的转发（`/forward/<端口>/…`，WebSocket 是 `/forward-ws/<端口>/…`）→ 员工电脑 `127.0.0.1:<端口>`。电脑只转给「这位员工自己的程序」：端口在 1024 到 65535、有程序在监听、监听者是这位员工自己的系统用户（官方镜像里每位员工一个系统用户）、不是电脑自己的服务端口；任何一条不满足都只答同一句「That port cannot be opened.」，不透露是别人的、没监听还是电脑自己的。请求体最多 10MB、响应最多 100MB，等响应头最多 60 秒，WebSocket 单条消息最多 16MB。程序看不到你的任何凭据：请求去掉所有 cookie（含内容源 cookie）、`Authorization`、代理头和标明员工座位的头，`Origin` / `Referer` 改写成程序自己的 `http://127.0.0.1:<端口>`；程序的 `Set-Cookie` 在端口方式下一律丢掉、在域名方式下改成只属于该子域并丢掉与内容源 cookie 同名的，`Strict-Transport-Security`、`Clear-Site-Data`、`Alt-Svc` 一律丢掉；不许注册 Service Worker；重定向只能回到本源，指向别处的丢掉、3xx 变成 502；POST、PUT、PATCH、DELETE 的 `Origin` 必须是本源、`Sec-Fetch-Site` 只能是 `same-origin` 或 `none`，别的站点让浏览器发来的写请求在改写 `Origin` 之前就被拒；每位员工的电脑上每个人每分钟最多 600 个请求，同一位员工所有人合计每分钟最多 3000 个；还在流式传输的响应和 WebSocket 每分钟重新确认一次授权，不再被允许或到了从首次打开起 12 小时就切断。**程序不带 `sandbox` 头（2026-11-23 决定：运行中的程序要能用 cookie 取自己的文件和接口）。** 域名方式下子域就是隔离；端口方式下程序的源与应用只差一个端口，同一个浏览器里先后打开的程序能互相读到内容（界面会提示「独立端口模式下，同一浏览器里先后打开的程序能互相读到内容，只打开你信任的程序」，替换掉之前打开的程序时写「已替换你之前打开的程序」），应用自己的会话 cookie 是 HttpOnly 所以读不到，但应用不能新增非 HttpOnly 的 cookie。**只打开你信任的程序；用端口方式时建议改成域名方式。**部署上的两点：服务器、数据库和员工电脑放在同一台主机、同一个系统用户下时，用 `COMPUTER_FORWARD_DENY_PORTS`（逗号分隔，默认不设）把服务器端口、内容源端口 `XIONGBAO_CONTENT_PORT`、数据库端口排除在转发之外；关掉「每员工独立系统用户」（共享模式）后分不出是哪位员工的程序，一位员工的交付可能把另一位员工的端口转给看交付的人，不要对不信任的员工开放程序转发。不带范围的「打开」（没有对话运行或交付卡）能打开该员工座位上任意本机端口，界面不走这条路。本项不带迁移。
- **修复：员工一轮的产物记录不再在分段或跨运行时丢失。** 「每轮首尾记文件」原先按单个运行的流记快照，而快照是懒的（第一次真正动电脑时才记），电脑工具又都在段与段之间、流外执行，所以服务器分段执行工具、或页面逐个执行电脑工具的轮，每段结尾比对时标记仍是待记、被丢弃，整轮没有一条事件，下载清单和按「对话加运行」放行的下载范围都落空。现在：服务器执行工具的单聊整条轮在外层统一观察；看板派活、群聊、例行等无人值守轮在整轮上观察，外层观察了整轮，里面各段让位、不再冲掉标记；页面自己执行电脑工具的单聊，一轮跨多个运行时标记按（人、员工、对话）留在运行之间（最长 30 分钟、最多 500 条，被丢下的轮次连同电脑上的快照一起忘掉），结束时不再有待执行工具调用的那个运行才比对，人的下一条消息开始新的一轮；这一轮里员工交了付、或停在服务器自己接着办的等待（审批）上，当场比对，清单挂在交付所在的运行上，交付卡的下载才找得到。
- **群聊里被时限停掉或出错收尾的轮也列出这一轮的文件；群聊里带电脑的员工每轮最多 25 分钟，多个群并行回答、同一个群仍按顺序（修复，2026-11-24 决定）。** 以前群聊每轮固定 5 分钟、30 段就硬停，被停的轮以运行错误收尾，产物比对只在正常结束时做，所以这一轮的文件在电脑上、对话里却没有清单，下载和预览 404，人说「继续」也补不回来（慢模型、视频转码、装依赖都会碰上）。现在：一轮不论正常结束、出错、被停还是流断开，都比对并列出清单（插在运行错误之前，原错误照常给人看）；群聊回复行在出错时也带清单，并和正常结束一样经过「主人放行」（有别人在场、需要放行时清单先扣着，放行后显示）。群聊里这一轮能用电脑工具的员工改用工作档：每轮最多 25 分钟、80 段，与单聊一致；用不了电脑的员工不变（到点仍是硬停，但会列清单）。为此群聊队列在长轮里每 5 分钟续一次租，不会被另一个副本中途接管；每个服务器进程同时处理多个群（`XIONGBAO_GROUP_TURN_WORKERS`，默认 4，1 到 16，写错启动失败），同一个群的消息严格按顺序处理（以前多副本时同一个群也可能并发，本版一并修好）。本项不带迁移。
- **内容源的授权在非单用户部署里也能用了（修复）。** 内容源的独立端口和域名请求不在应用的请求帧里，每次确认成员资格要读库（角色、员工资料、运行事件），读库被租户帧守卫拒绝，异常被吞成 502，团队版里打开网页和程序都是 502；单用户部署的角色判断不读库所以开发时看不出来。现在在授权里记的那个人（签发令牌时的用户 id）自己的帧里作答；记的人不是可以代为行事的租户（空、team、platform、system）的授权一律判不允许，不借 platform 帧绕过行级安全。

### 模型

- **模型库新增提供方「AIHUB 中转」（OpenAI 兼容）。** 接口地址留空时默认 `https://aihubcc.cc/v1`，也可自填，密钥填中转站发的 `sk-` 开头的密钥；员工要调工具只能选它转发的 `gemini-4-argon`、`gemini-4-hydrogen`（带 `-app` 后缀的版本不支持工具调用，选了员工用不了电脑上的工具）。`gemini-4-argon` 的上下文按 1M 计，`gemini-4-hydrogen` 中转站文档没写，需要在模型库里手动填上限。思考内容经 `reasoning_content` 返回；2026-11-23 用 `gemini-4-argon`、`gemini-4-hydrogen` 和真实密钥实测（员工能力冒烟 `code`、`edit-grep` 通过），思考模式下多步工具调用正常，不需要回传思考内容，所以没有为它加补丁（DeepSeek 那条补丁只对 `api.deepseek.com` 生效）。评测作业 `model-e2e.yml` 的 provider 选 `aihub` 时改用同一个 Environment 里的 secret `AIHUB_API_KEY`。迁移 `0239_aihub_provider_template` 往 `provider_templates` 加一行，已有的提供方不受影响。
- **DeepSeek 思考模式下，多步工具调用的对话不会再被 400「reasoning_content must be passed back」打断。** 发往 DeepSeek 官方主机（`api.deepseek.com`）chat/completions 的请求，在最外一层（全局 fetch 包装和出站守卫 `createGuardedFetch`）再守一遍：思考没关、带 tool_calls 的 assistant 消息缺 `reasoning_content` 的，补成空字符串，不论请求体是哪条路径拼出来的；只在确实缺字段时才改正文，别的主机、思考关着的、已有 `reasoning_content` 的请求不动。另修一处：员工没有自己授予的工具、工具全靠 `input.tools` 的服务器执行单聊，多段续跑时以前只回传空的 `reasoning_content`，现在回传上一步真实的思考。服务器日志的 `model-provider-refused` 行遇到含 `reasoning_content` 的 400 时多一个不含内容的 `reasoningDiagnosis` 摘要（请求是否带 thinking 及其类型、assistant 消息数、带 tool_calls 的条数、缺字段的条数和下标；拿不到请求体写 `bodyUnavailable: true`）。本项不带迁移。
- **思考模式不再有开关，所有员工一律开；单容器部署里自建员工不再被误标成外部托管。** 员工设置里的「思考模式」开关去掉了，所有员工的对话都先想再做（DeepSeek），以前被关掉的员工也恢复为开着，库里留着的 `thinking:false` 不再被读，不做迁移。部署级的 `DEEPSEEK_THINKING=disabled` 仍可全关（运维应急，界面不显示）。`PATCH /api/agents/:id`、创建员工时带的 `thinking` 字段接受但忽略，员工资料里不再返回 `thinking`。另修一处判断：没配 `MANAGED_AGENT_AG_UI_URL` 的单容器部署里，自建员工没有地址，以前被当成外部员工，设置页「模型」一行写「运行在它自己的端点上 / 外部托管模型」、「难任务模型」行不显示；现在按本部署运行的员工处理，有自己地址的远端员工不变。

### 员工做活更稳（评测里查出来的）

- **员工调模型时连接被瞬时断开，这一步自动再试一次。** 员工主循环（看板、单聊、群聊、例行都走这里）的每一步调模型，如果抛出网络断线错误（`ECONNRESET`、「The socket connection was closed unexpectedly」、`ETIMEDOUT`、`EPIPE`、`ECONNREFUSED`、`UND_ERR_SOCKET`、`fetch failed` 等），或流在还没吐出任何文字、思考、工具调用之前就因此中断，等 1 到 2 秒后重试一次，不再让这一轮直接失败。已经吐出内容之后才断的不重试（照旧报错，避免重复输出或重复调用工具）；HTTP 状态错误（401、402 余额不足、400 等）、429 和 5xx 的处理不变（仍按 AI SDK 原有的重试），运行被中止也不重试。重试时服务器日志多一行不含内容的 `model-net-retry`（运行号、错误码、第几步、是否恢复）。**默认开**，设环境变量 `XIONGBAO_MODEL_NET_RETRY=off` 关掉。本项不带迁移。
- **模型调用的断线重试放宽到「只吐了思考」时（无人值守的运行）。** 评测里仍有两次 `ECONNRESET` 没被重试：断开时流里已经出现了思考部件，旧规则把它当成「已经说话」。现在看板卡、例行、巡检等没人看着的运行，会把思考部件先扣住，直到第一个正文或工具调用部件才放出；只吐了思考就断线的，丢掉扣住的思考，等 1 到 2 秒后重试一次，`model-net-retry` 日志行多一个 `afterReasoning`（true/false）。已经出现正文或工具调用（含 `tool-input-start`、`tool-input-delta`）之后才断的仍不重试，运行被中止不重试，`XIONGBAO_MODEL_NET_RETRY=off` 照旧关掉。有人看的单聊不变：思考仍实时显示，只在一个字都没吐时重试。本项不带迁移。
- **交付被接受之后，这一轮的收尾若被停掉或模型报错，不再记成失败。** 员工的 `deliver_task` 被接受之后，收尾那一小段如果被中止，或交付后提醒触发的那次模型调用出错，事件里会多一条运行错误，服务器以前据此把整轮记成失败：卡片标失败、这一轮的收尾带出错信息、不做复盘和记忆。现在只有「运行错误出现在被接受的交付之后、且之后没有再继续说话或调用工具」才不算失败，运行错误照样写进线程历史、照样给人看。交付之前的错误、被挡回或被拒的交付之后的错误、没有交付的错误、错误之后又继续了的，都照旧算失败。复盘日志行在有运行错误时多带 `runErrorKind`（`ended_early` / `segment_limit` / `other`，不含原文）和 `runErrorAfterDelivery`，评测的复盘日志也打这两项。本项不带迁移，没有开关。
- **交付被接受之后若还有提醒，只放行一步，然后这一轮结束。** 员工的 `deliver_task` 被接受后，如果还有提醒（计划里有没做完的项、改完文件没校验、说了没兑现的承诺），以前这一轮会继续，模型再调工具就一直跑下去（评测里一轮交付之后又调了 33 次模型，把后面的运行和复盘都拖乱）。现在只多放行一步：员工可以在这一步里补验证、补计划，这一步里的工具调用照常执行；这一步之后不再问模型，这一轮直接结束。这一步里又交付了一次且被接受，同样结束；被挡回的交付不算已交付，原逻辑不变；没有提醒的照旧交付后立刻结束。跟随 `XIONGBAO_DELIVER_ENDS_TURN`：设成 `off` 时完全照旧、不限步数。本项不带迁移。
- **员工用了技能的快路径，交付前必须先跑过技能自带的核对命令，否则第一次交付被挡回。** 评测里有员工照技能的快路径几步就交付，快路径算出来的值没核对，交上去的结果和预期不一致。现在：这一轮用到了带核对命令（`fastPathCheck`）的自写技能（这一轮开头附上了它的快路径，或员工用 `read_skill` 读了它），而员工这一轮还没运行过那条命令（`computer_run_command` 的命令里含有它即可，前面可以带 `cd <目录> && `，`<dir>` 换成实际目录，引号和空白不同都算；有几条时跑过任何一条就算），`deliver_task` 第一次被挡回，提示先跑「<命令>」并确认通过再交。每一轮最多挡一次，再交一律放行，不会让员工卡死；被挡回的交付不算已交付，卡片不动，交付后只给一步提醒的收尾不受影响。没用技能、技能没有核对命令时照旧。服务器每挡回一次写一行不含内容的 `{"type":"fastpath-check-bounce","runId":...}`，评测作业日志里多一行「交付前核对：挡回 N 次」。部署开关 `XIONGBAO_FASTPATH_CHECK_GATE=off` 关掉，默认开。
- **做完活之后的复盘，写进技能快路径的值不再「取第一个」。** 复盘给员工留技能时，快路径里凡是由输入决定的值（文件、币种、分隔符、列名等），现在要求写出这次验证过的选择规则（例如按任务说明或账单里写明的币种找对应的汇率文件、按表头判断分隔符），不许用「多个候选里取第一个」这种碰巧对的取法；只该有一个候选时先断言只有一个，取不到就停下说明。只改了复盘给模型的提示，技能格式、长度上限和安全规则都没变。本项不带迁移，没有开关。
- **做完活之后的复盘写出的技能，不再因为代码里的「对象.方法」被当成域名而转待审。** 技能步骤里的 `re.fullmatch(...)`、`os.path.join`、`json.load`、`self.id`、`s.split`、`df.to[0]` 这类 Python / JS 写法，以前可能被「要求访问或外发到网址或域名」的规则当成域名，技能就停在待审、下一轮用不上。现在：后面接着 `(`、`[` 或再一个 `.名字` 的不算；两位字母但不是真实国家顶级域的（`re.fu`）不算；`self`、`os`、`row`、单个字母变量等常见代码名字后面的属性不算。带 `http://`、`https://`、`ftp://` 的地址、`www.` 开头、IP 地址、像主机名的 `api.example.com`、`evil.io/x`、`foo.cn`，以及 `curl`、`wget`、`fetch`、`requests.get(` 后面的目标，照旧判中；其余安全规则没动。
- **做完活之后的复盘加了总时限，到点放弃。** 复盘从认卡、拼整卡轨迹，到复盘函数里的模型调用（含超时重试、追问快路径、改写破坏性命令、答「不值得」后的重问），现在整段最多 8 分钟（480 秒）；到点放弃，服务器日志写一行不含内容的 `{"type":"retrospect","outcome":"timeout",...}`（字段同别的复盘行），不存技能，放弃之后不再起新的模型调用，这张卡后面的轮仍会被复盘。以前复盘整段没有总上限，卡在某一步就一行日志也没有。单次模型调用的 120 秒超时等原有设置不变。部署开关 `XIONGBAO_RETRO_TOTAL_TIMEOUT_MS`（毫秒，默认 480000，写 `off` 不限）。本项不带迁移。
- **服务器日志多三种不含内容的诊断行，便于查「复盘为什么没有日志行」。** 一轮在服务器上结束、交给观察者之前写 `{"type":"turn-ended","kind":...,"runId":...,"failed":...}`（另带是不是个人租户）；复盘观察者入口写 `{"type":"retrospect-start","runId":...}`；观察者抛错以前被静默吞掉，现在写 `{"type":"retro-observer-error","error":"<错误码或类型，前 60 字>"}`，之后照旧吞掉，不影响这一轮。只加日志，行为不变，不带迁移。

- **DeepSeek 的思考模式默认打开了（期三）。** 模型地址指向 `api.deepseek.com`（或员工绑定了 DeepSeek 官方地址的模型）时，员工先想再做：思考内容作为推理事件随对话流出、跟着这一轮存档，刷新后还在；带工具的多步对话按 DeepSeek 的规则把思考传回去，不再中途回 400。**token 用量和等待时间会上升。** 单聊里思考折叠成可展开的「思考」块，刷新后仍显示「思考了 N 秒」，群聊的回复上方也有（每段最长 8000 字，超过截断并注明）。想关：设 `DEEPSEEK_THINKING=disabled`（改后要重新创建容器，全部员工关闭）；只关某个员工，在员工设置里关「思考模式」，或 `PATCH /api/agents/<id>` 带 `"thinking": false`。路由、起标题这类辅助请求仍不思考。别的模型供应商不受影响；经代理、OpenAI 兼容地址接入、名字是 DeepSeek 的模型，调过工具的历史消息也会补上 `reasoning_content`，免得一轮中途被拒。
- **看板交付：员工漏了交付会被提醒，交付时自动接活，必需项核对放宽。** 看板卡派的无人值守轮要结束却没调 `deliver_task` 时，提醒一次（`XIONGBAO_DELIVER_NUDGE=off` 关掉）。`deliver_task` 发现卡还没接下，就按卡上已有的验收标准自动接下（不报预计时间）再交付，省掉被拒、补接、再交的两三步；第一次干活时仍不自动接，因为验收标准和预计时间是员工自己写的。「必需：…」项的核对放宽：去掉标点和空白后整项或拆开的各段都出现就算对上，不含空格的中文段按相邻两字对上六成算对上，测试或校验类的必需项，自查里有通过的测试命令且没有失败字样也算；完全没提到的仍然挡回。`accept_task` 的结果会列出必需项原文，工具说明请员工把必需项写成短名称。
- **看板派活、群里 @ 派的活漏了交付，进「等验收」时带上员工写过的文件。** 员工做完没调用 `deliver_task` 时，这一轮结束卡会自动进等验收，以前交付物是空的；现在卡上带着这件活各轮里员工成功写过、改过的工作区文件（`computer_write_file`、`computer_edit_file`，只收工作区内的相对路径，去重，最多 20 个）。收尾读事件前会先等这一轮最后一批事件写进库（最多 5 秒）。调用过 `deliver_task` 的卡，交付物不动。

### 能放手让员工在后台跑（期九）

- **网页单聊里的电脑工具默认改由服务器执行。** 关掉网页、锁屏，员工照样把活干完（一轮最长 25 分钟，到点停下），回来能看到每一步，对话里有「后台进行中」标记，中断或到点后有「继续」。只有声明了「电脑工具交给服务器」的新前端的运行才这样跑，其余照旧由浏览器执行。`XIONGBAO_CHAT_SERVER_COMPUTER_TOOLS` 默认由 `off` 改为 `on`，设 `off` 回到电脑工具全由浏览器执行（保留一个版本）。
- **一轮边跑边落库，服务重启后会告诉你被中断了。** 对话的一轮在跑的时候，每 200 条事件或每 5 秒（先到为准）写一次库，状态记在新表 `thread_run_liveness`。进程死了之后，每个副本每 15 秒检查一次（启动时也查一次），心跳过期 30 秒的一轮标为中断，在对话里补一句「要接着做，请回复「继续」」；还没有结果的工具调用写明「服务重启时这一步正在执行，可能已经做了一部分，系统没有重新执行它」。**不会重放任何一步**，因为那一步可能已经花了钱或动了电脑。一轮最后那一小段还没合并写出的文字增量，进程死时会丢。
- **接管浏览器、输入密码、登录这三种要人的事，在服务器上等 10 分钟，超时后交还时自动续跑。** 人交还、填完或登录后，这一轮接着跑；等满 10 分钟还没人回，这一轮以「需要你」结束，服务器每 3 秒看一次电脑的状态，人回应后从停下的位置接着跑（接管和输入值的快照存进新表 `computer_waits`，登录沿用原来的登录请求，挂起时间从一刻钟延到一天）。员工从来看不到密码，只知道值有没有填。
- **单聊一轮跑完、你又不在这段对话的页面上时，会通知你。** 做完、出错、停下等你、到点、被重启打断都会通知，内容是员工名加回答的首句和用时；你自己点的「停止」不通知，群聊、看板、例程不走这里。走手机推送、已绑定的聊天渠道（微信等）、打开着的网页或桌面版的系统通知。设置里「通知」多了三个开关（手机推送、聊天应用、网页和桌面版系统通知），默认全开；同一段对话 60 秒内连续结束多轮只通知一次，`XIONGBAO_TURN_NOTICE_WINDOW_SECONDS` 调（`0` 是每轮都通知）。
- **修复：单聊由服务器执行电脑工具时，命令跑得久了页面报「网络错误」。** 运行请求和重连请求的事件流静默超过 10 秒会被默认的空闲超时断开，服务器上那一轮其实还在跑。现在静默满 8 秒就写一行 SSE 注释 `: keep-alive`，它不是事件，不进页面、不落库、不进回放。
- **新的 `.env.delivery` 示例里打开了「卡流看门狗」。** `AGENT_STALL_TIMEOUT_MS=60000`：它只看远端 agent，模型流静默超过 60 秒就结束这一轮并报 `AGENT_STREAM_STALLED`。已有部署的环境变量不变，不设就是关。

### 员工越用越顺：记忆、复盘、自己写的技能（期二）

- **个人版默认开记忆。** 个人版的员工现在也有记忆的四个工具（`recall_personal_memory`、`remember_personal_fact`、`save_observed_memory`、`forget_personal_memory`），每轮带上你的记忆，后台同步和记忆界面也都开着；之前只有团队版有。设 `XIONGBAO_PERSONAL_MEMORY=off` 回到旧行为（只对个人版生效）。`/api/capabilities` 多了一个 `memory` 字段，浏览器的记忆入口据此显示。
- **员工每轮结束后自动记下值得记的事。** 单聊每一轮结束后，用这位员工的模型从对话里抽出稳定的偏好、常用文件、联系人、固定流程，存成「待你确认」的记忆，你可以在记忆页审阅、编辑、删除。每轮最多 3 条，和已有记忆去重，每位员工每天最多抽 40 次（`XIONGBAO_MEMORY_EXTRACT_PER_DAY`，计数在进程里，重启重算）；带密钥、邮箱、手机号的不存，失败的轮、闲聊不抽，只在你自己的单聊里抽。**多一次模型调用，计入你的用量。** 没确认的记忆照样放进上下文，但标明「待确认」、排在后面，并告诉员工只是线索。`XIONGBAO_MEMORY_EXTRACT=off` 关掉。
- **个人记忆按相关程度挑着放进上下文，不再整包注入。** 按和你最新一条消息的相关程度，从最近更新的 200 条里挑，合计不超过 `XIONGBAO_MEMORY_INJECT_CHARS` 个字符（默认 4000，不是不小于 500 的整数就用默认），放不下的在末尾说明条数，员工用 `recall_personal_memory` 按需取；要回到旧行为设成 `24000`。同一线程里话题没变，这个记忆块逐字节不变（新消息没有实词，或和上次挑选时的消息词重叠相似度不低于 0.3），不让每轮都变的记忆块把整段历史的前缀缓存弄废；`XIONGBAO_MEMORY_STICKY=off` 关掉。
- **配上向量服务后，记忆按语义挑。** 新变量 `XIONGBAO_EMBEDDING_BASE_URL`、`XIONGBAO_EMBEDDING_API_KEY`、`XIONGBAO_EMBEDDING_MODEL`（兼容 OpenAI 接口，三个缺一个就是没配），向量第一次用到时才算（一次最多 48 条）、存进新表 `memory_embeddings`；没配或服务出错时仍按词的相关程度挑，对话不受影响。**这会把消息和记忆的文字发给向量服务，请只配你信任的服务。**
- **员工会把做成的活写成自己的技能，同类任务第二次照着做。** 新增 `save_learned_skill`、`refine_skill` 两件工具（和浏览器里请本人保存技能的 `save_skill` 是两件事）和一次「复盘」：一轮工具调用达到 15 步（`XIONGBAO_RETRO_MIN_STEPS`）、看板卡交付成功（至少 6 步，`XIONGBAO_RETRO_CARD_MIN_STEPS`，交付发生在这件活的哪一轮都认，同一张卡只复盘一次）、或本人验收通过一张卡之后，员工回看工具轨迹和每一步成没成，值得就存成技能（带「快路径」：脚本和校验命令，第二次先照它做）。**复盘多一次模型调用，计入你的用量**；用员工设置里的轻量模型（没设置用平时的模型）；每位员工每天最多 6 次（`XIONGBAO_RETRO_PER_DAY`，计数在进程里），另有冷却；交付成功的多步任务，模型答「不值得」时会重问一次；带运行错误但已交付的轮也照常复盘。只给这位员工自己用的立刻生效；步骤里有网址或域名（`subprocess.run(` 这类函数调用不算），或教员工绕过审批、忽略规则、做破坏性的事、瞒着本人、把文件发到外部的，不自动生效，进「学习」里的待审列表等你批准；只因递归删除要转待审的，先让模型改写一次再判。递归删除只拦根目录、家目录、绝对路径、变量、带 `..` 的、通配符、当前目录本身和 `--no-preserve-root`，工作区里清缓存、清构建产物的 `rm -rf .cache` 不算。邮箱换成占位符，带密钥、令牌、口令、手机号、证件号、银行卡号的整条不存。每位员工最多 50 条（`XIONGBAO_SKILLS_PER_EMPLOYEE`），最近 30 天没用过的在挑选时排到后面；在员工工具权限里关掉 `bot/save_learned_skill` 即不复盘、不给这两件工具。技能记录来源请求的指纹（只存哈希，不存请求原文），同类任务第二次靠它稳定命中。
- **员工自己写的技能改成「清单在提示里，正文用到才读」。** 提示里只列清单（最多 8 条，每条标题、id、什么时候用，不超过 160 字符），和这件事对得上的标 `[MATCH]`；对得上的第一条带快路径时，清单后面直接附快路径段（不超过 1400 字符）。读全文用新工具 `read_skill`（只带 id，只读得到这位员工自己写的，不排在 `search_tools` 后面，只在员工手上有自己写的技能时才给）。读出的全文留在对话历史里，不再每一步重发。人点了命令的技能照旧把正文放进提示；`XIONGBAO_PROMPT_SLIM=off` 回到原来的写法。
- **挑技能的模型调用按线程缓存。** 同一线程里新消息和上次挑选时的消息词重叠相似度不低于 0.6、技能目录没变、距上次不到 10 分钟，就复用上次的结果。`XIONGBAO_SKILL_CHOOSE_CACHE=off` 关掉。
- **员工设置新增「轻量模型」。** 巡检（主动检查）、员工给自己留的跟进、心跳、复盘和自动抽记忆这类轻量活可以用便宜的模型：`agents.configuration.lightModel`，`GET/PUT /api/agents/:id/light-model`，选项是对话里模型选择器那份目录，只有能编辑这位员工的人能改。没设置、或设置的模型已不在可用目录里，仍用平时的模型。设置界面这版没有，只有接口。
- **对话的自动压缩默认打开。** 以前要设 `SIDEBAR_AUTO_COMPACTION=true` 才会在一轮开始前压缩较早的消息；现在内置员工每一轮开始前，若上一轮已用 ≥ 上限减预留（上限的 10%），先压缩再跑。设 `XIONGBAO_AUTO_COMPACTION=off` 回到旧行为（保留一个版本）；原有的 `SIDEBAR_AUTO_COMPACTION=false`（或 `0`、`off`）仍然关，`XIONGBAO_AUTO_COMPACTION=off` 压过它。

### 常驻与主动（期三）

- **员工可以开「心跳」：隔一段时间自己醒来，照清单检查，没事静默。** 员工设置 `agents.configuration.heartbeat = { enabled, intervalMinutes, checklist }`（间隔 15 分钟到一周），接口 `GET/PUT /api/agents/:id/heartbeat`（读出带最近几次醒来的结果；只有能编辑这位员工的人能改；外部员工不开），员工设置页有对应的界面。员工自己用新工具 `update_heartbeat_checklist` 维护清单，只能改清单，不能自己开关或改间隔。醒来是共用 `work_items` 队列上的一条，一串接一串，模型那一轮是不挂在任何对话上的新线程，用轻量模型。**没事就静默**：只回 `HEARTBEAT_OK` 就收工，不往单聊里写、不发通知、不在看板上开卡；清单空着又没有卡可领的，连模型都不叫；有事才写进单聊、发通知、留一张卡。和巡检合起来共用每天次数上限，沿用巡检的几道关（本人关了主动检查、员工被暂停、管理员关了、本月额度）。已知限制：心跳那一轮不带电脑工具，清单里要碰电脑的事暂时做不了。`XIONGBAO_HEARTBEAT=off` 整个关掉（到点的醒来不领、不排下一次，已存的设置保留）。
- **安静时段：每个人可以设一段不被员工打扰的时间，默认对所有人开着。** 默认 22:00 到次日 08:00，按本人作息里的时区算，可以跨午夜。这段时间里员工自己主动的行为不做、对人的通知不发，都推迟到时段结束，不丢：心跳醒来、定时巡检、员工自己排的跟进、看板自主认领（只领紧急的卡）、送达核对器的催办，以及所有对人的通知（照常写进发件箱，到时段结束才发）。**不挡人亲自设好的后台工作**：例程和自动任务的定时触发、自动任务的外部事件、责任的事件唤醒照常运行，只是它们产生的通知同样推迟；对话里的回复、审批和提问，人自己点的「现在检查」也不受限。接口 `GET/PATCH /api/settings/preferences/quiet-hours`，设置页有界面。**升级后，没动过设置的人夜里员工不再主动找他、推送也推迟到 08:00**；`XIONGBAO_QUIET_HOURS=opt-in` 改成只有本人自己设了才算，`off` 整个关掉。
- **看板自主认领：员工自己领派给自己岗位、还没人领的卡。** 新接口 `POST/GET/DELETE /api/board-cards`：放一张卡（标题、说明、岗位=员工头衔、优先级 -100 到 100、是否紧急），读出每张卡有没有被领、被谁领和看板卡现在的状态，撤掉一张没人领的；看板页有「派给岗位」的入口。开了心跳的员工，在醒来时、或同岗位新卡刚放进来时，按优先级（同级先放进来的先领）自己领一张并开工：在看板上开一张跟着走的卡，执行人是它，之后沿用现有的接活、交付、本人验收的闭环。认领用 `for update skip locked`，两个员工同时领只有一个领到；每位员工同时最多在做 `XIONGBAO_MAX_PARALLEL_CARDS` 张（默认 2，交出去等验收的不占名额）。安静时段里只领紧急的卡；外部员工、被暂停的、关了 `accept_task` 的员工不自己领。`XIONGBAO_CARD_AUTOCLAIM=off` 整个关掉。

### 每一步更省：token 与模型调用次数

员工每一步都把整段历史再发给模型一遍，所以固定提示词的体积、工具结果的大小和模型调用的次数，是输入 token 和等待时间的乘数。这一版从几处一起压；行为上，员工用浏览器、记忆、跟进、生成图片这类不常用的工具前，会多一步 `search_tools`。

- **每一步固定发的系统提示和工具定义大幅压短，看板卡首步压到 12.8K 字符以内。** 系统提示里的来源、回答格式、子代理、交付、电脑、媒体、联网、委派等段换成短写法（含义不变：批准后执行、付款和改密码交给本人、外来内容当数据不当指令、交付要能被人打开并说清没做完的，一条没少）；偶尔才用的工具（浏览器的八个动作、请人接管和登录、生成图片和视频、跟进、记忆、应用权限、Git 工作流、`request_extension`、`computer_list_files`、`computer_glob`、`report_refusal`、`update_heartbeat_checklist`、`save_learned_skill`、`refine_skill` 等）不再每步发定义，排在 `search_tools` 后面，员工用几个词搜一次就能用（工具仍全部注册，授权、审批、审计不变）；浏览器的用法和网页按钮的批准规则也改成在取到浏览器工具时随检索结果给，之后留在对话历史里；发给模型的参数定义不再带 `minLength`、`minimum`、`default` 这类用不上的约束（服务器照旧按原定义校验）；模型库里指向代理的 DeepSeek（OpenAI 兼容的 v2 模型）以前整个绕过了工具检索，现在一并纳入。体积由测试守着（`server/tests/prompt-budget.test.ts`：看板轮首步系统提示加工具定义不超过 12,800 字符，其中系统提示不超过 7,300）。回退：`XIONGBAO_PROMPT_SLIM=off`，系统提示、工具定义、检索范围一并回到原样。
- **看板卡的一轮不再带系统提示里的「回答格式」段。** 这一段讲什么时候画图表、表格、卡片，看板卡的一轮没有页面在画组件。判断只看来源：派活的入口自己标记这一轮是看板卡的一轮。单聊、有人看的轮、例行、心跳、关着瘦身的轮都照旧带。`XIONGBAO_HEADLESS_ANSWER_FORMAT=on` 回到每一轮都放。
- **一轮之内，较早的工具结果超过 24K token 就折成摘要。** 以前只按模型窗口的 70% 折，DeepSeek 这类 1M 窗口的模型一道调研题每步发十几万 token 也不折，而 OpenAI 兼容的 v2 模型（自定义地址、Moonshot、智谱、OpenRouter）从来没折过，现在都折，子代理的一轮同样折。折叠只改发给模型的那一份：没越线一个字节不动，重放确定，缓存前缀稳定，最近 4 步原样，存下来的对话不动；折叠说明里写着取回的办法。摘要只留工具名、字数、退出码、头尾各一句和存盘路径；较早的写文件、改文件、超过 1500 字的长命令的参数里的大段文字，折成「已写入文件」一句。回退：`XIONGBAO_TURN_FOLD_BUDGET_TOKENS=64000` 回到 64K，`0` 关掉绝对预算（只按窗口的 70%），`XIONGBAO_TURN_FOLD=off` 整个关掉；`XIONGBAO_TURN_FOLD_BRIEF=off` 回到原来的摘要，`XIONGBAO_TURN_FOLD_CALLS=off` 不折参数。
- **大段的工具结果存进工作区，对话里只留头尾和路径。** 命令输出超过 8KB（`XIONGBAO_COMMAND_INLINE_BYTES`）、没指定行段的读文件超过 12KB（`XIONGBAO_READ_INLINE_BYTES`）、网页正文超过 8KB，完整内容存进工作区的 `tool-outputs/`，回传开头、结尾、路径和读法（读文件还带总行数和按行段读的办法）；员工没有电脑可存的，网页正文截到 8KB 并说明没存下来。这三个阈值原来都是 16KB；`XIONGBAO_COMMAND_INLINE_BYTES=16384`（或 `off`）、`XIONGBAO_READ_INLINE_BYTES=off` 回到 16KB。整条命令都是安装或构建（`bun install`、`npm ci && npm run build`、`pip install`、`make`、`cargo build` 等，带管道、分号、后面还跑别的脚本的不算）且成功时，只回传最后 12 行，完整输出存盘，失败时照旧给头尾，`XIONGBAO_QUIET_BUILD_OUTPUT=off` 关掉。发给模型的历史里，工具结果中的二进制数据（截图的 base64）换成一句说明，不再当文字发给模型，折叠估算也不再少算它。
- **一张看板卡少调几次模型：交付即收尾，接活、计划、命令不再各占一步。** 各有回退开关，默认都开，互相独立：交付被接受之后这一轮直接结束，不再为一句收尾的话多调一次模型（计划里还有没做的项、改完没校验时仍照旧提醒，被挡回的交付一步不省），`XIONGBAO_DELIVER_ENDS_TURN=off`；接活回执和第一批读取放在同一步发，`XIONGBAO_ACCEPT_WITH_READS=off`；更新计划和下一步动作放在同一步发，`XIONGBAO_PLAN_WITH_ACTION=off`；几条前后依赖、不需要看中间输出的命令用 `&&` 合成一条，`XIONGBAO_MERGE_COMMANDS=off`。
- **员工一步里可以发出多个互不依赖的调用，只读的电脑工具在同一步里并行执行。** 读文件、按内容搜、按名字找、列目录四个只读工具和同一步的其他调用一起开始；写文件、改文件、命令、浏览器动作仍然一个接一个，互不相关的几处修改也可以同一步一起发。`XIONGBAO_PARALLEL_TOOLS=off`：提示换回原写法，只读工具也不再并行。
- **员工收尾前的提醒改成看整轮，新增「改完必验」。** 看板派活、例行这类无头的一轮会被服务器切成很多次运行，早先写的计划、改过的文件在后面的运行里成了「历史」，计划还有没做完的项，一句话就收尾了。现在收尾提醒读的是整轮：计划里还有没做的项会被提醒；改过非文档文件（写文件、改文件，或命令重定向、`sed -i`、`mv`、`cp` 写出的代码或数据）、之后没有跑任何测试、构建或校验命令的，收尾前提醒一次（持有 `computer_run_command` 的员工才会收到）。走自定义地址、Moonshot、智谱、OpenRouter 的员工以前根本没有最后一步保护和收尾提醒，现在也有。测试命令（`bun test`、`pytest`、`jest`、`go test`、`cargo test` 等）退出码为 0 且失败数为 0 时，命令结果末尾加一句请收尾的提示。回退：`XIONGBAO_NUDGE_WHOLE_TURN=off`、`XIONGBAO_VERIFY_NUDGE=off`、`XIONGBAO_TESTS_PASSED_HINT=off`。另外，联网来源那一段加了一句「每个要点有一个可靠出处就够」；交付核对那一段加了一句：核对靠任务目录里的独立计算，不到目录以外找参考答案、判分或预期结果。

  and only connectors an administrator listed for self-install).
- **Device app (F2):** a desktop app 「熊宝数字员工 设备端」 (`com.xiongbao.device`) runs the runner,
  pairs, starts at login, shows the live screen and lets a person take over. Its own release workflow
  (`device-v*` tags) publishes unsigned builds only as prereleases.

- **Before upgrading: merge any catalogue server two administrators each added.** Migration
  `0127_team_connectors` makes every administrator's MCP server the team's, and the team holds one
  row per catalogue entry, so it stops before changing anything when two administrators' rows share a
  catalogue key. The error's DETAIL names each key and the rows that hold it (`tenant: server id`).
  To find them beforehand, run as the migration role:

  ```sql
  SELECT s.catalogue_key, array_agg(s.tenant_id || ': ' || s.id ORDER BY s.created_at) AS rows
    FROM mcp_servers s
   WHERE s.catalogue_key IS NOT NULL AND s.tenant_id <> 'system'
     AND (s.tenant_id IN ('team', 'platform', '')
          OR EXISTS (SELECT 1 FROM user_roles r WHERE r.user_id = s.tenant_id AND r.role = 'admin'))
   GROUP BY s.catalogue_key HAVING count(*) > 1;
  ```

  Do **not** remove the extra row from the Plugins page: removing a server revokes every person's
  connection to that catalogue entry and releases its grants, including the ones made through the row
  you keep. Merge directly instead, as the migration role, once per extra row (`<keep>` and `<drop>`
  are server ids from the query):

  ```sql
  BEGIN;
  -- People connected only through the dropped row keep their connection, now on the kept row.
  UPDATE mcp_user_credentials SET server_id = '<keep>', updated_at = now()
   WHERE server_id = '<drop>'
     AND user_id NOT IN (SELECT user_id FROM mcp_user_credentials WHERE server_id = '<keep>');
  -- The dropped row's own token or OAuth client is no longer used by anything.
  UPDATE credentials SET revoked_at = now(), updated_at = now()
   WHERE id = (SELECT credential_id FROM mcp_servers WHERE id = '<drop>') AND revoked_at IS NULL;
  DELETE FROM mcp_servers WHERE id = '<drop>';
  COMMIT;
  ```

  Grants are keyed by catalogue entry, not by row, so every Bot's grants are kept. What is lost: the
  dropped row's own tool list (the kept row has its own) and, for a person connected through both
  rows, the dropped row's connection (their connection through the kept row stays).

- **Before upgrading: re-enter each MCP server's token and OAuth client once after deploying.** An
  administrator's MCP servers and their tools now belong to the whole team (migration
  `0127_team_connectors`): every person's Bots can be granted them, and only an administrator
  changes them. Their secrets are sealed to the team too, and a person's call reaches a server's
  secret only for that server. Secrets stored before cannot be moved, because each one is
  cryptographically bound to where it was stored, so the migration revokes the token or OAuth client
  each moved server pointed at, and such a server answers "needs a credential this deployment no
  longer holds" until an administrator gives it its secret again. Model and connector keys are
  unchanged. An OAuth client is registered again on the server's page under **Admin → Plugins**. A
  server's own token is **not** entered on **Admin → Credentials**: that screen stores model and
  connector keys only, and a server refuses any credential that is not an MCP token minted for it.
  Until the Plugins page can replace the token of a server that is already added, an administrator
  sends two requests, signed in (the token is stored for the team because its kind is `mcp`):

  ```
  POST /api/admin/credentials
       {"kind":"mcp","provider":"<name>","keyId":"mcp-<name>","plaintext":"<token>","metadata":{}}
       -> {"credential":{"id":"<credential id>",...}}
  POST /api/plugins/servers         {"key":"<name>","credentialId":"<credential id>"}
       (a catalogue server; add "instanceHost" for one that has an instance address)
  POST /api/plugins/servers/custom  {"id":"<name>","title":"<title>","url":"<its url>","credentialId":"<credential id>"}
       (a server added by URL, with the url it already has)
  ```

  `<name>` is the catalogue entry's key for a catalogue server and the server's id for one added by
  URL, exactly, or the server refuses the token.

  Only rows somebody could legitimately have written move: a server stamped with a current
  administrator (or the platform), and a tool carrying its server's stamp. A server or tool row any
  other person had written for themselves is deleted (with the people's connections to that server),
  and from now on only an administrator writes either. For a vendor that registers itself (Notion),
  the first connect after the upgrade has to be an administrator's; a person who connects first is
  told so. A Bot's tool grants now always carry the Bot's own owner (or the team, for a shared Bot),
  and grants somebody else had written onto it are removed, except an administrator's, which are
  kept.

- The platform-hosted runtime and Automatic Learning are gone from this build. Threads, memory and
  what a Bot keeps live in this deployment's own PostgreSQL, so nothing has to be provisioned before
  the stack answers: `INTELLIGENCE_API_URL`, `INTELLIGENCE_GATEWAY_WS_URL`, `INTELLIGENCE_API_KEY`
  and the library's licence token are not read at all, and `INTELLIGENCE_MODE` is read only to be
  refused — set it to `local` or leave it unset, and naming `managed` stops startup with the reason
  rather than falling back quietly. **Admin → Automatic Learning**, `scripts/setup-learning.ts` and
  the `learning_settings` / `learning_thread_bindings` tables went with the mode (migration
  `0078_drop_learning`); a deployment skill somebody wrote stays in this database and is granted to
  Bots through **Admin → Skills**. Such a deployment now reports no `licenseStatus` at all, and both
  `scripts/start.sh` and the smoke journey were stopping a healthy stack over its absence.

- A cancellation the native host never collected is now dropped instead of being reported as
  pending forever. Every timed-out, stopped or revoked host operation queues a cancel for the desktop
  worker, and only that worker ever removed it: a worker that stopped polling left the entry in
  memory for the life of the process, so the Host access panel showed an operation that could never
  finish. A desktop that reconnects within the operation timeout is still told to stop.
- A Bot's shell now honours a Stop that landed before the command was spawned, not only one that
  arrives afterwards. A person who pressed Stop in the window between the request reaching the
  computer and the command starting got no answer until that command finished on its own.
- A file download refused because the computer's response carried no usable byte length now releases
  the connection before reporting the refusal. The unread body could be as large as the whole
  download budget, so a computer reached through a proxy that re-chunks left a transfer running and a
  connection checked out of the pool on every attempt.

- A conversation title cut at 60 characters no longer ends in half an emoji. `slice` counts UTF-16
  code units and an emoji is two of them, so a title cut between the halves rendered a replacement
  character in the sidebar and the picker, where the character itself should have been.

- A tool result that arrives before the call it answers is now paired with that call by the LangGraph
  Bot, as the sibling Bots already did. Read back from the durable thread store the result arrives
  first, which is a payload no provider accepts: a tool message with no preceding call, then a call
  with nothing following it. The model answers that with silence rather than an error, so the Bot
  stopped responding for the rest of the conversation.

- Pressing Stop now stops the computer even when the desktop worker never collects the instruction.
  A stop was queued with no timeout and the worker was the only thing that could ever remove it, so a
  worker that stopped polling left the entry in memory for the life of the process and the Host
  access panel showed an operation that could never finish, growing by one per press. Pressing Stop a
  second time also withdrew the first Stop before the desktop could collect it, and rejected a request
  that nobody was waiting for, which the server treats as fatal. A desktop that reconnects within the
  operation timeout is still told to stop.

### A computer refuses the cloud metadata address written through the NAT64 prefix

A Bot's computer is now refused the cloud metadata address when it is written through the NAT64
prefix (`64:ff9b::a9fe:a9fe` is 169.254.169.254), under every network policy including allow-all.
Only the plain and IPv4-mapped spellings were refused, so on a network with a NAT64 gateway the
metadata endpoint was one rewrite away. Browsing already refused this spelling; the computer's
filter now agrees.

### `?sslmode=require` on `DATABASE_URL` now connects to a managed database

A deployment pointed at RDS, Cloud SQL or Azure Database could not start. The server sent
`sslmode` to Postgres as a connection parameter instead of turning TLS on, so the connection went
out unencrypted and was refused with `no pg_hba.conf entry for host ... no encryption`, the very
error the Helm chart's README says `?sslmode=require` avoids. Migrations were unaffected, which is
why a deployment got as far as a migrated database and then crash-looped. `sslmode=require` now
encrypts the connection, and `sslmode=disable` turns TLS off. `sslmode=verify-full`, with an
optional `sslrootcert`, checks the certificate on Bun 1.4 and later and is refused on Bun 1.3,
which connects to any certificate. `verify-ca`, `prefer` and `allow` are refused with a message
naming the modes that work.

### A coworker the message speaks to is routed to without asking a model

Addressing a coworker by name went to the intent router like any other message, so the deployment
paid a model call to be told what the person had already said, and sometimes was told something
else. A message that speaks to a coworker by its full name now routes straight to them: it opens
with the name ("Risk Analyst, please check this"), names it with `@`, or asks it ("ask Risk Analyst
to review this"). It is recorded as `matched a coworker’s name in the message` with
`viaNameMatch: true` on the same `channel.routed` row. A name in passing ("don't send this to Risk
Analyst") and a word that only ends a name ("review this contract", "my meeting notes") still go
to the router. When the message addresses more than one coworker, or two share the addressed name,
it is refused with distinct labels, and the composer keeps the draft and asks the person to choose
instead of starting the default coworker. Explicit picker choices still use `viaMention: true`.

### A Bot's turn in a group is no longer offered coordination tools it cannot call

A Bot answering another Bot in a group conversation was offered `ask_person`, and `message_bot`
when hops allowed it, but every call was refused with "This run no longer has permission to
coordinate work in this conversation" and an `mcp.callback_refused` row nobody had caused. A run is
now offered these tools only when a call from it would be allowed, so that turn is offered neither.
A call that is refused anyway, from a schema offered earlier, is still refused and audited.
